### v1.3.0 — 2026-10-05 (issue #17 landed: the two Node floors became one number)

- **Rationale**: v1.0.0's one conflict was that **Astro 7 requires Node ≥ 22.12.0 and the root manifest advertised ≥ 20.19.0**, which the root manifest could not both advertise and satisfy — so the site became a self-contained subproject with its own higher floor. **Issue #17 raised the root floor**, merged 2026-10-05 as `>=24.15.0`, and the product owner then decided the site's floor rises to match it. The constraint that forced two *different* floors has therefore dissolved, and one clause of FR-008 asserted exactly that difference. Left as written it would be **false against the shipped tree**, which is the defect this document's amendment discipline exists to prevent.
- **Requirements changed, one by one** — **no requirement id was renumbered, added to, or dropped**; the counts v1.2.0 recorded (77 FRs, 9 NFRs, 10 SCs, 31 ACs) are unchanged:
  - **FR-008 — re-cut in place, id unchanged.** *Was:* *"The site's own manifest MUST declare a Node floor that satisfies its build tool, and that floor MUST be higher than the repository root's floor; the two floors are different requirements for different subtrees and both MUST be documented in [quickstart.md](quickstart.md)."* *Now:* the site's floor **MUST NOT be lower than** the root's, and **every other clause is retained verbatim** — the site still declares a floor in its own manifest, that floor must still satisfy its build tool, and both must still be documented in `quickstart.md`. **Not weakened, and the reason is mechanical**: the obligation was never *"be different"*, it was *"never ask for a Node the repository itself refuses"* — a subproject whose floor sat *below* the root's would claim a compatibility the repository does not have. A `not lower than` assertion forbids that direction and nothing else, and it now admits the equality the owner decided on. **The check is against the two manifests read at run time, never against a recorded root number**, which is why it survives equality and why the root's `24.15.0` is deliberately absent from the suite: the next legitimate change to the root's floor is not a failure here.
  - **No other requirement text changed.** AC-018 and AC-019 name **no version number at all** — AC-018 asks that the root verification command keep its steps, order, timeout, and test count, and AC-019 that the root's lint and TypeScript project report no file under `site/` — so **neither needed an amendment and neither was touched**. FR-007's own clause, that the root manifest's declared floor MUST remain unchanged **by this feature**, is unaffected: the site still adds nothing to the root manifest, and the root floor moved on `main` under issue #17, not here.
- **The dated records above are preserved, not rewritten.** `research.md` §1.4 and §2 are byte-preserved by this feature's own convention and the resolution is **appended as §9**, which records which of the three branches §1.4 set out is now history (branch 1 — raise the root floor — is what happened, and the rejection's *reasoning* did not survive it, because the host never reads root `engines.node`) and which is still load-bearing (branches 2 and 3 — no `workspaces`, self-contained subproject). `plan.md` and `tasks.md` keep their **dated reasoning** as Phase-4/5 records, per the same convention v1.2.0 recorded — but that convention is narrower than *"keep their wording"*, and this is where the line falls. **A dated record may say *why* a decision was taken; it may not assert a fact the shipped tree contradicts or point at a record that now says something else.** So `plan.md`'s constraint 1, its Technical Context floor row, its project-structure comment and **D1** — and `tasks.md`'s T-001 floor and its parallelization note — are **re-pointed at the merged floor**, and **D1's** rationale is restated on the invariant that actually sustains it. **No decision, rejected alternative, or wave boundary changed**: `site/` is still a self-contained subproject with its own manifest, its own lockfile, and its own gate. What was corrected is the *number* and the *pointer*, in both directions: `plan.md` and `tasks.md` also cited 005's amendment as `v1.16.0` throughout, which after the merge names main's Status-tab-cadence amendment (issue #20) rather than ours, so those citations and the `005 v1.15.0` baseline they sat beside now read `005 v1.17.0` → **`v1.18.0`**; the mirror-image staleness is corrected in 005's own documents, which cited **this** specification at `v1.0.0` and now read `v1.3.0`. ### v1.0.0 — 2026-10-05 (initial specification)

- **Rationale**: GitHub issue #11 asked for a GitHub Pages homepage with a landing page explaining what the tool does and help-style documentation for install, configure, use, and debug. The specification exists because the documentation had **two homes and no owner**: `README.md` (384 lines) and `specs/002-agent-event-extension/quickstart.md` (~180 lines, of which §6 spends 94 lines on the service store) both carried install, first-run, store, and troubleshooting prose, neither was authoritative, and the drift was already visible — `README.md` §Install tells the reader the approval dialog *"asks for exactly these four things"* and names `network`, while `AGENTS.md` invariant 3 records that `network` was removed by product-owner order on 2026-09-30 and is *"no longer requested at all"*. A third surface without a synchronisation requirement attached would have made that worse, so the feature amends 002 FR-042 rather than merely adding a site (see the table above).
- **What this version specifies**: 76 functional requirements in seven blocks (site shape; landing page; the four documentation pages; fidelity and the single-source rule; entry points; build, verification, publishing; the license), 9 non-functional requirements, 10 measurable outcomes, and 31 binary acceptance criteria.
- **The constraint that shaped it**: this is a **move**, not an expansion. 007 FR-049 requires each README section to map to exactly one site page with no substance left in both places, and NFR-006 measures documentation prose before and after against `.project-health/baseline.json` (`allDocProseLines: 10833`) so the move is falsifiable rather than asserted. The repository's most recent commit on `main` (`d2d3f40`, *"repository reduction pass — comments, tests, specs, instruction surface, lint config"*) moved that number in the direction of reduction.
- **The one conflict the feature had to resolve**: Astro 7 requires Node ≥ 22.12.0; the repository's root `package.json` declares `>=20.19.0` and, by `AGENTS.md` invariant 2, **may not** gain a `workspaces` key because it is simultaneously the npm dev package and the OpenChamber installable manifest. Raising the root floor belongs to issue #17. The resolution is a self-contained subproject with its own manifest, its own lockfile, and its own declared floor — which means **the root `npm run verify` cannot reach the site**, so the site's pull-request job becomes its only gate (FR-065, FR-069). That consequence is stated in `spec.md` → `## Clarifications` Q4 rather than discovered during implementation. Full evidence in [research.md](research.md) §2.
