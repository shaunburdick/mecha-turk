# Tasks: Documentation Site and MIT Licence

**Feature**: `specs/007-homepage-docs` · **Spec**: v1.1.0 (**approved** with 002 v1.13.0 and 005 v1.16.0, one package) · **Date**: 2026-10-05
**Input**: [spec.md](./spec.md) · [plan.md](./plan.md) · [research.md](./research.md) · [quickstart.md](./quickstart.md) · [`AGENTS.md`](../../AGENTS.md) · constitution v1.3.0
**Bar**: an operator who has never seen the product reads the site and can install, configure, use, and debug it without a second source; the README is a summary that points there; the About tab points there; the address serves five pages and no broken asset; and the repository's own gate is unchanged and green.

**Rules that bind every task below**:

- **`npm run verify` runs at every wave boundary and must stay green** — 1303 tests across 106 files today, and it must not decrease. It means build → lint → typecheck → test, unchanged in steps, order, and meaning (FR-070, NFR-007, AC-018).
- **Any wave that touches `src/`, `panel/*.ts`, or `service/*.ts` ends with `npm run build` and the rebuilt `panel/main.js` committed in the same commit** (`AGENTS.md` invariant 1). That is Wave 5, and it is the only wave that touches `src/`.
- **The root `package.json` is byte-identical after this feature** — no dependency, no devDependency, no script, no `workspaces`, no `version` change, no `engines` change (FR-007, AC-017). Task T-001 is a test that fails if it moves.
- **No suppression anywhere** — no `@ts-ignore`, no `@ts-expect-error`, no `# type: ignore`, and no `eslint-disable` added to accommodate the site (FR-072, invariant 7). The site directory is *excluded* from the root lint scope; that is a scope exclusion, not a suppression (FR-070).
- **Everything is offline and deterministic.** No live OpenChamber, no real PAT, no network, no browser download. The two operator-gated checks (the published address returning 200, and the first deployment being observed to completion) are named tasks, not tests.
- `[P]` marks a task that is parallel-safe: different files, no dependency on another task in the same wave. **`[P]` is a claim about file sets, not about time** — read the wave notes before trusting it.

## Wave count and honest sizing

**46 tasks in 8 waves.** The count is high because the work is genuinely wide rather than deep: five pages of documentation, four generated enumerations, a two-job workflow, an assertion script, five repository test changes, and a prose-budget measurement. The depth per task is small — most are one file and one sitting.

**Parallelizable, with one hard gate.** Waves 3 and 4 are almost entirely `[P]` and can be dispatched as parallel sessions; Wave 2 is parallel-safe after T-005. But **the whole feature is serialized behind one thing that cannot be parallelized: the site must build before any page can be checked against its declaration, and the build needs Node `>=22.12.0` while the content authoring needs the declarations to be stable.** A wave-based orchestrator is therefore reasonable but gains less than it usually does — expect the win to come from Wave 4's eight page tasks and Wave 6's three independent test suites, not from the whole. If you are dispatching rather than orchestrating, **dispatch Waves 1–2 as one session, Wave 3 as one, Wave 4 as four parallel sessions, and Waves 5–7 as one each.** Waves 7 and 8 cannot start before the PR is merged, so they are post-merge work.

**Content is the long pole, not plumbing.** The four documentation pages carry roughly 300 lines of prose that must each be traced to shipped code, and FR-049's prose budget means it is a *move*, not a writing exercise. Whoever takes Wave 4 should read the README's current text and the four spec blocks (FR-020 – FR-046) side by side before writing a word.

**Wave 4b status (2026-10-05)** — T-017, T-018, T-019 landed as **three `.astro` pages, not three `.md` ones**, and the extension is the one correction in this wave.

**Why `.astro`.** Astro 7 renders a markdown page as markdown: a component element or a `{expression}` in the body reaches the output as **literal text**. Measured on this tree before choosing: `<Permissions describe={…}>` arrived in `dist/install/index.html` escaped and unrendered, and `{OPENCHAMBER_ENGINE_FLOOR}` arrived unevaluated. A markdown page therefore cannot carry the generated tables FR-022, FR-029, and FR-038 require, and rendering them as retyped markdown would be exactly the second copy `declarations.ts` exists to prevent. The plan's own data-flow line reads `site/src/pages/*.md|.astro`; the landing page is already `.astro`; and AC-001 constrains the *addresses*, not the extensions. No requirement names an extension.

**What landed.** `install.astro` (111 lines), `configure.astro` (307), `use.astro` (186) — 604 lines of source, of which the components render the three tables and the prose is what the pages add.

**The three `describe` maps are complete, and that is measured rather than asserted.** Each is keyed by token, and each component throws on a missing key: removing `service` from the install page fails the build with *"the permission table has no description for \"service\"… (FR-022)"*, and removing `blocked` from the use page fails it with *"the dispatch-state table has no description for \"blocked\"… (FR-038)"*. The configure page supplies no `describe` — `SettingsFields` takes none, because the prose about a field is the field's own `format` string, read from the service.

**Two facts were traced to a source other than the README.** The install page's *"No network capability is requested"* line and the unsupported-surface paragraph were verified against `src/prerequisite-records.ts:202` and `src/status-tab.ts:398-402`, not against the walkthrough. **One build failure remains and it is not ours to fix.** `assert-build.mjs`'s `PLACEHOLDER_TOKENS` matches the substring `placeholder`, and `settings-fields.astro` renders the service's own `STARTING_PROMPT_FORMAT` — which contains the phrase *"with no placeholders"*.
