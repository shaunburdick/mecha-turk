## Problem Statement

Mecha Turk must turn GitHub activity — issue assignments, pull-request review requests and assignments, and mentions in comments and issue bodies — into agent-led work sessions inside the operator's own OpenChamber installation, without inbound firewall exposure, without a hosted control plane, and without Mecha Turk reimplementing the harness.

Feature 001 proved the extension path end-to-end as a spike (S1–S7 all passed, 2026-09-27) but as a single-account, panel-scoped prototype. Production needs are strictly larger: **N GitHub accounts** each with its own credential and rate-limit pool, **multi-repository polling** with durable checkpoints and correct deduplication across restarts and replays, **post-dispatch agent verification** so work is provably handled by the project-manager agent, and a **durable audit trail that survives an extension uninstall** (constitution v1.3.0, Security and Operational Standard 4 — `host.storage` alone is not an audit home). No single platform surface provides all of this: the panel is sandboxed and single-account, and the platform allows exactly one `integration` card per manifest (`001/research.md` §b.3 — **historical path**: the `specs/001-agent-event-orchestrator/` directory was removed 2026-09-28, commit `110c0a2`; recover it with `git show 110c0a2^:specs/001-agent-event-orchestrator/research.md`; the finding is restated as a requirement in FR-011 below).

This specification therefore describes the production system as an **OpenChamber extension (panel) plus an OpenChamber-hosted local guest service** — the product owner's approved "Option B" path. The panel is the configuration, dispatch, and observability surface; the service owns credential custody, GitHub polling over its own outbound HTTPS, and normalized event relay. OpenChamber keeps ownership of projects, worktrees, sessions, and agents.

**v1.13.0 — what the operator chooses when they bind a repository.** Binding a repository is where an operator decides what Mecha Turk will do with it, and until v1.13.0 that decision did not include *when the watch starts*. A binding whose scan loop had never completed a scan opened its window with **no lower bound at all**, so every open issue on the repository qualified whatever its age (FR-065 narrows the rule v1.0.0 established here). That is right for an operator who wants a staged backlog picked up and wrong for an operator who wants a repository watched quietly from now on, and it also means re-creating a binding after data loss re-triggers the whole past. Two behaviours in one, with no way to choose between them: that is the problem this amendment adds a field for. What makes it more than a field is that the same absence is how the product **recovers from a lost event queue** — the queue-recovery path clears checkpoints precisely so the next cycle re-detects what the lost rows carried — so the mode governs ordinary scanning and must never govern recovery (FR-073, FR-074).

## Architecture Decision (locked, 2026-09-27)

Two components, one extension package, one approval flow:

| Component | Owns | Never does |
| --- | --- | --- |
| **Panel** (extension iframe) | Configuration UX (accounts, repository bindings, triggers, policy, worktree option), account-token entry and one-shot handoff, project picker (`host.listProjects()`), dispatch via `host.startSession()`, run list, health display, post-dispatch agent verification | Holding tokens beyond the handoff, polling GitHub directly, creating/deleting projects, worktrees, sessions or agents, writing to GitHub |
| **Service** (OpenChamber-hosted local guest service) | Multi-account token custody in durable storage, GitHub polling over its own outbound HTTPS (headers, ETags, `x-ratelimit-*`), checkpoint/dedup/rate accounting, normalized event relay to the panel, service-owned audit history | Calling host APIs, spawning sessions, touching the harness, any GitHub write |
| **OpenChamber host** | Projects, worktrees, sessions, agents, the `serviceRequest` loopback transport, capability approval, the service process lifecycle | — (Mecha Turk never recreates these) |

Transport: `panel --serviceRequest--> host --HTTP 127.0.0.1:<ephemeral port>--> service`, request/response only (`001/research.md` §b.9 — **historical path**, removed with the 001 directory in commit `110c0a2`; restated in the Architecture Decision table above and in FR-002). GitHub traffic never crosses the panel→host leg; it originates in the service with its own credentials.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Configure GitHub accounts and repositories (Priority: P1)

As a self-hosting operator, I paste a GitHub personal access token for each GitHub account I work with, verify each account, and bind each repository to one account, one existing OpenChamber project, and a set of triggers — so that Mecha Turk knows what to watch and under which identity.

**Why this priority**: Nothing else in the system can run without accounts and bindings; this is the first screen an operator touches and the one every other story depends on.

**Independent Test**: On a clean install, add two accounts (paste token → verified login returned), bind one repository to an account and an already-registered project, enable issue-assignment and mention triggers, and observe the binding become `active` — without any CLI, any GitHub write, and with zero token bytes in persisted panel state, logs, or audit.

**Acceptance Scenarios**:

1. **Given** no accounts exist, **When** the operator pastes a fine-grained PAT, **Then** the service verifies it against GitHub `/user`, stores it outside `host.storage`, returns the numeric user id and login, and the panel displays `Connected as <login>`; the token appears in no storage, ledger, log, toast, or audit record.
2. **Given** the `service` capability has not been approved, **When** the operator attempts a token handoff, **Then** the handoff is refused with the approval instruction, and no token leaves the panel.
3. **Given** a verified account, **When** the operator adds a repository, **Then** they choose the account, then an existing project from the `listProjects()` picker, then per-repo triggers; if the desired project is not registered, the panel shows the manual "Add project" guidance and the binding stays in the recoverable `project_missing` state — no project is ever created by the extension.
4. **Given** two accounts with overlapping repository interests, **When** each repository is polled, **Then** each account polls only its own bound repositories under its own identity and its own rate budget.

### User Story 2 — An event arrives and a project-manager session is created (Priority: P1)

As a repository maintainer, I assign an issue to one of my configured account identities (or request a PR review, or mention it in a comment or an issue body) so that Mecha Turk discovers the event, applies policy, and starts an OpenChamber session attached to the source with the project-manager agent — without an inbound webhook and without me copying context by hand.

**Why this priority**: This is the product's core value: unattended conversion of GitHub activity into bounded agent work.

**Independent Test**: With one active binding and default policy, seed a new issue assignment for the bound identity, run the poller through a checkpoint boundary, and observe exactly one run and exactly one `host.startSession()` call whose session's read-back verifies against the configured `expectedAgent` baseline — or an explicit blocked state that explains why not. (With no baseline configured, v1.10.0, the read-back records the observed agent and compares nothing.)

**Acceptance Scenarios**:

1. **Given** an active binding and default autonomous policy, **When** polling observes an issue assignment to the bound account identity, **Then** the service normalizes a delivery, records policy approval, relays it to the panel, and the panel dispatches `host.startSession()` with the resolved `projectId`, the issue attachment, a bounded delimited untrusted-context excerpt, the configured worktree option, and the correlation id.
2. **Given** the same assignment observed again inside the 10-minute overlap window (or replayed 100 times), **When** deduplication runs, **Then** no second delivery, run, or session is created.
3. **Given** the dispatched session reports `onSession().agent` equal to the operator's Session Defaults → Default Agent, **When** verification completes, **Then** the run becomes `dispatched` and is listed with a link to the session.
4. **Given** the observed agent differs from the pinned default (or cannot be read), **When** verification fails, **Then** the run is marked `blocked:agent-mismatch`, an audit entry and a panel warning are recorded, and no further automated action occurs for that run.
5. **Given** a configured approval gate on "start work", **When** a matching event arrives, **Then** the run waits in `waiting_approval` and starts only after an auditable approval.

---

### User Story 3 — Observe runs and system health (Priority: P2)

As an operator, I see, in one panel, which accounts are connected, when each repository last polled, how much of each account's GitHub rate budget is spent, what the service is doing, whether the agent pin is holding, and every run with its source link and status — so that I can trust and explain unattended operation.

**Why this priority**: Constitution Principle IV makes unattended operation unacceptable without visibility; this story is what makes stories 1 and 2 operable over time rather than demo-able once.

**Independent Test**: With two accounts and three repositories running, open the panel after a service restart and confirm every health field renders from real state (service status, per-repo last poll, per-account rate usage, agent pin status), then trace one run from source issue to session using its correlation id.

**Acceptance Scenarios**:

1. **Given** a running system, **When** the panel opens, **Then** it shows per-account identity, per-repository last successful poll time and checkpoint age, per-account rate usage against budget, `serviceStatus()`, and the agent-pin verification result — with no secret material anywhere.
2. **Given** the extension is disabled, **When** polling stops, **Then** the panel (once re-enabled) reports the stopped interval honestly rather than masking it; while OpenChamber itself is not running, no polling occurs at all and this dependency is documented and surfaced as health.
3. **Given** a run in `blocked:agent-mismatch` or `blocked:project-missing`, **When** the operator inspects it, **Then** the panel states the exact cause and the manual step that clears it.

---

### User Story 4 — Recover safely from failure (Priority: P2)

As an operator, I want failures — a crashed service, a revoked token, a rate limit, a force-pushed PR head, a removed assignment — to stop work with a precise, auditable reason instead of silently retrying, duplicating, or guessing, so that I can fix the cause and resume without cleanup.

**Why this priority**: Unattended operation is only safe if failure handling is deterministic; this story is the operational half of constitution Principles II and III.

**Independent Test**: Kill the service mid-poll, revoke a token, and force-push a watched PR head; in each case confirm the checkpoint is preserved, the run states an exact blocked/retrying reason, no duplicate session exists, and clearing the cause resumes cleanly under the same run key.

**Acceptance Scenarios**:

1. **Given** a service crash, **When** the host reports `SERVICE_FAILED`, **Then** polling stops, checkpoints remain durable, the panel offers a manual retry, and no silent restart loop occurs.
2. **Given** a revoked or scope-insufficient token, **When** the next poll fails authentication, **Then** the affected streams block with the exact capability named, the token is never echoed, and other accounts continue unaffected.
3. **Given** PR head SHA drift or an assignment removed after discovery, **When** the service re-fetches before execution, **Then** the run pauses and requires a new trigger rather than acting on changed source state.
4. **Given** cleared causes, **When** the operator retries or replays, **Then** the original delivery identity and dedup rules are preserved and no duplicate work results.

### User Story 5 — Choose when the watch starts (Priority: P1 — added at v1.13.0, GitHub issue #22)

As a repository owner, I say when I bind a repository whether Mecha Turk should watch it **from now on** or **from now on and once look back over the last week**, so that a repository with a long assignment history does not open sessions for assignments I made months ago, while a backlog I deliberately staged ahead of time still gets picked up.

**Why this priority**: It is the default's behaviour, so every operator gets it whether or not they read the field — and it is a behaviour change. It also has to arrive together with User Story 4's recovery guarantee: the same mechanism that used to force a full replay is what makes data-loss recovery work, so a change to the first scan that did not leave recovery intact would trade one silent failure for another.

**Independent Test**: Create one binding per mode against a repository holding an assignment five days old and one assigned a minute ago, run one scan each, and read the events: the default-mode binding produced an event only for the recent assignment; the look-back-mode binding produced events for both. Then clear the queue through the recovery path and scan again: **both** bindings re-offered their in-window work.

**Acceptance Scenarios**:

1. **Given** a binding created with no explicit choice, **When** its first scan runs, **Then** the window opens at the binding's own creation boundary widened by the configured overlap, an assignment made before the binding existed produces no event, and one made since does.
2. **Given** a binding created in the look-back mode, **When** its first scan runs and then further scans run over the following days, **Then** the first scan covers exactly the assignments inside the fixed seven-day window and nothing older, and no later scan re-covers any of them.
3. **Given** one binding in each mode, both holding a completed checkpoint and dispatched work, **When** the event queue is quarantined and the recovery path clears their checkpoints, **Then** both bindings' next scans re-offer their in-window work, and neither scan had an unbounded window.
4. **Given** a binding created weeks ago whose first scan has still not completed, **When** the operator opens it after this version ships, **Then** it reads with the default mode, the stored file is byte-for-byte what it was, and its backlog is skipped — the accepted consequence of the default, not a fault.
5. **Given** an operator who reviews a repository where an old assignment never started work, **When** they open that binding, **Then** they can see the window it has been watching and since when, without reading a store file or a service log.

---

### User Story 6 — Land on the project I am already in (Priority: P2 — added at v1.14.0, GitHub issue #21)

As an operator working inside one OpenChamber project, I want the add form's project field to start on **that** project, so that binding a repository costs me no lookup I have already done just by being here.

**Why this priority**: it is a default, not a capability — nothing breaks without it, but every operator with a current project pays the lookup today, and the panel is the surface that already holds the answer (the ready context names the directory, the loaded project list names every project's).

**Independent Test**: With the host's current directory equal to a registered project's, load the panel, open a fresh add form, and read its *Dispatch project* field: it shows that project, nothing anywhere claims a pick was made, and `mecha-turk:project` is still absent. Switch the host's project with the panel open and read it again — unchanged.

**Acceptance Scenarios**:

1. **Given** a registered current project, **When** a fresh add form opens, **Then** its *Dispatch project* field shows that project and `mecha-turk:project` is not written.
2. **Given** the same load, **When** the operator picks a different project, **Then** that pick is what the draft saves into **that binding's** `projectId` — nothing is stored panel-side.
3. **Given** a fresh add form and a host current project that changes while the panel is open, **When** the panel is still open, **Then** the field keeps the value it opened with — the default is load-time only (FR-095).
4. **Given** the host reports no current directory, or one no registered project matches, **When** the panel loads, **Then** no default is displayed: the field opens exactly as it did before this feature — empty, with no provenance line to fall back to.

### Edge Cases

- **Same issue reached by two triggers** (assignment + mention): two deliveries with distinct delivery keys normalize to one deterministic run key → one run, both source references preserved.
- **Clock skew / delayed GitHub indexing**: timestamp overlap (10 min) plus delivery-key dedup; never a single global cursor — each endpoint/stream keeps its own cursor.
- **IDs not globally ordered across endpoints**: endpoint-specific checkpoint state; ordering assumptions never cross streams.
- **Pagination interrupted mid-window**: prior checkpoint retained, full safe window re-scanned; checkpoint advances only after the whole window is durably represented.
- **Comment edited or deleted between discovery and execution**: re-fetch the current source object; deleted, inaccessible, or ambiguous content is non-actionable and never triggers new work.
- **PR head force-pushed after discovery**: SHA drift detected at re-fetch → run pauses, new trigger required.
- **Assignment removed after discovery**: re-check before any downstream action, record the discrepancy, do not proceed as if assigned.
- **Token revoked, expired, or missing a required scope**: that account's streams block with the exact capability named; no token bytes in any error surface; other accounts unaffected.
- **Rate limit (primary or secondary) hit**: checkpoint preserved, `retry-after`/reset obeyed, bounded backoff with jitter, delayed status shown, no catch-up burst.
- **304 responses unavailable or unsupported on some endpoint**: correctness identical — conditional requests are an optimization only, never a dependency.
- **Project not registered in OpenChamber**: binding enters recoverable `project_missing`, dispatch blocked with the manual Add-project guidance; the extension never creates a project.
- **Agent pin absent or verification inconclusive**: run marked `blocked:agent-mismatch` (fail-closed); a session may exist but is never reported as valid work.
- **Service capability not approved**: no token handoff, no polling, panel states the required approval (the in-panel consent step this edge case also named was removed by product-owner order at v1.9.0; the static Accounts disclaimer carries its warning).
- **Unsupported surface (VS Code, mobile)**: explicit unsupported/disabled state; no claim that polling runs.
- **Service process crashes**: `SERVICE_FAILED`, manual retry, no silent loop, durable state intact.
- **Extension uninstalled**: panel UI state in `host.storage` is wiped (documented); service-owned durable records are the audit home and their uninstall behavior is verified and documented — audit history is never dependent on `host.storage` alone.
- **Empty state (fresh install)**: panel shows the setup-prerequisites checklist and an empty run list, not an error.
- **Error state (4xx/5xx/timeout from GitHub)**: bounded retry with backoff, checkpoint preserved, exact reason surfaced in health with correlation id.
- **An assignment or review request whose actor the event does not name** *(re-cut at v1.12.0, FR-045/FR-052 — the v1.11.0 text read "no readable subject author"; superseded wording recorded in changelog.md → `### v1.12.0`)*: the naming event's `assigner` / `review_requester` is `null`, `''`, or a bot. There is no identity to attribute to, so there is **no event this cycle** — no run, no work, nothing written for a later gate to guess about. Treated as non-actionable exactly as an unreadable mention author already is. **Nothing is substituted**: not the same row's `actor`, not the issue author, not the `assignee`. Because the scan window overlaps, the candidate is re-detected next cycle and the event is created exactly once, if and when GitHub has propagated a readable actor — so this costs at most one cycle of latency and is self-healing, not lost.
- **An assignment or review request performed by a bot** *(re-cut at v1.12.0, FR-045)*: the mention triggers already refuse bot-authored text (FR-016); the same refusal covers the other two kinds, read from the `simple-user` `type` on `assigner` / `review_requester` by the **same** `isBotAuthor` predicate. A bot cannot be attributed into an allow-list match, and there is no binding field that makes one allowed.
- **An in-window event that names a different subject** *(new at v1.12.0, FR-050)*: a `bob`-to-`carol` assignment alongside a legitimate `dave`-to-`bound` one on the same issue. The `bob`→`carol` event is **a different act** and is not used, even when it is the newer of the two; the attribution comes from the naming event. Symmetrically, a `review_requested` event naming a reviewer other than the bound account is not this trigger's evidence.
- **A naming event older than the scan window** *(new at v1.12.0, FR-051)*: an issue still sitting in `assignees`, whose assignment happened long before `lastScanAt − overlapMs`. There is no in-window naming event, so **no event is enqueued**. This is the correction working rather than a loss — a stale assignment is not new work, and gating a session on a decision nobody made this week would be the worse error.
- **A naming event beyond the declared page bound** *(new at v1.12.0, FR-051)*: an issue with a very long event history whose in-window naming event the bounded walk never reaches. The item produces **no event for this cycle** and the exhaustion is **recorded** with the item and the bound. The walk's stop rule is deliberately one-directional — it only stops on a page *entirely* outside the window — so a wrong assumption about GitHub's ordering spends budget, never visibility.
- **App or bot automation acting for a human** *(new at v1.12.0, FR-049)*: an event whose `actor` is an automation account while `assigner` is the human who asked it to act. The attribution is the **human**, from `assigner`, because that is the actor of the act; recording the automation would put an app's login into an allow-list comparison as though a person had assigned the issue. Untested on this repository's data — which has only ever had one human actor — so this is specified from the field's documented meaning rather than from observation, and the conservative direction is preserved either way (FR-052).
- **A stored row carrying `subject-author`** *(new at v1.12.0, FR-044)*: a row the shipped build wrote before this correction, sitting in `events.json` under an account that never cleans its queue file. It **parses**, it is **admitted**, the gate reads its `actorLogin` normally, and every surface renders it **with its basis stated** — the union member stays readable precisely so this row is not orphaned (NFR-011). What it may not do is mislead: the surface says the row was attributed under the rule in force when it was written, and does **not** claim GitHub fails to record the actor, because GitHub does.
- **An event re-detected under a changed allow-list** (v1.11.0, FR-046): the allow-list is **not** part of the event id, so tightening a binding's list cannot split one already-queued event into two, and loosening it cannot resurrect a deduplicated one. The gate is evaluated when the dispatch is authorized, against the binding as it stands then — never twice, never at a different answer.
- **A binding created with no explicit history-scope choice** *(new at v1.13.0, FR-053, FR-058)*: the mode is `new-only`. The binding's first scan opens at its own creation boundary widened by the configured overlap, so an assignment made before the binding existed produces nothing while one made a minute ago does. The default is the common case, not a fallback — the operator's only way to get the other behaviour is to ask for it.
- **An item that existed before the binding but was touched after it** *(new at v1.13.0, FR-066)*: in `new-only`, **it fires**. The comparison is on the event's own timestamp (FR-051), never on the item's age, so a pre-binding issue assigned today is detected exactly as a new one would be. A rule admitting only items *created* after the binding would judge the same trigger two different ways depending on when the binding was made.
- **An item older than the look-back window that is touched today** *(new at v1.13.0, FR-067)*: in `recent-history`, it fires if its **event** is inside the window. The item's age is irrelevant in both modes; only the event's `created_at` is compared.
- **A stored `historyScope` that is neither name** — a number, a boolean, an object, an array, the empty string, or an unrecognized string *(new at v1.13.0, FR-061)*: the bindings file is quarantined with a logged reason naming the field and the two accepted names, the poll loop scans nothing until the operator repairs it, and **nothing** is coerced, defaulted, or silently dropped. A stored `null` is **not** this case: it reads as *cleared to the default* (FR-062).
- **A stored creation stamp the clock cannot read** *(new at v1.13.0, FR-072)*: the window's baseline cannot be computed honestly, so the scan opens **no** window and creates no events for that binding, recording the reason. It does **not** fall open and admit every observation — the behaviour an unreadable stamp produced before v1.13.0, retired because it was the one remaining route to an unbounded window.
- **A first scan that keeps failing** *(new at v1.13.0, FR-066)*: the baseline does not move. It is not recomputed from a later clock on each attempt, so a binding whose credential stays broken returns the same window it promised rather than a later one, and cannot quietly exclude work it never failed to scan.
- **The queue is quarantined while a look-back sweep is in flight** *(new at v1.13.0, FR-073)*: the recovery replay takes precedence — it is the broader of the two and the one that recovers lost work — and the sweep's remaining content is still covered, because a sweep's window is bounded rather than absent.
- **A look-back sweep of a repository with more in-window items than one scan's page bound** *(new at v1.13.0, FR-083)*: the walk stops by the existing rule and the exhaustion is **recorded**. An item the walk never reached produces no event plus a recorded reason, never a partial answer — the posture FR-051 already sets, unchanged by the window having a lower bound.
- **A historical trigger whose naming actor GitHub will not report** *(new at v1.13.0, FR-071)*: no event, no run, no substitute actor, in `recent-history` exactly as in every other case. Looking further back does not relax who may be attributed.
- **The host's current project is registered** *(new at v1.14.0, FR-095, FR-097; recut at v1.15.0)*: a fresh add form opens pre-filled with that project. Saving the add form untouched stores the id in **that binding's** `projectId`; the `mecha-turk:project` key stays absent — it has had no writer since v1.15.0.
- **The operator clicks the displayed default to "keep" it** *(new at v1.14.0, FR-099; recut at v1.15.0)*: no change event fires, nothing is stored, nothing errors, nothing moves — the SDK select skips `onChange` when a click matches the value already displayed, and the default re-derives at the next load or refresh. Nothing can store it either: there is no pick key and no pick handler any more. **Pinning is not required to use the default**, and no control is added to make the same value pickable twice.
- **A manual pick exists from a pre-v1.15.0 install** *(recut at v1.15.0)*: nothing reads it. The `mecha-turk:project` key and every reader of it were removed with the panel-level picker (issue #39), so a value left behind in extension storage is inert and the default derives regardless of it.
- **The host reports no current directory, a directory no registered project matches, two registered projects sharing one directory, a list that is not `ready`, or a failed `listProjects()`** *(new at v1.14.0, FR-096)*: **no default** — the field opens empty, byte-for-byte the behaviour before v1.14.0; the project list's status line renders its honest loading/error/empty state, the select offers no options, no project is invented, and the feature blocks nothing.
- **The operator switches the host's project while the panel is open** *(new at v1.14.0, FR-095)*: nothing in the panel changes — not the form's field, not the add form's draft. The default is a load-time value; it moves only when the panel loads again or the project list is reloaded.
- **An add-mode draft carrying the default, saved untouched** *(new at v1.14.0, FR-097)*: the binding stores the default as its own `projectId`. That is the binding write the operator asked for by saving, not a stored pick of any kind; edit mode never does this because it never receives one.

## Requirements *(mandatory)*

### Functional Requirements

#### A. Architecture and platform boundary

- **FR-001**: The production system MUST consist of exactly one OpenChamber extension package containing a panel and one OpenChamber-hosted local guest service ("Option B"). The panel MUST provide configuration, dispatch, and status/run surfaces; the service MUST provide multi-account credential custody, GitHub polling over its own outbound HTTPS, normalized event relay to the panel, and service-owned durable state. OpenChamber remains the sole owner of projects, worktrees, sessions, and agents (Constitution Principle VII).
- **FR-002**: The manifest MUST declare `contributes.service` together with the minimum capability set required to operate (`sessions`, `prompt`, `service` — the `network` this requirement used to name as "implied by the declared integration" left the set with that integration on 2026-09-30, per FR-011 as re-cut at v1.8.0). The host MUST spawn the service on first `serviceRequest`; the service MUST listen on `127.0.0.1` only, MUST require `Authorization: Bearer <service token>` on every request including `/health`, and MUST be observable through `serviceStatus()` (`stopped | starting | ready | failed`).
- **FR-003**: The supported service surfaces are OpenChamber **desktop and web**. On surfaces where services are not spawned (VS Code, mobile) the panel MUST present an explicit unsupported/disabled state and MUST NOT claim that polling, custody, or relay is operating.
- **FR-004**: The panel MUST NOT create, delete, or mutate projects, worktrees, sessions, or agents. Repository-to-project resolution MUST use `host.listProjects()`; "project not registered" MUST be a first-class recoverable state with operator guidance, never an error and never an implicit creation.
- **FR-005**: All dispatch MUST go through the documented `host.startSession()` with issue/PR attachment (source id, title, url, kind, text, data), the resolved `projectId`, and the configured worktree option. No private UI route, undocumented API, or direct worktree/session manipulation is permitted.

#### B. Accounts and credential custody

- **FR-006**: The system MUST support N GitHub accounts. Adding an account is: panel input pastes a token → one-shot handoff to the service via `serviceRequest` → the service verifies the token against GitHub `/user` using its own fetch → the service persists the credential in service-owned durable storage outside `host.storage` → the service returns the numeric user id and login to the panel.
- **FR-007**: The panel MUST NOT retain any token beyond the transient handoff. Tokens MUST NOT be written to `host.storage`, the ledger, logs, toasts, run records, audit entries, or error bodies at any point. Panel-side handling is write-through only, and every surface that renders request/response material MUST apply redaction.
- **FR-008**: A security gate MUST precede any token handoff, in two mandatory parts: (a) the operator has approved the extension's declared capabilities (including `service`) at install time; (b) the panel MUST present a **static disclaimer beneath the Accounts section**, always visible and rendered from the canonical block the token-handoff contract §1.1 pins, that states, in plain language, that the GitHub token goes to the local service over the loopback proxy, that the service is sandbox-advisory and an allowed service has the operator's full user access, that the token is stored outside extension storage at file permissions and unencrypted (plaintext) on disk, and that a connection is recorded in the service audit as an occurrence only — never the token. The disclaimer is informational: **no Accept/Decline control, no stored acceptance, no version to renew, nothing to click** (002 v1.9.0). The credential routes MUST be gated by their remaining protections only — bearer authentication before route resolution, the loopback-only listener, body/size caps, shape-before-network validation, the verify throttle, and the redaction/logging rules — and the panel MUST NOT send a `consentVersion` member. No consent occurrence is recorded, because none is given to record.
  - ***Was*** *(v1.1.0–v1.8.0, superseded 2026-10-01 by product-owner order at v1.9.0)*: "A security gate MUST precede any token handoff. The gate has two mandatory parts: (a) the operator has approved the extension's declared capabilities (including `service`) at install time, and (b) the panel presents an explicit consent step before the first handoff that states, in plain language, that service permissions are advisory in Phase 1 and an allowed service has the operator's full user access. The occurrence of consent MUST be recorded in audit without any token material."
- **FR-009**: Account identity MUST be keyed by the numeric GitHub user id discovered from `/user` (durable); the login is display-only and MUST NOT be used as a durable key. If an operator-supplied expected-login constraint exists and disagrees with `/user`, the account MUST be rejected (fail closed).
- **FR-010**: The system MUST document and validate the credential scope matrix: `Metadata: read`, `Issues: read`, `Pull requests: read` (and `Contents: read` only if repository metadata is passed to OpenChamber). Write scopes are NOT required. Missing permissions MUST block the affected stream with the exact capability named, never silently downgrade. The GitHub Notifications API MUST NOT be used as a discovery source.
  - **Single-verdict note (Wave 2, documented by T-009m — FR numbering unchanged, L5)**: today the matrix is emitted as **one shared verdict for all four capabilities**, because GitHub reports a single granted-scope set per token: each capability reads `ok`/`missing` from the classic scopes GitHub returned, or `unknown` when it returned none (fine-grained PATs, GitHub App tokens). The fail-closed rules are unchanged by that shape — `missing` still pre-blocks the affected stream with the capability named, `unknown` is resolved by the first real 403, and neither ever silently downgrades (FR-010's operative requirement). Per-capability divergence would need response-specific probing and is deferred to a later wave rather than implied by Wave 2 output.
- **FR-011**: **Manifest integration card — retired by product-owner order (2026-09-30).** The manifest MUST declare **no** `contributes.integration` card at all: the host-managed GitHub token card the first release shipped (`apiOrigin: https://api.github.com`, `account.path: /user`, `scheme: bearer`) is removed, and with it the two products FR-011 named at v1.1.0 — (a) a connected-login identity badge in the panel and (b) an optional read-only connectivity/identity diagnostic. There MUST be no second credential surface: GitHub credentials are service accounts under this document's own custody rules (FR-006, FR-007), and **all GitHub traffic for polling, discovery, and dispatch originates in the service** — this clause is unchanged from v1.1.0. The product MUST be fully functional with no card present, and the panel MUST NOT render a card-derived identity, badge, or diagnostic anywhere: a panel holding no card state must not report one. The panel MUST NOT make a GitHub request of its own either — `host.request()` has no caller in panel source — so `network` is no longer an implied capability; `service` still is, from `contributes.service`.
- **FR-012**: Credential rotation and revocation MUST be supported without data loss: revoke on GitHub, replace the token through the account handoff flow, and retain all existing checkpoints, deliveries, runs, and audit history for that account.

#### C. Repository binding and triggers

- **FR-013**: Adding a repository MUST follow the sequence: choose account → choose an existing OpenChamber project from the `listProjects()` picker → enable per-repository triggers → choose the **history scope**, whether this binding watches the repository from now on or also looks back over recent activity once (FR-053, FR-089). **The project step MAY arrive pre-filled — with the current-project default and nothing else (FR-095, FR-097): the form opens with that project already selected, the operator keeps it by saving or changes it with an ordinary pick, and the pre-fill stores nothing (FR-096).** The history-scope step MAY be skipped, and skipping it is not a distinct choice: it means the documented default (FR-058). The supported target scale is fewer than 10 repositories per deployment.
- **FR-014**: Project creation is out of scope (no platform API exists). The binding form's **Dispatch project** select MUST carry a "not listed?" affordance that documents the manual steps (command palette → Add project, sidebar **+**, or folder browser) and MUST leave the binding in a recoverable state until a registered project is selected.
- **FR-015**: The trigger set MUST include, each independently toggleable per repository: (a) issue assignment to a configured account identity, (b) pull-request review request or review assignment for that identity, and (c) a configurable mention token appearing **either in a new issue/PR comment or in an issue body** — a mention in either place triggers (extended from comments only by operator decision, 2026-09-28; see `## Clarifications`). The mention token defaults to `@<login>` of the bound account, matches case-insensitively, and MAY be overridden per repository (for example a shared bot handle). Both placements share the same match, the same bot-authored-source exclusion (FR-016), and the same scan window; one issue body yields at most one mention event per bound account.
- **FR-016**: All trigger matching MUST be scoped to the identity bound to that repository. Events for other identities, bot-authored duplicates, and non-matching content MUST be ignored or audited as non-actionable, and MUST NOT create work.

#### D. Polling and discovery (service-side)

- **FR-017**: Discovery MUST be outbound HTTPS polling performed by the service, with a default interval of **60,000 ms** (configurable within 15,000–300,000 ms). No inbound listener, webhook endpoint, or webhook configuration exists in this feature. Discovery MUST use repository-scoped endpoints only.
- **FR-018**: For each account + repository + stream the service MUST persist a durable checkpoint containing endpoint/filters, last safely observed item id and timestamp, pagination position, conditional validators (`ETag`/`Last-Modified`) where captured, poll time, and credential/account scope. A checkpoint MUST advance only after the fetched page/window is durably represented in full. **The same durable state MUST additionally be able to say that this binding's checkpoint was cleared to recover lost work** (FR-074), and both facts MUST be written in the same atomic write, so neither can survive without the other or be inferred from the other's absence.
- **FR-019**: Polling MUST overlap the last observed window by **10 minutes** by default (configurable) and MUST deduplicate by a stable **delivery key** scoped to provider, account, repository, source type, source id, and event kind. Identifier-only cursors MUST NOT be treated as sufficient. **What the window is overlapped onto** has two sources, and both are bounded: a binding with a completed scan is overlapped onto that scan's recorded stamp, while a binding with none is overlapped onto the baseline its history scope fixes (FR-066, FR-067). The dedupe clause is therefore load-bearing on **both** new window-opening paths — the bounded look-back sweep and the forced recovery replay — and each MUST produce no second event, no second run, and no second session for the same trigger across a widened window, a repeated scan, a restart, and a re-run (FR-082).
- **FR-020**: Pagination MUST be processed completely or the prior checkpoint retained; `per_page` MUST NOT exceed 30, and responses MUST be paginated rather than fetched at provider page limits.
- **FR-021**: Because the service owns its own request and response headers, it MAY send conditional requests (`If-None-Match`/`If-Modified-Since`), read `ETag`/`Last-Modified`, and read `x-ratelimit-*` headers. Correctness MUST NOT depend on any of this: 304 handling is a feature-detected optimization, and every requirement in this specification MUST hold identically when conditional requests are unavailable.
- **FR-022**: Rate budget MUST be accounted **per GitHub account and shared across all repositories bound to that account**. The steady-state design point is approximately 600–1,500 requests/hour at the default interval for up to 10 repositories, within the documented 5,000 requests/hour authenticated limit. The service MUST honor primary and secondary rate-limit signals, `retry-after`/reset guidance, network timeouts, and transient 5xx responses with bounded exponential backoff plus jitter, and MUST expose next poll/retry time and remaining budget.
- **FR-023**: Polling schedules and checkpoints MUST survive restart, resume within the overlap window, and audit any replayed observation as duplicate or previously processed. **Restart survival, overlap resumption, the duplicate-or-previously-processed audit, deduplication, and source identity are unchanged and in force.** A rescan MUST be expressible as *a chosen lower bound for one binding's next scan*, without weakening deduplication or altering source identity — and **exactly one rescan mechanism MUST exist**, so that a rescan cannot mean two different things. **What that mechanism is required to support is the one caller this document specifies: the history-mode catch-up** (FR-084), which reuses it rather than introducing a second. **A general surface on which an operator chooses an arbitrary timestamp for an arbitrary binding is NOT required by this document and is recorded as debt in `## Out of Scope`**; nothing here promises it, and no requirement, plan, or acceptance criterion may be read as promising it. **A chosen lower bound is the window's start and nothing else**: the rescan is bounded exactly as every other scan is (FR-065), it deduplicates through the same delivery key (FR-019), it changes no source identity, and it MUST NOT offer to scan with no lower bound (FR-060).
- **FR-024**: The system MUST fail closed for unconfigured repositories, identity mismatch, invalid or expired credentials, unsupported API responses, ambiguous event classification, missing policy, unresolved projects, **and a scan-window baseline that cannot be computed from the stored record (FR-072)** — blocking with an explanation rather than proceeding or degrading silently.

#### E. Normalization, policy, and dispatch

- **FR-025**: Events MUST be normalized to the carried-forward event contract (**historical path**: `specs/001-agent-event-orchestrator/contracts/events.md` v1 — removed 2026-09-28 with the 001 directory, commit `110c0a2`; recover with `git show 110c0a2^:specs/001-agent-event-orchestrator/contracts/events.md`. The **live** record is `contracts/events-carry-forward.md`, which carries v1 forward as the reference schema and versions it additively to v1.1): kinds `mention`, `issue_assignment`, `review_request`, `review_assignment`; source identity scoped by provider/account/repository/type; untrusted, delimited content; correlation id. This feature may version the schema; the v1 record remains the reference.
- **FR-026**: Before any downstream action the service MUST re-fetch the current source object. Deleted, edited, inaccessible, or ambiguous content is non-actionable; assignment removal and PR head SHA drift MUST pause the run and require a new trigger, with the discrepancy recorded.
- **FR-027**: Policy MUST be autonomous-by-default for authorized actions, with per-action toggles (starting work now; future write/merge gates exist only as documented policy statements because this feature never writes to GitHub). A missing policy MUST fail closed for that action. Every policy decision MUST record policy version, actor/source, requested action, decision, timestamp, and reason.
- **FR-028**: Dispatch MUST call `host.startSession()` with: the resolved `projectId`, the source attachment, the configured worktree option (`none` | `generated` | `new:<branch-name>` with a `{number}` placeholder substituted from the source issue/PR number), a **bounded untrusted-context excerpt** (default: ≤4,000 characters per source item, ≤12,000 characters per dispatch, explicit truncation markers), explicit delimiters that prevent source text from altering system policy, credentials, approval requirements, or tool scope, and the correlation id.
- **FR-029**: **Agent pinning** MUST be configured through OpenChamber's own Settings → Sessions → Session Defaults → Default Agent (documented setup step: set it to **the agent your dispatches should run on** — the choice is the operator's, and this extension names none; v1.10.0); the extension MUST NOT attempt to pass an agent, model, or variant per call (the platform strips those fields). After every dispatch the extension MUST verify the agent via `onSession().agent`; if the observed agent differs from **the comparison baseline** (sourced as below), or cannot be read, the run MUST be marked `blocked:agent-mismatch`, audited, surfaced in the panel with a warning, and MUST NOT receive further automated handling (fail closed).
  - **Baseline source (amended 2026-09-28 by the product owner's card-emptied ruling, and 2026-10-01 by the product owner's blank-default ruling; the superseded wording — *the pinned default*, mirrored from the manifest setting `expected-agent`, and case (ii)'s fallback to `project-manager` — is recorded in `### v1.7.0` and `### v1.10.0`)**: the panel MUST read the comparison baseline from the **service configuration** — the `expectedAgent` member of the document `GET /v1/config` returns (006 FR-100) — and MUST NOT read it from the manifest, because the integration card carries **zero** settings (FR-041). **The documented default is the empty string, and empty means *no baseline configured***: nothing is assumed, so nothing is compared. **The fail-closed rule splits into two cases, stated so they are never confused**: **(i)** an *observed* agent that differs from a **configured** baseline, or that cannot be read, is the fail-closed condition — `blocked:agent-mismatch`, audited, warned, no further automated handling, exactly as above; **(ii)** a **baseline that is absent, blank, or unreadable** — service unreachable at verification time, the field absent from a document written before 006 v1.3.0, a value that fails to parse, or an operator's explicitly blank value — means **no comparison is possible**: the read-back MUST still run and MUST still record the observed agent, and the run MUST **proceed to verification** rather than be blocked for the baseline's own absence. In case (ii) the verification outcome MUST record **why no baseline was in force**, with its provenance — `configured` when a real value was read, `defaulted` when the document could not be read, `unset` when it was read and found blank — so an outcome taken without a comparison is explainable afterwards (003 FR-061's redaction rule; no credential material). **No mismatch may be derived from an absence**: with no baseline there is nothing to differ from, so neither a warning nor `blocked:agent-mismatch` follows from case (ii) alone. The baseline is read per verification (`next-dispatch`, 006 FR-100(e)); a save acknowledged before the next verification is in force for that one, with no restart and no service-side consumer.
- **FR-030**: Dispatch MUST be idempotent: every run carries a deterministic run key (provider, account, repository, subject type, subject number, action class). A run with a successful non-empty `sessionId` MUST NEVER be dispatched again; runs in `blocked` or failed states MAY retry only after the underlying cause clears, under the same run key, with each attempt audited.
- **FR-031**: The extension and service MUST be **read-only with respect to GitHub**: no comments, reviews, reactions, acknowledgements, labels, state changes, or any other write. There is deliberately no ack reaction — silence is preserved until the responding agent acts inside its own session. All GitHub writes are the agent's responsibility within its session.
- **FR-032**: Autonomous merge, deployment, repository administration, permission changes, and arbitrary shell orchestration MUST NOT exist in this feature under any policy setting (Constitution Principles II and IV).

#### F. Persistence, audit, and health

- **FR-033**: The service MUST durably own accounts, tokens, configuration, checkpoints, deliveries, runs, and audit history in storage that exists **outside `host.storage`**, located under the operator's OpenChamber data directory with operator-restricted file permissions and a location the operator can back up. The uninstall behavior of this store MUST be verified during planning and documented; it MUST NOT be assumed.
- **FR-034**: Panel UI state (selections, filters, last-viewed, bounded display mirrors) MUST live in `host.storage` with documented uninstall-wipe semantics. UI state MUST NOT be the sole home of audit history, checkpoints, or runs — `host.storage` alone does not satisfy the durability standard in constitution v1.3.0.
- **FR-035**: An append-only, bounded audit trail MUST record polls, checkpoints, observations, routing, credential identity (numeric id/login only, never a token), policy decisions, dispatches, agent verification results, retries, failures, and terminal outcomes — each with a correlation id and redaction metadata. Retention defaults MUST be documented and configurable without deleting the minimal references required to explain a run. **A change to a binding's history scope is a configuration change and MUST be recorded as one** (FR-086), so that the question *"why was this event not offered?"* is answerable from the trail rather than only from the binding's current value.
  - ***Clause removed at v1.9.0***: the list above no longer contains "**consent events**" — the `consent` audit event type left the vocabulary with the consent dialog (product-owner order, 2026-10-01; recorded in changelog.md). Rows written before the removal remain readable history and keep their sequence numbers; no writer emits the type any more.
  - ***Was*** *(v1.1.0–v1.8.0)*: "…credential identity (numeric id/login only, never a token), **consent events**, policy decisions…"
- **FR-036**: Health MUST be exposed and displayed: `serviceStatus()`, per-account identity and connection state, per-repository last successful poll and checkpoint age, per-account rate usage against budget, and agent-pin verification status. **Per-repository polling health MUST additionally carry the lower bound of the window that binding's next scan will use, and whether a recovery replay is in force for it** (FR-092) — the two facts that turn "this old assignment never started work" from a mystery into an answer. Disabling the extension MUST stop polling. The dependency that unattended operation requires OpenChamber (and its service) to be running MUST be documented and surfaced, never masked by an undocumented background mechanism (Constitution, Security and Operational Standard 3).
- **FR-037**: The system MUST support graceful shutdown, bounded queue and resource limits, bounded retries with backoff, dead-letter capture with manual replay under duplicate protection, and a non-looping crash response (`SERVICE_FAILED` → operator-initiated retry).

#### H. The actor allow-list (added at v1.11.0; GitHub issue #9 — FR-044, FR-045, NFR-011, SC-005, AC-024, and AC-025 **re-cut at v1.12.0**, which adds FR-049 – FR-052 and AC-028 – AC-031)

- **FR-043**: The normalized event MUST carry the **triggering actor** as first-class members, on the base snapshot every trigger kind shares: `actorLogin` — the GitHub login the event is attributed to — and `actorAttribution`, the closed union naming **how** that attribution was made (FR-044). Both are credential-free by construction (a login is public repository identity, never a secret), both are validated on write and on read like every other member, and an unrecognized `actorAttribution` value MUST refuse the record rather than default to a guess (FR-024). The normalized-event schema is versioned **additively** to `schemaVersion 1.2` for this addition, exactly as `1.1` was for the delivery key and the run linkage: **no existing member changes shape, nothing is removed, and `contracts/events-carry-forward.md` remains the live record of both versions.** This document owns the model; the **gate** that decides what the actor may do is 003's, and the **rendering** is 005's.
- **FR-044** *(re-cut at v1.12.0 — the proxy rationale was a false premise; superseded wording recorded in changelog.md → `### v1.12.0`)*: `actorAttribution` MUST be one of exactly two values, and the union **remains closed** — an unrecognized value MUST still refuse the record rather than default to a guess (FR-024). What changed is which values this build **writes**:
  - **`'direct'`** — **GitHub itself named the identity that performed the act.** Nothing is inferred, nothing stands in, and this is now the basis for **all four** trigger kinds. For the two mention kinds GitHub names the author of the text that carried the token — the comment's author for a comment mention, the issue's author for an issue-body mention. For the assignment and review kinds GitHub names the actor in a **dedicated field on the issue's own event record**: `assigner` on the `assigned` event, and `review_requester` on the `review_requested` event, both on `GET /repos/{owner}/{repo}/issues/{issue_number}/events`, both nullable `simple-user` members carrying `login` and `type` (FR-049, FR-050).
  - **`'subject-author'`** — **readable, and no longer produced.** The value stays in the closed union because the shipped build already wrote rows carrying it to `events.json`, and a vocabulary a stored file still holds cannot be deleted without invalidating that file; **the reader MUST accept it** and every surface that encounters it MUST render it rather than refuse the row, because a row the panel cannot read hides an **entire** dispatch. **No row written under this amendment may carry it**, and no requirement, path, or code may introduce a producer for it. It survives as a **record of what shipped**, not as a sanctioned attribution.

    **Why v1.11.0 believed otherwise, stated plainly because the belief is instructive.** It read the **two list feeds the poller happens to call** — `GET /repos/{owner}/{repo}/issues` exposes `assignees`, the *current* assignee set, with no actor behind it; `GET /repos/{owner}/{repo}/pulls` exposes `requested_reviewers`, the *current* reviewer set, with no requester behind it — and generalized from those two endpoints to GitHub as a whole. The list feeds really do name no actor. **GitHub does.** The actors live one endpoint away, on the per-item **events** feed, in fields whose names are the whole answer: `assigner` and `review_requester`. This is a research failure, not a design failure — a two-endpoint sample generalized to a provider — and it is recorded here, and in `research.md` §R8, because a specification that hides how it was wrong cannot be checked for being wrong again.

    **What remains genuinely true**, and is why the closed union keeps a second member rather than collapsing to one: an attribution is a **claim about provenance**, and a stored row may carry a basis this build would not have written. That is exactly what the pre-v1.12.0 rows are. An unrecognized value still refuses; a known-but-unproduced one still reads.
- **FR-045** *(re-cut at v1.12.0 — the actor for the assignment and review kinds is now the event's named assigner/reviewer, the unreadable-actor clause is narrowed to that actor, and the sentence requiring `PollPull`'s author fields is **struck**; superseded wording recorded in changelog.md → `### v1.12.0`)*: Attribution is **mandatory and fail-closed**. Every enqueued event MUST carry a readable, non-bot `actorLogin`, judged by the two judgements this product already applies to mention authorship and reused rather than reinvented: the exported `isBotAuthor` predicate — a `[bot]` login suffix **or** the account's `type === 'Bot'` — and the mentionable-author check beside it, which additionally refuses an identity GitHub would not name at all (`''`). Both judgements read the `simple-user` shape unchanged, because that is where `login` and `type` live on **every** actor member of every feed this product reads, the new ones included. Consequently: **(a)** a bot-authored comment, issue body, **assignment, or review request** is non-actionable and creates no work, which **extends FR-016's exclusion from the mention triggers to all four trigger kinds**; **(b)** an event whose **actor** is unreadable or bot-authored creates no event at all — it is dropped as non-actionable rather than enqueued with an empty actor for a later gate to guess about — and for the assignment and review kinds **that actor is the one the event names**, `assigner` or `review_requester`, so a `null` on that field is the unreadable case and is refused rather than filled from `actor`, from the subject author, or from anyone else (FR-052); and **(c)** no binding field may be written to allow-list a bot, because no bot event is ever created to be allowed.

    **Struck at v1.12.0**, from the v1.11.0 text of this requirement: *"To make FR-044's `subject-author` basis possible at all, `PollPull` gains `authorLogin` and `authorType` mirroring `PollIssue` and `PollComment`; without them the review kind has no identity to attribute to."* The stated purpose no longer exists — the review kind's actor now comes from the event's `review_requester`, not from the pull request's author — so **no requirement at v1.12.0 asks for those two fields**, and whether the implementation keeps or removes them is Phase 6's business and not a specification question. What replaces them is FR-049 and FR-050, which say where the review kind's actor comes from instead. The strike is recorded here rather than made silently because a requirement that quietly stops needing a field is the kind of drift a reader of the code would find before a reader of the spec.
- **FR-046**: The actor MUST **not** enter the deterministic event id. `evt-<owner>~<repo>~<issueNumber>~<accountNumericUserId>` plus its optional discriminator — `~mention~<commentId>`, the fixed `~mention~body`, or `~review` — is **unchanged by this amendment**, for the reason 003 FR-012 already gives for the same identifier: it is simultaneously the delivery's dedupe key, its relay path segment, and the reference recorded in existing panel ledgers, audit rows, and the run history. The actor therefore **rides the record and never its identity**. An issue observed once before this amendment and again after it produces **one** event, not two; and an issue observed once under one allow-list and again under another produces **one** event, because the policy is evaluated once, when a dispatch is authorized (003 v1.8.0), not again on each detection.
- **FR-047**: A binding MAY carry **`allowedUsers`**, an array of GitHub logins, with exactly three states and no fourth:
  - **Absent** — no policy is configured and **any human actor may trigger** this repository. Absent is a complete, valid state: the key is omitted, never written as `[]`, `null`, or `''` (the same rule 004 FR-022 set for `startingPrompt`, and for the same reason — "unset" needs no sentinel).
  - **Non-empty** — **exactly** those logins may trigger. Comparison is **case-insensitive**, because GitHub logins are case-insensitive and this document's own mention token already matches that way (FR-015); the stored spelling is preserved verbatim and only the comparison folds case.
  - **Explicitly empty (`[]`)** — **a refusal**, not "any user" and not "nobody". An empty array is ambiguous in exactly the way this product refuses to be ambiguous, and it is refused by the fail-closed binding validator with a field-level remediation naming the two honest alternatives (remove the field to allow everyone, or name at least one login). The way to stop every trigger is to **disable the binding**, which the store already models.

  The field is validated on **every read and every write** of the bindings document, by the service, in the same per-field collect-every-refusal posture as `startingPrompt` (004 FR-013, 004 FR-022, 004 FR-071) — a hand-edited file and a panel save are judged by one rule set or by neither. It rides the **existing whole-file grant** `GET` / `PUT /v1/bindings`; no new endpoint, method, or error code is added, and the per-binding `PATCH /v1/bindings/:bindingId` this document records as deliberate MVP-DEBT is not reopened. **This document owns the field's rules**; 003 owns the gate that evaluates it and 005 owns its rendering — the same three-way split every other binding field follows, and the reason no two of them re-specify it.
- **FR-048**: **Exactly one repository per binding is retained; pluralizing it, or adding a wildcard, is forbidden.** A binding is the edge **`repo → project`**: `binding.projectId` flows to the enqueued event's `projectId`, then to the run record, then to `host.startSession({ projectId })` (002 FR-013, FR-028; 003 FR-010's run key; 005 FR-053). A binding spanning several repositories would make *"which project does this dispatch into?"* ill-defined, and the product owner considered and rejected both the plural `repository` and a wildcard on exactly that ground. The three scenarios GitHub issue #9 asks for are therefore expressed as **N bindings**, which is expressible today and needs no new structure:
  1. *A specific list of users on a specific list of repositories* → **one binding per repository**, each carrying that list. The list is repeated per binding; there is no shared-list object, because a shared list would be a second thing with a second lifecycle and a second validation rule.
  2. *A specific list of users on any repository* → **one binding per repository**, each carrying the **same** login list. "Any repository" means *every repository the operator chooses to bind*, not a wildcard — the binding is created per repository exactly as it is today, and the login list is repeated by the operator.
  3. *A specific list of repositories that allow any user* → **N bindings with no `allowedUsers`**, which is precisely today's shipped behaviour: absent means any human may trigger, and 005's rendering says so in words wherever the binding is listed.

#### H2. Naming the actor of an assignment or a review request (added at v1.12.0)

Four requirements, and they exist because FR-044's corrected premise is only half a specification. *That* GitHub names the actor says nothing about **how the poller reaches those fields**, **which event answers which candidate**, **what the scan window means against an endpoint with no window parameter**, or **what happens when the actor is not there**. Those four answers are FR-049 – FR-052, and none of them is a detail: each one is a place where the obvious implementation guesses, and each guess would be a wrong actor in the audit trail or a session started for someone nobody vouched for.

- **FR-049**: **The actor for the assignment and review kinds is read from the item's own event list, and only for an item already detected as a candidate.** When — and only when — the issues or pulls **list** feed has already identified an item as an **assignment candidate** or a **review candidate** for the bound account, the poller MUST read **`GET /repos/{owner}/{repo}/issues/{issue_number}/events`** for **that item** and take the actor from that response. Three rules bound it:
  1. **Per item, never repository-wide.** The repository-wide `GET /repos/{owner}/{repo}/issues/events` and the `GET /repos/{owner}/{repo}/issues/{issue_number}/timeline` MUST NOT be called for attribution. The reason is not tidiness and should be read as the design it is: a repository-wide read costs one to two requests **every cycle regardless of whether anything matched**, and — because these endpoints have no server-side window (FR-051) — it would need its **own** pagination-truncation concept, since a busy repository can push a rarely-scanned binding's in-window events past the page cap. Per-item reads cost **zero** when nothing matched, are small when something did, and introduce no second truncation surface. **A pull request is an issue** to GitHub and is served by the same path; the `issue.pull_request` member on the response is what distinguishes the two.
  2. **Read-only.** This read is a discovery read like every other the poll loop makes. It MUST NOT write to GitHub, and it inherits FR-031's read-only-to-GitHub rule verbatim.
  3. **Same budget, same discipline.** The read MUST be charged to the **same per-account rate budget** as every other request (NFR-003), MUST honour `retry-after` and the bounded backoff ladder on failure (FR-022), and MUST NOT be issued more than **once per candidate item per cycle**. Cost model, stated so the budget arithmetic is not a surprise: **zero** requests when no item matched; **one** request per matched candidate item per cycle, on top of the list-feed scan the cycle already performs.

  The response members this requirement reads, and nothing else: `event` (the kind word — the schema carries **no enum**, so an unrecognized word is ignored rather than treated as a known kind), `assigner`, `review_requester`, `assignee`, `requested_reviewer`, `actor`, `created_at`, and the `issue` member's `number` and `pull_request`. **`assigner` and `review_requester` are the fields to read, not `actor`.** In every row observed on this repository `actor` equalled the explicit field, but the explicit field is the correct one: `actor` is documented as *the person who generated the event*, while `assigner` and `review_requester` name the actor **of the act**, and the two can differ for app and bot automation — where the event is generated by the app and the assignment is performed by the human who asked it to. Reading `actor` would record the automation as the person who assigned the issue.
- **FR-050**: **The correlation is closed, and an event that does not name the bound account is a different act.** Given a candidate item, exactly one rule per kind selects the event that answers it, and there is no fallback to another event, another field, or another kind:
  - **Assignment candidate** → the event is an **`assigned`** event on that item whose **`assignee.login` is the bound account**. Its actor is that event's **`assigner.login`**. An `assigned` event naming a *different* assignee is a different act and MUST NOT be used, even when it is newer.
  - **Review candidate** → the event is a **`review_requested`** event on that item whose **`requested_reviewer.login` is the bound account**. Its actor is that event's **`review_requester.login`**. A `review_requested` event naming a *different* reviewer is a different act and MUST NOT be used, even when it is newer.
  - **Where several qualify** — a bulk assignment that touches the bound account more than once inside the window, or the same account re-assigned and re-unassigned — the answer is the one with the **greatest `created_at`** among the qualifying events (FR-051). The event word alone is not the filter: `unassigned`, `closed`, `labeled`, `referenced`, and `head_ref_deleted` are all kinds the endpoint returns, and none of them is an answer.

  **The asymmetry, stated because it is easy to read backwards.** The subject field is the one that must match the bound account — `assignee` for an assignment, `requested_reviewer` for a review request — because those are the identities FR-015 makes the trigger *about*: an issue assigned **to** the bound account, a review requested **for** it. The actor is read from the **other** field on the same event. Matching on `assigner.login` instead would be a different product: it would fire on *the bound account having assigned somebody*, which FR-015 does not specify and which the intake's own rule — *an event that does not name the bound account is a different act* — rules out, since such an event names the bound account as the **performer** and somebody else as the subject. Both fields are **nullable**, and a null on either fails closed under FR-052; neither may be defaulted from the other.

  **A consequence worth stating, because it is a behaviour change and not only a new capability.** Requiring an **in-window** naming event means an assignment made long before the window no longer enqueues anything, where the v1.11.0 list-feed-only build would re-fire on it every time the item re-entered the scan. That is the correction working: a stale assignment is not new work, and an allow-list evaluated against an assignment from months ago would gate a session on a decision nobody made now.
- **FR-051**: **The scan window is applied client-side on `created_at`, because the endpoints have no window parameter.** `GET /repos/{owner}/{repo}/issues/{issue_number}/events` accepts **only** `per_page` and `page`. It has **no `since`**. Neither does the repository-wide `GET /repos/{owner}/{repo}/issues/events`; nor does `GET /repos/{owner}/{repo}/issues/{issue_number}/timeline`, which adds only `exclude`. No requirement, plan, or implementation may therefore send a `since` parameter to any of them or assume one exists. The in-window test MUST be a **comparison the service makes** between the event's `created_at` and the same window start the list feeds are scanned with, with the overlap semantics unchanged. **What that window start is has two sources and no third** *(re-cut at v1.13.0 — the v1.12.0 text ended "…`lastScanAt − overlapMs` — with the existing overlap semantics unchanged, **including the replay case**", and the replay case is retired as a window source)*: for a binding with a completed scan it is that scan's recorded stamp minus the configured overlap, and for a binding with none it is the baseline its history scope fixes (FR-066, FR-067). **A scan never opens with no window at all** (FR-065), so there is no case in which this comparison has nothing to compare against and admits every observation; what the comparison decides, and how a candidate is selected among qualifying events, is unchanged.
  - **Ordering is not relied upon.** Selection is by **maximum `created_at`** among qualifying events, never by position in the response. A fixture whose events arrive newest-first, oldest-first, or interleaved MUST produce the same actor. This is a deliberate choice against the cheaper "the last matching row wins" implementation, which is correct only as long as GitHub's undocumented ordering holds and silently picks the wrong actor the day it does not.
  - **The page walk is bounded, and its stop rule is conservative.** The walk uses the `per_page` bound the product already declares (≤30) and stops when a page arrives whose events are **all** older than the window start. Because the rule requires the *whole* page to be outside the window, an ordering assumption that turns out to be wrong can only cause **over-fetching** — more requests until the bound — and can never cause the walk to stop early and miss an in-window event. That asymmetry is the point: the failure direction must be wasted budget, never a silently unattributed trigger.
  - **Exhausting the bound fails closed.** If the walk reaches its declared maximum page count before such a page arrives, the item produces **no event for this cycle**, the exhaustion is **recorded** with the item and the bound (constitution IV — an operator must be able to explain a missing trigger), and the attribution MUST NOT be taken from the partially-seen list. The page bound itself is a planning constant; what this requirement fixes is the **behaviour at the bound**, which is the part a test can hold it to.
- **FR-052**: **An actor that cannot be read produces no event this cycle, and the next cycle asks again.** For an event that FR-050 selected, the actor is `assigner.login` or `review_requester.login`. If that member is **`null`**, or the account is **unreadable** (`''`), or the account is a **bot** (FR-045's `isBotAuthor`), then **no event is enqueued for this cycle** — no run, no work, and nothing written for a later gate to guess about. Specifically **forbidden** as substitutes, each of which was available in the v1.11.0 build and each of which would record a guess as a fact: the event's `actor` member, the issue or pull-request author, the `assignee` or `requested_reviewer` on the same event, and any previously recorded actor for the same item. This is the existing `isAttributableAuthor` posture — one judgement, now applied to the actor the event names — and it is FR-045(b) landing on the corrected actor.

  **The case is self-healing, and that is why refusing is honest here rather than lossy.** The scan window **overlaps** — it starts at `lastScanAt − overlapMs`, not at `lastScanAt` — so the same candidate is **re-detected on the next cycle**. A `null` because GitHub had not yet propagated the field is therefore asked again, and creates its event exactly once, on the cycle where the actor becomes readable. Refusing costs at most one cycle of latency; guessing would cost a permanently wrong attribution in the audit trail, which is what constitution IV forbids and what no latency is worth.

  **What is untested, stated rather than assumed.** Every behaviour above was verified against this repository's own data and against GitHub's OpenAPI description for the endpoint. Three cases were **not**, and none of them is guessed:
  - **Bot and app actors** on `assigner` / `review_requester` — unobserved here, this repository having only ever had one human actor. Handled by the existing bot predicate, which reads the `simple-user` `type` the same way it already does on every other feed; if a future row shows a bot that predicate does not catch, the outcome is a refused event, not a granted one.
  - **Bulk assignment** — several events naming the bound account inside one window. Handled by the maximum-`created_at` rule (FR-050), which is defined for it whether or not it has been seen.
  - **A `null` `assigner` or `review_requester`** — never observed. Handled by FR-052's refusal, deliberately, and the requirement is written so that a `null` fails closed **even though the `actor` member on the same row would usually have been readable** — because that is precisely the substitution that would make the correction cosmetic.

#### I. The binding's history scope (added at v1.13.0 — GitHub issue #22, FR-053 – FR-094)

One optional field on the binding record, and one rule: **where a scan window's lower bound comes from.** The mode decides a window's start and nothing else — which triggers exist, who may cause one, and how one is dispatched are untouched. This section is the authoritative text for the field; the gate at dispatch authorization stays 003's and the rendering stays 005's.

**FR numbering in this section**: `FR-053` onward, sequentially, grouped `I.1` field · `I.2` validation · `I.3` window rule · `I.4` forced replay · `I.5` the look-back sweep · `I.6` audit · `I.7` the operator's surface. `FR-001` – `FR-052` keep their numbers and their meanings except where this section says otherwise; nothing in this section renumbers them.

##### I.1 The field: schema, ownership, persistence, back-compatibility

- **FR-053**: A binding MAY carry one optional member **`historyScope`**, whose value is exactly one of the two names **`'new-only'`** or **`'recent-history'`**. **The documented default is `'new-only'`** — the mode a binding created without an explicit choice has, and the mode a binding storing no member has. **Two names, and no third.** There is no boolean spelling, no stored duration, no `null` meaning, no wildcard, and no empty string — in the wire, in the store, in a panel submission, in an audit row, or in an error body. The two names are fixed here because they travel in the persisted record and in the audit trail.
- **FR-054**: **Ownership: service-owned configuration.** `historyScope` MUST be persisted by the service in the service-owned bindings store alongside the other binding members, MUST NOT be written to `host.storage` by the panel, and MUST NOT be mirrored into the panel's ledger, a run record, or any shipped bundle. **Its value is one of two fixed names, so it carries no credential-shaped material** and needs no secret-scan exemption, redaction rule, or new assertion — unlike 004's starting prompt, which is free text and is the reason that field required those.
- **FR-055**: **Read path.** The bindings read MUST return the stored mode for every binding, including for a binding that stores no member — in which case it returns the documented default, so the operator's surface renders from one source of truth. No run, dispatch, or audit surface returns it as configuration: the audit trail names it as a change (FR-086) and the health surface names it as derived state (FR-092).
- **FR-056**: **Write path.** The bindings write MUST accept `historyScope` on each binding and validate it through the same fail-closed, additive, field-plus-remediation validator the other binding members use — the posture FR-047 already states for `allowedUsers`. **It rides the existing whole-file grant** `GET` / `PUT /v1/bindings`; no new endpoint, method, or error code is added, and the per-binding `PATCH /v1/bindings/:bindingId` MVP-DEBT is not reopened.
- **FR-057**: **Omission preserves; an explicit value sets.** In a whole-file write, a binding submitted **without** a `historyScope` member MUST keep whatever the store already holds for that binding. An explicit accepted name MUST set it, and an explicit `null` MUST clear it back to the documented default. Omission-preserves is required because the surface is a whole-file replacement: a client that does not know the member would otherwise erase a deliberate choice on its next unrelated save.
- **FR-058**: **Absence has exactly one reading, everywhere.** A binding carrying no `historyScope` — written before v1.13.0, or cleared — reads as **`'new-only'`**. There is no third state, no legacy reading, and no per-record-age behaviour. **Two consequences, both stated rather than discovered.** First, **the upgrade writes nothing**: no bindings file is rewritten, quarantined, repaired, or re-saved, no checkpoint is reset or seeded, and no binding's behaviour changes until the operator next edits it or a scan next runs for it. Second, **a pre-existing binding whose first scan has still not completed will skip its backlog after the upgrade**, because its baseline is now its creation boundary rather than the absence of one. That is the default doing what it says, and it is accepted rather than treated as a fault.
- **FR-059**: **The look-back length is a service-declared constant, not a configuration field.** It MUST be declared **once**, with a documented lower and upper bound it is required to satisfy, and it MUST NOT be a member of the service configuration document. It MUST NOT appear in the configuration schema projection, MUST NOT render as a Settings row, MUST NOT be writable through the configuration surface, and MUST NOT change 006 FR-010's or 006 FR-084's documented count of twelve fields. The operator does not choose the number, and a value the operator cannot change does not belong on the surface that exists for changing values.
- **FR-060**: **The stored shape cannot express an unbounded replay.** No combination of stored members may produce a scan with no lower bound. The mode's domain is the two names of FR-053, the mode is not a duration, and the look-back is not stored at all (FR-059) — so there is nothing in the record to set to zero, to `null`, or to absent in order to ask for *everything*. A stored document requesting it cannot be written, because no value requests it.

##### I.2 Validation and refusal

- **FR-061**: **One rule set, one refusal set, refused whole.** Every path that reads or writes the mode — the bindings read, the bindings write, the poll loop's read of the stored record, the panel's reader of the service's answer, and the audit writer's comparison against the recorded baseline — MUST judge the value by the **same two-name rule**, with no second rule set and no per-surface spelling. A present value outside the two names MUST be **refused whole** under FR-024: never coerced, cast, defaulted in place, dropped from the record, or persisted in a form that would later read as the default; the stored bindings file is quarantined with a logged reason naming the field and the two accepted names, the poll loop scans nothing until the operator repairs it, and no submitted value is echoed back. Every other problem in the same submission is reported with its own remediation in the same answer, and **no part of the submission is applied**.
- **FR-062**: **`null` reads as absent, and never as "unbounded".** A stored JSON `null`, and a submission whose `historyScope` is JSON `null`, both mean **cleared to the documented default** (FR-057). Neither means *no lower bound*, neither is a way to request unbounded replay (FR-060), and neither may be rendered anywhere as an empty control that reads as a third choice. This is 004 FR-017's treatment of a cleared prompt, stated here because `null` is the one value a reader could mistake for the absent window a scan used to open.
- **FR-063**: **The panel reads it fail-closed and never pre-empts the service.** A bindings answer carrying an unusable `historyScope` MUST render that binding's mode as **unreadable** and say so — not as the default, not as an empty control — which is the posture the panel's reader already takes for an unusable `allowedUsers`, and one refused member is never partially applied. The panel MUST NOT pre-emptively accept input the service will refuse and MUST NOT pre-emptively reject input the service would accept (005 FR-052's rule, applied here).

##### I.3 The window rule — and the containment boundary it is computed inside

*FR-064 leads this group because it is the boundary the rest of it is computed inside: the lower bound is derived from state the poll loop already reads, not fetched from a new surface. It is numbered here rather than in a scope group of its own so the new range stays contiguous.*

- **FR-064**: **No new surface, no new capability, no new route.** This section MUST NOT add any host capability, API, permission, manifest setting, service route, or host call, and MUST NOT reach for an undocumented or private interface (003 NFR-110). The window's lower bound is computed inside the poll loop from state the loop already reads, and the mode rides the bindings surface that already exists (FR-056).
- **FR-065**: **Every scan window has a lower bound.** A scan MUST NOT open with the absence of a window, under any mode and in any state of the store. The window's start MUST be a computable stamp, and where more than one applies exactly one decides it, in this order: **a recovery replay in force** opens at the binding's retained baseline (FR-073, FR-066, FR-067), because re-covering lost work is the obligation and that baseline is the earliest lower bound this binding has ever scanned from; **a catch-up armed for the binding** opens at the armed bound (FR-084), which is the more recent explicit request; **the binding's last completed scan's recorded stamp minus the configured overlap** (006 FR-059(a)) is the ordinary incremental window; and a binding with no completed scan, nothing armed and no replay opens at the baseline FR-066 or FR-067 fixes. The replay comes first because the other two are instructions about the *next* scan, and a narrower window here would drop work the recovery exists to restore. **A stamp that is present but the clock cannot read is not the same fact as no stamp.** It MUST NOT be coerced, defaulted or read as absent: at its own place in that order it **refuses**, recording the reason against that binding under FR-024, which is why a recorded scan stamp the clock cannot read stops the scan rather than falling back to the baseline below it (FR-072's direction, one source over). **The window with no lower bound is retired as a window source.** Three conditions reached it before v1.13.0 and each is specified below: a binding's first scan (FR-066, FR-067), the recovery replay (FR-073), and a baseline or recorded stamp the clock cannot read (FR-072).
- **FR-066**: **`new-only` baselines at the binding's own creation boundary.** For a binding with no completed scan in the `new-only` mode, the window's start is **the binding's creation stamp minus the configured overlap** — the same widening every later scan applies, applied once to the creation boundary instead of to a scan. **The boundary is the creation stamp, and the consequence is that an item which existed before the binding but was touched after it falls inside the first window and fires** — an item's age is never the test; the comparison is on the event's own timestamp (FR-051). The first scan obeys exactly the rule every later scan obeys, with the creation stamp standing in for a completed-scan stamp until one exists. **The baseline MUST be stable, and MUST only ever widen.** It is derived once, before the binding's first scan, and thereafter every **completing** scan that opens a wider window moves it **earlier and never later**: what it holds is the earliest lower bound this binding has ever scanned from. The two properties are different axes and neither replaces the other. *Stability is about the clock* — a scan that does not complete, and a credential that stays broken across any number of attempts, reuses the bound it already holds rather than recomputing it from a later reading, so the binding returns the same window it promised (AC-036). *Widening is about coverage* — a catch-up armed at `now − 7 days` for a binding younger than seven days opens **earlier** than that binding's own creation boundary does, so an un-widened baseline would be narrower than ground the binding had already swept and the replay FR-073 requires would drop it silently. So a completing scan records the **earlier** of the retained baseline and the window it opened, and a scan that does not complete leaves the baseline where it was.
- **FR-067**: **`recent-history` baselines one fixed look-back before the creation boundary, once.** For a binding with no completed scan in the `recent-history` mode, the window's start is **the binding's creation stamp minus the fixed look-back length of 604,800,000 ms (7 days)** — widened by nothing further **at derivation**, because the operator asked for a period rather than for a boundary — the baseline itself still widens afterwards whenever a later scan opens an earlier window, exactly as FR-066 states. The contents of that window are the only thing this mode adds; it is one-shot because the binding's checkpoint is an ordinary checkpoint from the first completed scan onwards (FR-080).
- **FR-068**: **The two modes differ only in the first window's start.** Once a binding has completed a scan, its mode is not consulted at all. Both modes then share every other rule exactly as they do today: the overlap widening, the client-side `created_at` comparison and its page-walk stop rule (FR-051), the `since` the list feeds carry, the actor attribution rule (FR-044, FR-049 – FR-052), the allow-list (FR-047), the trigger set (FR-015), deduplication (FR-019), the claim-and-lease cycle, and every audit row a run writes. **A mode MUST NOT appear in any comparison about an individual observation.**
- **FR-069**: **An observation with no readable freshness stamp is never in-window.** With a window in force, an observation that cannot report its own timestamp produces **no event, no run, and no work**, and substitutes nothing — not a listing's other fields, not a previously recorded stamp, not another source. This is the existing fail-closed rule and it holds in both modes unchanged.
- **FR-070**: **The mode is not a trigger and does not re-enable anything.** A binding with no enabled trigger still produces nothing in either mode; a disabled binding is not polled in either mode; and the mode never changes a binding's `state`, its trigger set, or its dispatch target. Changing it MUST NOT start, stop, or resume polling on its own beyond the effect its window rule has on the next scan.
- **FR-071**: **The mode never widens who may trigger.** The actor allow-list (FR-047), the bot exclusion (FR-045), and the mandatory readable-actor rule (FR-045, FR-052) apply identically in both modes. A historical trigger is admitted exactly when a current one would be, and no substitute actor is available in one mode and not the other. The look-back mode widens **when** the product looks, never **who** may make it look.
- **FR-072**: **An unresolvable baseline fails closed.** When the baseline a mode calls for cannot be read from the stored record, the scan MUST open **no window and create no events for that binding**, recording the reason against that binding under FR-024 — the same direction FR-069 takes for an unreadable observation. It MUST NOT fall open and treat every observation as in-window.

##### I.4 Forced replay and recovery

- **FR-073**: **Recovery replays regardless of the mode.** When the service clears bindings' checkpoints to recover from a lost or quarantined event queue, the next scan of every affected binding MUST re-detect and re-offer that binding's in-window work **whatever its history scope is**. A recovery replay is not a first scan and MUST NOT be governed by the first-scan rule: the mode governs ordinary scanning and never governs recovery. **The replay's window start is the retained baseline** (FR-065) — the earliest lower bound that binding has ever scanned from — so a replay re-covers at least everything any earlier scan of that binding covered, whichever mode was in force when each of those scans ran. **That baseline must be readable for this to hold**, and one the clock cannot read does not become a window by being wanted: the replay then refuses under FR-072 unless another source on FR-065's list is itself computable, in which case that source is used. An unreadable baseline therefore never widens an ordinary incremental window either — that window is computed from a different fact, so a scan that has one is unaffected. The replay is bounded by the same rules as any other scan (FR-065, FR-079, FR-083) and, where a catch-up is also armed for that binding, **takes precedence over it** (FR-084): the replay's obligation is lost work, while the armed bound is a request about the scan after this one — and a catch-up whose ground this replay did not reach stays armed for that scan (FR-076).
- **FR-074**: **"No completed scan" and "cleared for recovery" are distinguishable, and the recovery path is the only writer of the difference.** The durable per-binding scan state MUST be able to express both, and the two MUST NOT be the same value or be inferred from one another by any reader. The forced-replay record MUST be written by the recovery path alone and MUST NOT be written by a first scan. FR-018's atomic-write rule covers it.
- **FR-075**: **A recovery replay is duplicate-free and audited like any other replay.** It MUST deduplicate through the deterministic delivery key (FR-019), every replayed observation MUST be audited as a duplicate or as previously processed (FR-023), and a replay after a loss MUST NOT produce a second session for a trigger that was already dispatched.
- **FR-076**: **A forced replay survives an incomplete scan.** A scan that starts with a forced replay in force and does not complete MUST leave the forced replay in force, and the next scan MUST replay again. A transient failure — an unusable credential, a store error, a provider outage — MUST NOT consume the recovery. This composes with the retained-checkpoint rule rather than restating it: that rule says an incomplete scan does not advance the checkpoint, and this one says the same of the record beside it.
- **FR-077**: **A recreated binding starts over.** A binding removed and created again for the same repository and account is a new record with a new baseline, and the mode applies to it afresh (FR-066, FR-067). **This is what answers a re-binding after data loss**: recreating a binding with the default mode produces no session for anything that happened before the recreation.
- **FR-078**: **A recovery replay is visible while it is in force.** While one is in force the per-binding health surface MUST say so (FR-036, FR-092), so a burst of older events arriving together is explained from the operator's own surface. The product MUST NOT present the replay as the mode's look-back sweep, and MUST NOT present a forced replay as an operator choice.

##### I.5 The bounded look-back sweep

- **FR-079**: **The sweep is bounded by its window's contents, and nothing is dropped to bound it further.** The set of triggers one sweep may offer is exactly the triggers inside its window. **No count cap, truncation, sampling, or priority order may apply within that set**, and no sweep may end early having offered only part of it. A sweep that stopped part-way would leave a checkpoint recording a completed scan while in-window triggers were never offered, and nothing could name which ones.
- **FR-080**: **The sweep is one-shot by construction.** After the binding's first completed scan its checkpoint is an ordinary checkpoint and every later scan is the ordinary incremental window. A binding in the `recent-history` mode MUST NOT sweep again on its own — not on restart, not after a long outage, not because the window widened, and not because a recovery replay followed one. The product MUST state to the operator that the look-back has already happened and will not repeat without an explicit operator action (FR-090).
- **FR-081**: **A sweep enqueues; it does not start sessions.** Every event a sweep detects enters the queue through the ordinary enqueue path, and dispatch remains **one session at a time** under the existing claim-and-lease cycle. A sweep MUST NOT start sessions directly, MUST NOT bypass the lease, and MUST NOT hold sessions outside that cycle. The size of the pending set is visible through the existing per-binding pending count.
- **FR-082**: **A sweep that runs again changes nothing.** A repeated sweep of the same window — because the service restarted, because the cycle overlapped, because the same observations were read twice, or because the operator retriggered it — MUST produce no second event for the same trigger, and no second run and no second session for it.
- **FR-083**: **The page bound and its exhaustion reason apply unchanged.** A window holding more items than one scan's page bound MUST stop the walk by FR-051's existing rule and record the exhaustion reason, producing no event for an item the walk never reached rather than a partial answer about it. A sweep MUST NOT raise the page bound, page further, or spend unbounded request budget to make its window complete.
- **FR-084**: **Editing a binding into the `recent-history` mode opens the bounded catch-up through FR-023.** If an operator changes an existing binding's mode to `recent-history`, the next scan of **that binding alone** MUST open a window whose lower bound is the fixed look-back length measured from that moment, through **FR-023's one rescan mechanism** — one mechanism with one rule set, not a second replay surface with its own. **This caller is the one the mechanism is required to support**; FR-023's general operator-chosen-timestamp surface is out of scope and is not built by it. No other binding's window is touched; the opened window is bounded exactly as a creation-time sweep's is (FR-060, FR-079); and deduplication and page-boundedness are FR-019's and FR-083's, unchanged. **The armed bound is served, not spent** *(clause added at v1.13.2, 2026-10-05)*. The mechanism's lower bound MUST be cleared by the first scan whose window actually reaches back that length, and MUST NOT be cleared by a scan that did not: neither a scan that failed to complete (FR-076) nor a recovery replay that took precedence over it (FR-073) leaves it in force for the next scan. Clearing it on completion alone would discard the operator's request with nothing recording that it was ever asked for — FR-076's durability rule, reached by a precedence decision instead of by a failure. **An arming the clock cannot read is neither used nor cleared, and that silence is chosen.** This is a different case from FR-061's, which refuses a bad value **on write**: an unreadable value **found in the stored record** is a text the parser accepts as a string, so the document is not even quarantined and every other member of that binding's slot survives. Such an arming MUST NOT become a window — a stamp the clock cannot read is not a bound anybody chose, and arming from it would fire work no operator asked for — and it MUST NOT be cleared either, because a scan that did not read the request cannot be the scan that served it. So it **stands armed indefinitely**, which is the fail-closed direction FR-072 takes for the baseline and the reason it is the same class of hazard. **It is deliberately unreported**: no projection carries the member and no log line names it, so the binding's health row shows its ordinary window and an operator sees look-back mode over it — indistinguishable from a look-back already served. That silence is recorded rather than overlooked: surfacing it means adding a member to the health row, which is a wire contract the panel reads (FR-036, FR-092) and therefore **a product decision that has not been taken**. Only FR-084's own caller writes the member, as the fixed look-back length measured from a moment, so the state is reachable only from a hand-edited or corrupted store. An edit that affected only bindings with no completed scan would do nothing at all on any binding that has ever scanned, so the effect of this edit is specified rather than left to be discovered as a control that appears to work.
- **FR-085**: **Editing a binding into the `new-only` mode replays nothing.** That edit MUST NOT clear a checkpoint, MUST NOT open a window, MUST NOT cancel or alter work already queued, and MUST NOT undo anything already dispatched. Work already queued keeps the snapshot it was detected with and dispatches under it. **Editing to stop looking back MUST NOT itself cause a look-back.**

##### I.6 Audit and auditability

- **FR-086**: **One change row per change, and only when the value changed.** Every change to a binding's mode — arriving through the panel's write, arriving inside a whole-file write alongside other members, or observed in the stored document without a write — MUST write **exactly one** audit row naming the binding, the decision (`set`, `changed`, or `cleared`), the new mode, the previous mode, and who caused the change (`operator` for a write through the panel, `service` otherwise). A submission that resends the mode already in force MUST write nothing. The row is a **configuration row in the reserved `binding.` prefix**, carries **no other detail** — the mode's values are two fixed names, so there is no free text, no length, no fingerprint, and nothing credential-shaped — and introduces no new event type outside that prefix.
- **FR-087**: **Why an observation was not offered is answerable from durable state, and no per-observation row is added.** For any event and at any age, the product MUST make it answerable why an item inside a watched repository never produced work. It does so with **two** facts: the per-binding health surface carries the **window start currently in force** and the mode in force as derived state (FR-036, FR-092), and the trail carries the mode's change history (FR-086). Together they answer *this event is older than the window this binding has watched since the date the mode changed*. **A per-observation or per-detection audit row for non-matching observations is not added by this section**, and 002's reserved-but-unwritten `poll.observation` and `poll.checkpoint` vocabulary remains reserved for a future feature that can afford that volume.
- **FR-088**: **No dispatch-lifecycle row changes, and a recovery replay adds no audit vocabulary of its own.** No row of the dispatch lifecycle gains, loses, or renames a member because of this section; no trigger, allow-list rule, actor rule, or page-walk rule changes; and the row the recovery path already writes is the record of why a replay happened (FR-078), with no second row describing it and no row that could be mistaken for an operator having chosen a sweep.

##### I.7 The operator's surface

- **FR-089**: **One control, in the binding editor, on both create and edit.** The binding editor MUST offer exactly one control for the mode, as an addition to the field list 005 FR-053 enumerates, presenting the binding's current value and offering exactly the two names. On the **create** path it MUST carry the documented default when the operator does not choose it, so a choice the creator may indicate is met by a control that also works when they indicate nothing (FR-013). On the **edit** path it MUST offer both directions: choosing `recent-history` opens the catch-up FR-084 specifies, and choosing `new-only` does the nothing FR-085 specifies.
- **FR-090**: **The guidance travels with the field.** The control MUST convey, in the operator's own terms and without the operator opening anything else: what each of the two options does; that the default watches from now on; that the look-back option looks back over a fixed **seven-day** period **once**, at creation, and does not repeat on its own; that the window is bounded and **there is no "all history" option**; and that choosing the look-back option on an existing binding will offer work for every matching item inside that window at once, which may be many sessions.
- **FR-091**: **One rendering of the mode, and a row summary may name it.** The mode MUST be rendered **exactly once in the entire panel** — as the editor's own control, which is 005 FR-051's rule applied to this value. It MUST NOT also appear on a dispatch row, in a Diagnostics view, on Status, or in a second editor. A row summary **MAY** show the mode's short label, on 005 FR-091's reasoning that a count is not a second rendering of a value; it MUST NOT show anything else derived from the mode, and MUST NOT be the only place the operator can see or change it.
- **FR-092**: **The window in force is shown as derived state.** The window start currently in force, the mode in force, and whether a recovery replay is in force MUST be visible on the binding's own surface, labelled as the scan window the service computed rather than as something the operator set (FR-036). It is the same fact the existing per-binding scan line already carries a stamp for, extended with the lower bound so both ends of the window can be read together.
- **FR-093**: **Honest absence and honest unreadability.** A binding storing no mode renders the **documented default** as the control's value, because that is what the binding will do. A binding whose stored mode is **unusable** renders **unreadable** and says so (FR-063), and MUST NOT render the default, an empty control, or a value implying the operator chose something. Because absence means the default (FR-058), a binding storing no mode never renders as "unset" — that is not a state this field has.
- **FR-094**: **Operable by keyboard alone, with an accessible name.** The control MUST be operable and completable by keyboard with visible focus and no trap, MUST expose an accessible name carrying what it decides, and both options MUST be reachable without a pointer (005 FR-016, FR-018).

#### J. The current-project default (added at v1.14.0 — GitHub issue #21, FR-095 – FR-099; recut at v1.15.0 — GitHub issue #39)

The panel already receives two facts it does not use: the host's ready context names the **current project's directory** (`HostReadyContext.directory`), and the picker's `host.listProjects()` answer names **every registered project's directory** (`GuestProject.directory`). This section derives one value from those two — the project the panel should open on — and binds it to the product owner's decisions of 2026-10-06 as they stand after the 2026-10-07 recut (issue #39): the default is computed **at load and never stored**, the binding form's *Dispatch project* field resolves from it **alone**, that field takes it in **add mode only**, and a derived value never claims to be a pick. The premise is verified rather than assumed — pinned `@openchamber/sdk` `1.24.2` `dist/contract.d.ts`, `dist/workspace.d.ts`, and the Host API docs, read 2026-10-06 (`research.md` §R11) — so no new host call, capability, or wire surface is needed to ask the question at all.

**FR numbering in this section**: `FR-095` onward, sequentially, grouped `J.1` resolution · `J.2` persistence and failure · `J.3` the one surface, add mode only · `J.4` what may not be claimed of the value · `J.5` the click that changes nothing. `FR-001` – `FR-094` keep their numbers and their meanings except where FR-013 above says otherwise; nothing in this section renumbers them.

##### J.1 Where the default comes from, and what never preselects

- **FR-095**: **Load-time derivation of the current-project default.** The binding form's **Dispatch project** field resolves from exactly one term — **(1)** the **current-project default**: the registered project whose `directory` equals the host's current directory — and from nothing else. *(Amended at v1.15.0: term (1) of the v1.14.0 order — the stored manual selection in `mecha-turk:project` — is gone with the panel-level picker (issue #39), so there is no stored pick to resolve and the default is the first and only term.)* The binding-context project already in force (the first enabled binding's `config?.projectId`) remains dispatch context rather than a choice: it MUST NOT be preselected into a draft and MUST NOT be displayed (FR-097), so when no default resolves the field opens empty — the behaviour before v1.14.0, kept. The default MUST be computed **from the load/refresh snapshot alone**: the directory carried by the host's ready context when the panel loads, matched against each loaded project's `directory` by **exact string equality** — no path normalization, no case or trailing-slash folding, no prefix match — because both values are the host's own and a guessed normalization would invent a match the host never reported. It is computed when the panel loads and **recomputed when the project list is reloaded**, and at no other moment. **It is load-time only**: the panel MUST NOT recompute it, and MUST NOT change any value or control it displays, in response to a directory change while the panel is open — no directory subscription is registered for this purpose — so switching the host's project never moves a field out from under an operator mid-edit (product-owner decision, 2026-10-06).

##### J.2 Derived, never stored, fail-closed, no new surface

- **FR-096**: **The default is derived, never stored — and it fails closed.** Three clauses, each normative. **(a) Never stored.** The default MUST NOT be written to any storage key — not at mount, not at refresh, not at add-form reset, not on save. Since v1.15.0 there is no pick to store either: `mecha-turk:project` has no writer and no reader (issue #39), so no value anywhere can claim the origin *a human picked this* it never had (constitution IV applied to storage). **(b) Fail closed** (constitution II): a `null` host directory, a directory that matches no registered project, **two or more registered projects sharing the directory** (ambiguous — so no default rather than the first hit), a project list that is not `ready`, or a `listProjects()` failure or error snapshot each produce **no default**, and the field opens empty exactly as it did before v1.14.0. In every such case the project list's status line keeps rendering its honest loading/error/empty note and the select offers no options, **no project is invented**, and the feature introduces no block of its own: it never delays, disables, or invalidates a control, and every refusal path that exists today still refuses with today's reason. **(c) No new surface.** This default adds **no storage key, no wire member, no route, method, or error code, no manifest field, no capability** — the manifest stays `sessions` + `prompt` with `service` implied by `contributes.service` (AGENTS.md invariant 3) — **and no host call**: the directory arrives with the ready snapshot the panel already handles, and the list it is matched against is the one the form already loads.

##### J.3 The one surface — the form's field, add mode only

- **FR-097**: **The binding form's field is the one project control, and it takes the default in add mode only.** **(a)** There is exactly one project control on the Bindings tab — the binding form's **Dispatch project** select (the panel-level **OpenChamber project** picker, its *Copy project id* button, and its provenance line were removed at v1.15.0, issue #39), and it renders its options from the loaded project list alone. **(b)** The **Dispatch project** field MUST preselect **the current-project default when one resolves (FR-095), otherwise nothing** — in **add mode only**, applied where the draft is reset. **The binding-context term of FR-095 is never preselected into a draft**: it is the panel's dispatch context rather than a choice, and today's add form never shows it — so with only a binding context in force the field opens empty, exactly as before v1.14.0, and the constraint the product owner set (the default is the field's only source) holds without being relaxed. The operator MAY change the preselection with an ordinary pick before saving. **(c)** **Edit mode is untouched**: opening an existing binding still loads that binding's saved project and nothing else, and the default MUST never replace it. **(d)** Saving an add-mode draft whose project was never touched writes the value into **that binding's own `projectId`** through the existing whole-file write — an explicit save, not a storage write — and a draft opened while nothing resolves starts empty exactly as it does today.

##### J.4 What may not be claimed of the value

- **FR-098**: **Provenance honesty: the default is never presented as a pick.** *(Amended at v1.15.0: the detail line and its closed set of four provenance strings — and with them *Copy project id* — were removed with the panel-level picker (issue #39), so no surface renders a provenance string for the project selection any more.)* What remains normative: the panel MUST NOT present the current-project default as a pick the operator made (constitution IV; NFR-011's *no surface may state more than the provenance holds*) — it MUST NOT be persisted, labelled as a selection, or attributed to the operator anywhere it renders. It reaches a binding only when the operator saves the add form untouched, which writes that binding's own `projectId` (FR-097(d)) — an explicit save, credited to the save rather than to a pick.

##### J.5 The click that changes nothing

- **FR-099**: **Clicking the already-displayed default stores nothing, and that is accepted.** The SDK select skips `onChange` when a click matches the value already displayed — the constraint the form's select carries from the SDK's verified behaviour — so an operator who clicks the displayed default to keep it gets **no change event**: nothing is stored, nothing errors, and nothing about the panel changes; the default simply re-derives on the next load or refresh. This is intended behaviour, not a gap: **pinning is not required to use the default** (FR-096(a)) — and since v1.15.0 there is no pick key and no pick handler for any click to reach, so storing it is not an option the panel offers at all. No *Pin* control, no synthetic or mount-time storage write, and no change to the select's change semantics may be introduced to make the same value pickable twice.

### Key Entities

- **Account**: GitHub identity used for matching and polling — durable `numericUserId`, display `login`, optional expected-login constraint, credential reference held only by the service, verified-at timestamp, scope check result, connection state.
- **RepositoryBinding**: one repository under one account — GitHub repository id/owner/name, bound account, resolved OpenChamber `projectId`, per-trigger enablement flags, mention token override, worktree option, **optional `allowedUsers` login list (FR-047; key absent when unset)**, **optional `historyScope` — `'new-only' | 'recent-history'`, key absent meaning the documented default `'new-only'` (FR-053, FR-058)**, policy profile, enabled state.
- **History scope**: one optional enum member on a binding — *watch from now on* or *watch from now on, and once look back over recent activity*. It selects a scan window's lower bound and nothing else. Owned by the service, persisted with the binding, validated by one rule set (FR-053 – FR-063).
- **Look-back length**: a fixed, service-declared period — 604,800,000 ms (7 days), inside a declared bound of 3,600,000 ms to 2,592,000,000 ms — that is **not** stored on a binding and **not** an operator-chosen or configurable value. Its only consumers are FR-067's baseline and FR-084's catch-up (FR-059).
- **Scan window in force**: derived state — the lower bound the next scan of a binding will use, and whether a recovery replay is in force for it. Reported for the operator's explanation, never configured by hand (FR-078, FR-092).
- **Current-project default** *(added at v1.14.0; recut at v1.15.0)*: derived panel state — the registered project whose `directory` equals the host's current directory at load. It is the binding form's **Dispatch project** field's only preselect source. Never persisted (the `mecha-turk:project` key has had no writer since v1.15.0), never a configuration source, recomputed only on panel load or project-list reload, and never claimed as a pick anywhere it renders (FR-095, FR-096, FR-098).
- **Checkpoint**: per account + repository + stream cursor — endpoint/filters, last observed id/timestamp, pagination position, validators, overlap window, last poll time, retry/backoff state, next poll time.
- **Delivery (normalized event)**: immutable normalized provider fact — schema version, provider, account id, repository, source type/id/updated_at/url, event kind, **triggering actor (`actorLogin` + `actorAttribution`, FR-043)**, subject (type/number/base ref/head sha), bounded content reference, correlation id, **delivery key**. The actor is a **record member and not part of the delivery key or the event id** (FR-046). **Updated at v1.12.0**: the actor is named by the event for **every** kind (FR-049, FR-050), and `'actorAttribution'` is written as **`'direct'` only** — `'subject-author'` remains a member of the closed union and remains **readable**, because rows the shipped build already wrote carry it, but it has **no producer** and no row written under v1.12.0 may carry it (FR-044).
- **Run**: work unit derived from one or more deliveries — deterministic **run key**, policy decision, lifecycle state, attempts, worktree option used, dispatch result, verification result, source links. A run **coalesces** its deliveries (003 FR-011), so it may carry more than one attributed actor; which of them authorized the dispatch is 003's rule, not this document's.
- **SessionRef**: pointer to the host-owned session — `sessionId`, title, source url, dispatch timestamp, observed agent/model, verification status. OpenChamber remains authoritative; the extension stores only the reference.
- **PolicyProfile**: per-action autonomy/approval configuration — action name, gate on/off, policy version, effective timestamp.
- **AuditEntry**: append-only record — timestamp, correlation id, event type, actor/source, decision/reason, redaction metadata; never contains a token.
- **ServiceHealth**: `serviceStatus()` value plus per-account rate usage, per-repository last poll/checkpoint age, and agent-pin verification status.

### States

- **Account**: `pending_handoff → verifying → active | rejected`, plus `revoked` and `error` transitions out of `active`. Only `active` accounts may poll.
- **RepositoryBinding**: `draft → project_missing → active | blocked | disabled`. `project_missing` is recoverable; `blocked` carries an explicit reason; `disabled` stops polling for that repository.
- **Checkpoint**: `uninitialized | active | backing_off | stale | blocked | disabled`. Advances only after a fully durable window.
- **Delivery**: `discovered → ignored | duplicate | queued → processing → dispatched | dead_lettered`, with `blocked` available before dispatch.
- **Run**: `created → dispatching → verifying_agent → dispatched`, or `waiting_approval`, `blocked` (incl. `blocked:agent-mismatch`, `blocked:project-missing`, `blocked:credential`, `blocked:policy`, and **`blocked:actor-not-allowed`**, added at v1.11.0 for the allow-list gate 003 v1.8.0 owns), `retrying`, `completed`, `dead_lettered`. Transitions out of `blocked` occur only when the cause clears, under the same run key.
- **Service**: `stopped | starting | ready | failed`, plus the panel-only `unsupported_surface`. Crashes map to `failed` with manual retry.

## Setup Prerequisites

Documented and shipped with the feature (FR-038); each prerequisite is also surfaced in the panel's first-run checklist.

1. **Default Agent pin (required for dispatch)**: In OpenChamber, set **Settings → Sessions → Session Defaults → Default Agent** to **the agent your dispatches should run on** — the value is yours to choose, and since v1.10.0 no agent name is prescribed here (the product owner's order: *"Default Agent pin should default to blank, not everyone is going to use project-manager"*). The platform does not let an extension name an agent per call, and the guest-send path checks this setting first, so this is the only deterministic pin (`001/research.md` §b.2 — **historical path**, removed in commit `110c0a2`; the same finding is researched and stamped in 002's own `research.md` §R3 and enforced by FR-029). Set the matching **`expectedAgent`** baseline on **Settings** as well: it is the value FR-029's verification compares against, and with it blank the read-back records the observed agent without comparing it. Side effect to document: new user sessions also default to the pinned agent until changed. The panel cannot read this setting, so the pin is enforced **post-dispatch** by verification against that baseline (FR-029), not pre-flight.
2. **OpenChamber must be running**: Unattended operation means "unattended while the operator's OpenChamber is up". Polling and dispatch stop when OpenChamber stops, when the extension is disabled, or when the service is not running (constitution v1.3.0, Security and Operational Standard 3).
3. **Desktop or web surface**: Guest services spawn on desktop and web only; VS Code and mobile do not spawn services, so those surfaces show the unsupported state (FR-003).
4. **GitHub PAT scopes**: fine-grained PAT preferred, with `Metadata: read`, `Issues: read`, `Pull requests: read` (+ `Contents: read` only if repository metadata is passed to OpenChamber). No write scopes. Organization approval policies for fine-grained PATs must be granted where the organization requires them. The Notifications API is not used (classic-PAT-only limitation, `001/research.md` §a.6 — **historical path**, removed in commit `110c0a2`; the rejection is carried as a requirement in FR-010 above and re-stamped in 002's `research.md` §R6).
5. **Registered project**: each bound repository's project must exist in OpenChamber (command palette → Add project, sidebar **+**, or folder browser). The extension cannot create it.

**~~6. Service capability approval~~ — removed at v1.9.0** (product-owner order, 2026-10-01): the line read *"approve the extension's declared capabilities at install; token handoff additionally requires the in-panel consent step (FR-008)"*. The consent clause went with the dialog, and with it the numbered line: **five prerequisites remain**, exactly the five the panel's first-run checklist renders (005 FR-037). Install-time capability approval itself is unchanged and still enforced — it is the host's own install gate under FR-002, and an unapproved `service` still refuses the first handoff with instruction (AC-002, token-handoff F1); it simply is not a numbered setup step any more.

## Non-Functional Requirements

- **NFR-001 Detection latency**: Under normal rate conditions, p95 from GitHub event timestamp to run creation MUST be ≤ 2 × the poll interval (default ≤ 120 seconds), measured with ≤10 repositories and no rate-limit pressure.
- **NFR-002 Idempotency**: Replaying any repository window 100 times MUST produce zero duplicate deliveries-in-run, duplicate runs, duplicate sessions, or duplicate external side effects. **This MUST hold on every window-opening path**, and the two added at v1.13.0 are the ones where a gap would become duplicate *work* rather than a duplicate log line: the bounded look-back sweep and the forced recovery replay (FR-073, FR-079, FR-082).
- **NFR-003 Rate safety**: Steady-state polling MUST stay within the design point of ~600–1,500 requests/hour per account (≤30% of one account's 5,000/h budget at 10 repositories), MUST respect secondary limits, and MUST never enter a catch-up burst after backoff.
- **NFR-004 Secret containment**: Zero occurrences of any token value in persisted panel state, ledger, logs, audit entries, toasts, error bodies, or committed files, verified by automated scan in tests.
- **NFR-005 Fail-closed safety**: Every failure class listed in FR-024 MUST block rather than proceed, with an explanation naming the exact cause and no secret material.
- **NFR-006 Durability**: After any crash or restart in any state, checkpoints, deliveries, runs, and audit entries recover without silent loss and without duplicate side effects; the audit history home MUST survive extension uninstall.
- **NFR-007 Observability**: One correlation id MUST trace a source observation through checkpoint, routing, policy, dispatch, agent verification, and terminal state, in both the panel and the audit trail.
- **NFR-008 Compatibility**: The OpenChamber SDK version MUST be pinned exactly and re-pinned to the host's own release before execution (spike record: `@openchamber/sdk` `1.24.2`, `001/spike-evidence.md` §1 — **historical path**, removed with the 001 directory in commit `110c0a2`; recover with `git show 110c0a2^:specs/001-agent-event-orchestrator/spike-evidence.md`. The pin itself is live at `package.json` `dependencies` and re-stamped in 002's `research.md` §R7). Host capabilities MUST be adapter-abstracted and capability-checked at runtime; unsupported operations MUST fail safely instead of being reimplemented through private APIs.
- **NFR-009 Surface honesty**: On any surface where a required capability is unavailable, the panel MUST state what is disabled and why; it MUST never display healthy-looking state for non-operating subsystems.
- **NFR-010 Maintainability**: GitHub discovery and the panel↔service transport MUST be adapter boundaries with contract tests; a future webhook adapter MUST be addable without changing routing or policy semantics; strict type checking and linting apply with no suppressions (constitution, Development Quality Gates).
- **NFR-011 Attribution honesty** *(re-cut at v1.12.0 — the premise this requirement enforced was false; superseded wording recorded in changelog.md → `### v1.12.0`)*: **An attribution states a provenance, and no surface may state more than the provenance holds.** Every audit row, run record, source reference, status projection, and rendered surface that names an actor MUST name it **as GitHub named it**: for `'direct'`, the identity the provider recorded as the actor of the act, with no qualification, because there is nothing to qualify. For the one remaining member, `'subject-author'`, the surface MUST say that the row was attributed under the rule in force when it was written — the issue or pull-request author standing in for an actor the **list** feeds could not name — and MUST NOT claim that GitHub fails to record the assigner or the reviewer, because **GitHub does record both**, in `assigner` and `review_requester` (FR-044). No surface may present a proxy as a fact, and no surface may present a **corrected** rule as though it had always been the one in force. Verified by a test that drives all four trigger kinds and asserts the wording of each surface that renders an actor. This is the honesty half of the allow-list: a control that quietly guesses who acted is not a control, an audit trail that records a guess as a fact is worse than no audit row, and — the case v1.12.0 exists for — **a trail that states a falsehood about the provider is the same defect wearing the opposite hat.**
- **NFR-012 History-scope compatibility** *(added at v1.13.0)*: No stored record's meaning changes silently. A binding written before v1.13.0 keeps every existing member, gains nothing it did not have, parses, projects, and renders, and behaves as any other default-mode binding. A bindings file that does not carry `historyScope` is a valid file, not a legacy shape. The two mode names are a persisted vocabulary and MUST NOT be renamed without an explicit migration decision (AGENTS.md invariant 4's posture, applied to a stored value).
- **NFR-013 History-scope determinism** *(added at v1.13.0)*: Given the same stored state and the same observations, a binding's mode MUST select the same window and therefore the same events — no clock read, no randomness, and nothing outside the stored record and the configured overlap — so a replayed cycle detects the same set. A binding in either mode MUST cost, in requests, what the same binding cost before v1.13.0 plus the ordinary reads its window already implies (FR-083).

- [ ] **AC-037** *(FR-067, FR-080, FR-082)*: A binding created in the look-back mode opens a first window whose start is its creation stamp minus exactly **604,800,000 ms**, widened by nothing; the same fixture's in-window triggers all produce events and its out-of-window triggers none; a second scan over the same window produces **zero** further events for the same triggers; a restart, a cycle overlap, and a re-read of the same observations each produce **zero** duplicates; and a later scan days afterwards offers nothing from inside the original window.
- [ ] **AC-038** *(FR-072)*: A binding whose creation stamp cannot be read produces **no event, no run, and no work** for that binding, with a recorded reason — in either mode — and **never** a full replay.
- [ ] **AC-039** *(FR-073, FR-074, FR-075, FR-076, FR-078)*: With one binding in each mode, both holding a completed checkpoint and dispatched work, the recovery path clears them and the next scan re-offers **both** bindings' in-window work; the two bindings' durable scan state is distinguishable from a binding that has never completed a scan, and only the recovery path writes that distinction; the forced replay is still in force for a scan that then fails, and the following scan replays again; a replayed observation writes no second event and starts no second session; the replay is visible on the binding's surface while in force; and **no new audit event type** is introduced.
- [ ] **AC-040** *(FR-079, FR-081, FR-083)*: A sweep's offered set equals its window's matching triggers with nothing dropped from within it, and the sweep never starts a session itself — the whole set enters the queue and dispatch proceeds one at a time under the claim-and-lease cycle, visible in the existing pending count. A window holding more items than the page bound stops the walk by FR-051's rule and writes the exhaustion reason, with no partial answer for an unreached item.
- [ ] **AC-041** *(FR-084, FR-085, FR-089, FR-090, FR-091, FR-093, FR-094)*: Editing to the look-back mode opens a **bounded** catch-up **through FR-023's one rescan mechanism** — exactly one in the service, not two — for that binding alone, touching no other binding and deduplicating like a creation-time sweep; editing to the default mode clears no checkpoint, opens no window, and leaves every queued and dispatched run exactly as it was. The editor's one control carries the default when untouched, offers exactly the two names, states in its own guidance that the default watches from now on, that the look-back is **seven days, once**, and that there is no "all history" option, is keyboard-operable with a visible accessible name, and the mode renders exactly once in the panel with a row summary free to name it and nothing else; a binding storing no mode renders the default and a binding storing an unusable one renders **unreadable**.
- [ ] **AC-042** *(FR-086, FR-087, FR-088, FR-035, FR-036)*: One audit row per mode change — through the panel, inside a whole-file write, and observed in a hand-edited store — naming the binding, the new mode, the previous mode, the decision, and the actor, carrying nothing else; **no row** for a resubmission of the mode in force; no dispatch-lifecycle row gaining, losing, or renaming a member; **no per-observation row** written for a non-matching item on a cycle that matches nothing, and `poll.observation` still unwritten; and the per-binding health surface carrying the window start in force, the mode in force, and the forced-replay flag — which together answer why any given older item was never offered.
- [ ] **AC-043** *(FR-064, FR-070, FR-071, FR-042)*: No new route, capability, permission, manifest setting, or host call appears, and `capabilities[]`, `contributes.service`, and the panel id are unchanged; no trigger, allow-list rule, actor rule, or page-walk rule changes; a bot-authored or unattributable historical trigger produces nothing in `recent-history` exactly as in the other mode; a disabled binding is not polled in either mode and the mode never changes `state`; and `quickstart.md` and `README.md` state what the history scope is and is not, including that a recovery replay re-offers work regardless of the setting.

## Configuration Model

- **Accounts**: service-held credentials keyed by numeric user id, verified logins, expected-login constraints, scope check results.
- **Repository bindings**: account, project id, per-trigger enablement, mention-token override, worktree option, **the actor allow-list `allowedUsers` — absent by default, which means any human may trigger and is reported as such rather than as protection (FR-047, 005 v1.11.0)**, **the history scope `historyScope` — absent by default, which means `'new-only'`: this binding watches the repository from its own creation boundary (FR-053, FR-058)**, policy profile. **One repository per binding, permanently** (FR-048).
- **Policy**: autonomous default plus per-action approval toggles (start work now; future write gates documented only).
- **Polling**: interval (default 60,000 ms), overlap window (default 10 minutes), `per_page` (≤30), retry/backoff bounds. **The look-back length is deliberately absent from this list.** It is declared once, with a bound, like the fields above — but it is **not** a configuration member, not in the schema projection, and not on the Settings tab (FR-059), because the operator does not choose it and a value the operator cannot change does not belong on the surface that exists for changing values. 006 FR-010's and 006 FR-084's documented count of **twelve** fields is **unchanged** by v1.13.0; that is a decision, not an omission.
- **Retention**: audit and payload retention defaults, configurable within documented bounds.
- **Health**: log level, correlation-id exposure, rate-usage reporting.

All of it is service-owned and, since feature 006, operator-editable through `config.json` on the Settings tab. Two surfaces carry **none** of it, and the cleanup review of 2026-09-28 removed the duplicates that pretended otherwise: the manifest carries **no integration card at all** since 2026-09-30 (FR-011 as re-cut at v1.8.0; the card that did exist declared no settings from 002 FR-041) — the one value that once lived there, the agent-verification baseline, now belongs to this configuration as `expectedAgent` (006 FR-100) and is read through `GET /v1/config` (FR-029) — and there is no environment-file configuration of any kind: no `.env`, no `MECHA_TURK_*` variable, and the service's only environment inputs are the host-provided bootstrap pair (006 FR-090, FR-091).

The implementation MUST avoid speculative per-provider or per-agent knobs until a supported capability requires them.

## Out of Scope

The following are explicitly **not** part of this feature:

- Discord or any non-GitHub provider.
- Export/restore of configuration or audit data (post-MVP).
- Label triggers, and any trigger outside the FR-015 set.
- Webhook ingress, webhook secrets, delivery acknowledgements, webhook replay (future adapter only).
- Automatic cleanup of sessions, worktrees, or projects (manual cleanup only).
- Docker packaging (may wrap individual pieces later per constitution Principle V; packaging is not the architecture).
- Hosted/multi-tenant operation, billing, or SaaS authentication.
- Any GitHub write by the extension or service — comments, reviews, reactions, acks, merges, closes, labels.
- Merge, deploy, repository administration, or permission changes under any policy.
- Project creation or registration from the extension.
- Per-call agent, model, or variant selection (platform-stripped; not an attemptable feature).
- Direct panel-side `fetch()` to GitHub (undocumented, unsupported).
- GitHub Notifications API as a discovery source.
- **Allowing a bot to trigger** (v1.11.0). There is no field, sentinel, escape hatch, or policy that admits one: bots are filtered at detection for every trigger kind (FR-045) and no bot event exists to be admitted.
- **Pluralizing a binding's `repository`, or adding a wildcard repository form** (v1.11.0). Forbidden and load-bearing, not merely unbuilt — see FR-048. A binding's purpose is the edge `repo → project`.
- **A shared / reusable allow-list object** across bindings (v1.11.0). The list is a field on one binding; N bindings repeat it. A shared list would need its own identity, lifecycle, validation, and audit story, and buys an operator typing the same two logins twice.
- **Any second actor gate, or any gate at detection time** (v1.11.0). 003 v1.8.0's authorization-time gate is the single enforcement point; a detection-time filter would be cheaper and would leave no audit row, which constitution IV requires.
- **The per-binding `PATCH /v1/bindings/:bindingId` route** — recorded MVP-DEBT above and explicitly not reopened by v1.11.0; `allowedUsers` rides the existing whole-file grant.
- **Any migration, back-compat shim, or fallback for a pre-`allowedUsers` `bindings.json`** (v1.11.0). The product owner ruled it directly: *"there are no migrations needed as we haven't released yet. keep it simple as I can delete my one local install and start over easily."* A stored binding without the key is the **absent** state, which is already specified — there is nothing to convert, and a stored binding whose key is an empty array is **refused**, not reinterpreted.
- **A repository-wide or timeline read to obtain the actor** (v1.12.0). `GET /repos/{owner}/{repo}/issues/events` and `GET /repos/{owner}/{repo}/issues/{number}/timeline` MUST NOT be called for attribution. Named here as forbidden rather than merely unbuilt: unlike the `repository` plural above, this is a *rejected design* with a stated reason — it costs requests on cycles where nothing matched and, with no server-side window on any of the three endpoints, it would need its own pagination-truncation concept on top of the one the scan already has (FR-049, FR-051).
- **Any producer for `'subject-author'`** (v1.12.0). The union member stays **readable** for rows the shipped build already wrote, and the closed union is not narrowed to one value, because a stored file that still contains it must not become unreadable. But no requirement, path, or code may write it, and no fallback path may reach for it when the actor cannot be read — the fallback for an unreadable actor is **no event** (FR-052). Collapsing the union to `'direct'` alone is the tempting cleanup and is exactly what is not being done here; it is recorded as rejected so a later reader does not "tidy" it.
- **A durable per-repository baseline that outlives its binding** (v1.13.0). The creation-time choice is what serves the re-binding and data-loss case: the operator removes the binding and creates it again, and the mode applies afresh (FR-077). A baseline outliving the binding would need its own lifecycle, its own invalidation rules, and its own answer to "what happens when the operator meant something different by it", for a case the owner judged the cheaper path adequate for.
- **An operator-chosen look-back length, and any unbounded "all history" mode** (v1.13.0). The length is a declared constant the operator does not choose (FR-059), and no stored state may request an unbounded window (FR-060). Both are recorded as rejected designs rather than merely unbuilt: the alternative shapes — a stored duration an operator sets, and a third "all history" mode — are the two ways this field could have put the bound at risk.
- **The look-back as a configuration field or a Settings row** (v1.13.0). It is not configuration, because the operator cannot change it (FR-059). This is why 006 FR-010's and 006 FR-084's documented count of **twelve** fields does not move, and the omission is a decision on the record rather than an oversight.
- **A second replay surface** (v1.13.0). The history-mode catch-up **reuses FR-023's** one rescan mechanism rather than introducing one of its own (FR-084). Two replay mechanisms with different rules is how a rescan silently changes meaning, and one mechanism with one rule set is FR-023's guarantee now. *Chosen over building a general rescan surface alongside it*: FR-023's original promise of an operator-chosen-timestamp rescan is the debt recorded immediately below, and building a second mechanism for the mode change would have left that promise and a new one side by side with no rule relating them.
- **The general operator-chosen-timestamp rescan surface — a known gap, promised by v1.0.0 and never built** (recorded v1.13.0, 2026-10-05). FR-023 as written between v1.0.0 and v1.13.0 required *"a controlled operator rescan/replay from a chosen timestamp"* to be supported. **No such surface exists**: `service/routes/` carries no rescan or replay operation, and never has. **This is a known gap, not an oversight, and it is the product owner's decision of 2026-10-05 to keep it that way for now**: v1.13.0 narrowed FR-023 to the one caller this document specifies — the history-mode catch-up (FR-084) — and declined to build the general surface alongside it. What is still owed and what is not: FR-023's **other** clauses (restart survival, overlap resumption, the duplicate-or-previously-processed audit, deduplication, source identity) are in force and implemented; only the arbitrary-timestamp surface is unbuilt. Anyone reading this line in six months should know three things — the promise was real, it was never implemented, and building it later is additive rather than corrective, so it needs no migration and no data-model change. **No requirement, plan, task, or acceptance criterion in this document may be read as promising it.**
- **A count cap, truncation, or sampling on the look-back sweep** (v1.13.0). Named as forbidden rather than merely unbuilt (FR-079): a sweep that stopped part-way would leave a checkpoint recording a completed scan while in-window triggers were never offered, and nothing could name which ones. A visible backlog is the preferred failure to a silent partial coverage.
- **A per-observation or per-detection audit row for non-matching items** (v1.13.0). The volume is unbounded — a cycle matching nothing writes one row per open item, every cycle — and 002's reserved `poll.observation` and `poll.checkpoint` names stay reserved and unwritten for a future feature that can afford it (FR-087).
- **Any history scope other than per binding** — per repository, per account, or a global default (v1.13.0). One repository per binding is FR-048's standing rule; the mode selects a window, and there is nothing to compose, so a second tier would be a knob with no composition story behind it. The three-tier structure 004 built for the starting prompt is deliberately **not** extended to this field.
- **A history view, a backfill report, or a "what would this have caught" preview** (v1.13.0). The product's answer to "what did I miss" is the mode, the window in force, and the operator's choice at creation — not a simulator.
- **Live tracking of the host's current project, and any directory subscription for it** (v1.14.0). The default is a load/refresh value (FR-095): a value that moves while the operator is editing is worse than one that is briefly stale, and the product owner chose load-time only. The API that would make it live (`onDirectory`, which replays to late subscribers) exists and is deliberately not registered.
- **Storing the derived default, or adding a control to pin it** (v1.14.0; recut at v1.15.0). The default is written to no storage key (FR-096(a)), and since v1.15.0 the `mecha-turk:project` key the pick used to live in is gone with the panel-level picker (issue #39), so there is nothing left to store it in; a *Pin* button would exist to solve a problem the default does not create — clicking the displayed value stores nothing (FR-099).
- Phase 4 plan, data model, contracts, task breakdown, or application implementation.

## Assumptions

- **Worktree default**: per-repository worktree option defaults to `generated` (isolates autonomous work from the operator's working tree); `none` and `new:<branch-name>` are selectable. Both `none` and `generated` were exercised live in the spike; `new:` shares the same host-owned path.
- **Branch-name placeholder**: `new:<branch-name>` supports the single literal placeholder `{number}`, substituted with the source issue/PR number; no other templating exists.
- **Untrusted-context bounds**: ≤4,000 characters per source item and ≤12,000 characters per dispatch, with explicit truncation markers — chosen to stay far below host/service body limits and to keep prompts focused; tunable in planning without a spec change only within ±50%.
- **Retention defaults**: audit entries 180 days or 50,000 entries (whichever is reached first); raw/redacted payload excerpts 30 days; minimal audit references (ids, links, decisions) retained until the operator deletes the account/repository binding. Export/restore remains out of scope (see Gate Questions).
- **Mention token default**: `@<login>` of the bound account, case-insensitive; GitHub logins are case-insensitive, so matching must be too.
- **Agent verification mechanics**: reading `onSession().agent` requires the surface to be attached to the dispatched session, so verification opens the created session (a documented UI context switch). The pinned SDK has no silent alternative; planning MUST verify the exact mechanism against the pinned `dist/*.d.ts` and MUST NOT invent an undocumented one.
- **Service-owned storage durability**: service data written outside `host.storage` is expected to outlive extension uninstall because the host's documented uninstall action kills the service process and wipes extension storage, not third-party files; this MUST be verified in planning and documented before the claim appears in user-facing copy.
- **SDK pin**: `@openchamber/sdk` pinned exactly (spike: `1.24.2`), re-pinned to the host's release before execution if the host is newer (`001/spike-evidence.md` §1 — **historical path**, removed in commit `110c0a2`; live pin in `package.json`, re-stamped in 002 `research.md` §R7).
- **Scale**: fewer than 10 repositories, a handful of accounts, one local OpenChamber installation, one logical service instance; multi-instance leasing is deferred.
- **Provider**: GitHub.com REST API; GitHub Enterprise compatibility requires a later review.
- **Connectivity**: outbound DNS/TLS to GitHub only; no inbound Internet connectivity; OpenChamber's own endpoint is loopback.
- **Look-back length** (v1.13.0): **7 days (604,800,000 ms)**, declared with a bound of **3,600,000 ms – 2,592,000,000 ms**. Chosen to cover a staged backlog assigned in the days before binding without admitting "everything from the beginning"; the bound exists so the constant cannot be edited into unbounded behaviour without the bound moving, which is the mechanism that keeps FR-060 true over time. The lower bound is not derived from any other setting here — the configured overlap's own range is tuned for re-covering a missed cycle, a different job by orders of magnitude — and the value is the product's to choose, not the operator's (FR-059).
- **History-scope baseline** (v1.13.0): a binding's creation stamp is the baseline for a binding with no completed scan. The record's creation stamp is kept stable across refreshes, which is what makes it usable as a durable baseline; a stored stamp the clock cannot read fails closed rather than substituting a clock reading (FR-072).

- Q: **Where is the actor read from?** → A: **The item's own event list**, `GET /repos/{owner}/{repo}/issues/{issue_number}/events`, and **only** for an item the list feeds have already flagged as an assignment or review candidate. Zero requests when nothing matched; one per matched candidate per cycle; charged to the same per-account budget as the scan. **Not** the repository-wide events feed and **not** the timeline: both would cost requests on every cycle regardless of activity and — since neither has a server-side window — would need a second pagination-truncation concept on top of the one the scan already has. → FR-049, `## Out of Scope`
- Q: **Which event answers which candidate, and may a fallback answer instead?** → A: **One closed rule per kind and no fallback.** An assignment candidate is answered by an in-window `assigned` event whose **`assignee`** is the bound account, and the actor is that event's **`assigner`**. A review candidate is answered by an in-window `review_requested` event whose **`requested_reviewer`** is the bound account, and the actor is its **`review_requester`**. An event naming a different subject is a **different act** and is not used, however recent. The asymmetry is deliberate: FR-015 makes the trigger about the identity assigned **to** / requested **for**, so the *subject* field is what must match the bound account, and the actor comes off the same row's other field. → FR-050
- Q: **How is the scan window applied, when the endpoint has no window?** → A: **Client-side, on `created_at`.** The per-item events endpoint accepts only `per_page` and `page`; it has **no `since`**, and neither does the repository-wide events feed nor the timeline (timeline adds only `exclude`). The requirement therefore forbids sending a `since` anywhere, and compares `created_at` against `lastScanAt − overlapMs` itself. Selection is by maximum `created_at`, never by position; the page walk stops only on a page *entirely* older than the window start, so a wrong assumption about ordering spends budget rather than visibility; and exhausting the bound produces no event plus a recorded reason. → FR-051
- Q: **What if the event does not name the actor?** → A: **No event this cycle**, with **nothing** substituted — not the row's `actor`, not the issue author, not the `assignee`, not a previously recorded actor. The scan window overlaps, so the candidate is re-detected next cycle and the event is created exactly once if the actor has become readable. Refusing costs at most one cycle of latency; guessing would cost a permanently wrong attribution. → FR-052, FR-045 *(re-cut)*
- Q: **Why keep `'subject-author'` at all, if nothing writes it?** → A: **Because rows the shipped build already wrote carry it**, and a vocabulary a stored `events.json` still contains cannot be deleted without invalidating that file — which would refuse real stored rows and, at the panel, hide an entire dispatch. So it stays in the closed union, stays **readable**, and is rendered with its basis stated; and no row written under v1.12.0 may carry it. Collapsing the union to one value is the tidy-looking alternative and is **rejected**, recorded in `## Out of Scope` so a later reader does not "clean it up". → FR-044, `## Out of Scope`
- Q: **What is not known?** → A: **Three things, all stated rather than assumed.** Bot and app actors on `assigner` / `review_requester`; bulk assignment inside one window; and a `null` `assigner` / `review_requester` — none observed on this repository, whose data has only ever had one human actor. Each is handled by **refusing** rather than guessing, and the `null` case is specified to fail closed *even though* the same row's `actor` member would usually have been readable, because that substitution is precisely the one that would make the correction cosmetic. → FR-052, changelog.md → `### v1.12.0`

### Session 2026-10-05 — GitHub issue #22, the binding history scope

Six questions the issue left open, answered by the product owner on 2026-10-05. Each answer is now encoded in a requirement; the question, the alternatives considered, and the requirement-level reasoning are in [changelog.md](changelog.md) → `### v1.13.0`.

- **Where the watch starts when the operator does not choose** → **Future events only.** `'new-only'` is the documented default and what a binding created without a choice, and a binding storing no member, scans with. This **changes** the rule v1.0.0 set: a binding with no completed scan used to replay all open history, so an issue assigned before the binding existed was detected. → FR-053, FR-058, FR-065, FR-066
- **Is "all history" reachable?** → **No, and it is unreachable by shape rather than by rule.** The mode is a two-name enum, the look-back length is a declared constant and is not stored on a binding, so no combination of stored members can ask for an unbounded window. → FR-059, FR-060, FR-065
- **How far back does the look-back reach, and may the operator choose?** → **One fixed window: 7 days (604,800,000 ms), bounded 3,600,000 ms – 2,592,000,000 ms.** The operator does not choose the number, so it is not a configuration field, does not appear in the schema projection, and does not render on Settings. → FR-059, FR-067
- **What exactly does "only new items" exclude?** → **Nothing about pre-existing items; the boundary is creation, not the item's age.** An item that existed before the binding but was touched after it **does** fire, because the comparison is on the event's own timestamp. → FR-051, FR-066
- **May the mode be changed on an existing binding?** → **Yes, in both directions.** Changing it to the look-back mode opens a **bounded** catch-up **through FR-023's one rescan mechanism**, so there is one mechanism and not two. **Only the mode change is built**: the general operator-picked-timestamp surface FR-023 used to promise does not exist and is recorded as debt in `## Out of Scope`; changing it to the default replays nothing, cancels nothing, and undoes nothing. → FR-023, FR-084, FR-085, FR-089
- **How does a binding stored before this version read?** → **As the default, everywhere.** There is no legacy reading and no migration, shim, or fallback branch. The accepted consequence is stated in the requirement itself: a pre-existing binding whose first scan has still not completed will skip its backlog after the upgrade. → FR-058, `## Out of Scope`
- **Does the sweep need a cap to keep a burst bounded?** → **No.** The bound is the window's own contents. The burst is contained by design rather than by a cap: the sweep enqueues only, and dispatch stays one session at a time under the claim-and-lease cycle. → FR-079, FR-081

**Where the requirement lives.** The product owner directed that this amendment land **in this document** rather than in a separate feature specification, because the rule v1.0.0 set is stated here and a reader of `## Functional Requirements` must get the current behaviour from this section alone. 005 and 006 record the delta in their own changelogs; their bodies are untouched. 006 FR-059(a) — which stated that "a binding with no recorded stamp still replays with no window at all, exactly as today" — is now superseded on that point by FR-065, and 006 FR-010's and FR-084's twelve-field count is deliberately unchanged.
