## Problem Statement

Mecha Turk must turn GitHub activity — issue assignments, pull-request review requests and assignments, and mentions in comments and issue bodies — into agent-led work sessions inside the operator's own OpenChamber installation, without inbound firewall exposure, without a hosted control plane, and without Mecha Turk reimplementing the harness.

Feature 001 proved the extension path end-to-end as a spike (S1–S7 all passed, 2026-09-27) but as a single-account, panel-scoped prototype. Production needs are strictly larger: **N GitHub accounts** each with its own credential and rate-limit pool, **multi-repository polling** with durable checkpoints and correct deduplication across restarts and replays, **post-dispatch agent verification** so work is provably handled by the project-manager agent, and a **durable audit trail that survives an extension uninstall** (constitution v1.3.0, Security and Operational Standard 4 — `host.storage` alone is not an audit home). No single platform surface provides all of this: the panel is sandboxed and single-account, and the platform allows exactly one `integration` card per manifest (`001/research.md` §b.3 — **historical path**: the `specs/001-agent-event-orchestrator/` directory was removed 2026-09-28, commit `110c0a2`; recover it with `git show 110c0a2^:specs/001-agent-event-orchestrator/research.md`; the finding is restated as a requirement in FR-011 below).

This specification therefore describes the production system as an **OpenChamber extension (panel) plus an OpenChamber-hosted local guest service** — the product owner's approved "Option B" path. The panel is the configuration, dispatch, and observability surface; the service owns credential custody, GitHub polling over its own outbound HTTPS, and normalized event relay. OpenChamber keeps ownership of projects, worktrees, sessions, and agents.

## Architecture Decision (locked, 2026-09-27)

Two components, one extension package, one approval flow:

| Component | Owns | Never does |
| --- | --- | --- |
| **Panel** (extension iframe) | Configuration UX (accounts, repository bindings, triggers, policy, worktree option), account-token entry and one-shot handoff, project picker (`host.listProjects()`), dispatch via `host.startSession()`, run list, health display, post-dispatch agent verification | Holding tokens beyond the handoff, polling GitHub directly, creating/deleting projects, worktrees, sessions or agents, writing to GitHub |
| **Service** (OpenChamber-hosted local guest service) | Multi-account token custody in durable storage, GitHub polling over its own outbound HTTPS (headers, ETags, `x-ratelimit-*`), checkpoint/dedup/rate accounting, normalized event relay to the panel, service-owned audit history | Calling host APIs, spawning sessions, touching the harness, any GitHub write |
| **OpenChamber host** | Projects, worktrees, sessions, agents, the `serviceRequest` loopback transport, capability approval, the service process lifecycle | — (Mecha Turk never recreates these) |

Transport: `panel --serviceRequest--> host --HTTP 127.0.0.1:<ephemeral port>--> service`, request/response only (`001/research.md` §b.9 — **historical path**, removed with the 001 directory in commit `110c0a2`; restated in the Architecture Decision table above and in FR-002). GitHub traffic never crosses the panel→host leg; it originates in the service with its own credentials.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Configure GitHub accounts and repositories (Priority: P1)

As a self-hosting operator, I paste a GitHub personal access token for each GitHub account I work with, verify each account, and bind each repository to one account, one existing OpenChamber project, and a set of triggers — so that Mecha Turk knows what to watch and under which identity.

**Why this priority**: Nothing else in the system can run without accounts and bindings; this is the first screen an operator touches and the one every other story depends on.

**Independent Test**: On a clean install, add two accounts (paste token → verified login returned), bind one repository to an account and an already-registered project, enable issue-assignment and mention triggers, and observe the binding become `active` — without any CLI, any GitHub write, and with zero token bytes in persisted panel state, logs, or audit.

**Acceptance Scenarios**:

1. **Given** no accounts exist, **When** the operator pastes a fine-grained PAT, **Then** the service verifies it against GitHub `/user`, stores it outside `host.storage`, returns the numeric user id and login, and the panel displays `Connected as <login>`; the token appears in no storage, ledger, log, toast, or audit record.
2. **Given** the `service` capability has not been approved, **When** the operator attempts a token handoff, **Then** the handoff is refused with the approval instruction, and no token leaves the panel.
3. **Given** a verified account, **When** the operator adds a repository, **Then** they choose the account, then an existing project from the `listProjects()` picker, then per-repo triggers; if the desired project is not registered, the panel shows the manual "Add project" guidance and the binding stays in the recoverable `project_missing` state — no project is ever created by the extension.
4. **Given** two accounts with overlapping repository interests, **When** each repository is polled, **Then** each account polls only its own bound repositories under its own identity and its own rate budget.

---

### User Story 2 — An event arrives and a project-manager session is created (Priority: P1)

As a repository maintainer, I assign an issue to one of my configured account identities (or request a PR review, or mention it in a comment or an issue body) so that Mecha Turk discovers the event, applies policy, and starts an OpenChamber session attached to the source with the project-manager agent — without an inbound webhook and without me copying context by hand.

**Why this priority**: This is the product's core value: unattended conversion of GitHub activity into bounded agent work.

**Independent Test**: With one active binding and default policy, seed a new issue assignment for the bound identity, run the poller through a checkpoint boundary, and observe exactly one run and exactly one `host.startSession()` call whose session's read-back verifies against the configured `expectedAgent` baseline — or an explicit blocked state that explains why not. (With no baseline configured, v1.10.0, the read-back records the observed agent and compares nothing.)

**Acceptance Scenarios**:

1. **Given** an active binding and default autonomous policy, **When** polling observes an issue assignment to the bound account identity, **Then** the service normalizes a delivery, records policy approval, relays it to the panel, and the panel dispatches `host.startSession()` with the resolved `projectId`, the issue attachment, a bounded delimited untrusted-context excerpt, the configured worktree option, and the correlation id.
2. **Given** the same assignment observed again inside the 10-minute overlap window (or replayed 100 times), **When** deduplication runs, **Then** no second delivery, run, or session is created.
3. **Given** the dispatched session reports `onSession().agent` equal to the operator's Session Defaults → Default Agent, **When** verification completes, **Then** the run becomes `dispatched` and is listed with a link to the session.
4. **Given** the observed agent differs from the pinned default (or cannot be read), **When** verification fails, **Then** the run is marked `blocked:agent-mismatch`, an audit entry and a panel warning are recorded, and no further automated action occurs for that run.
5. **Given** a configured approval gate on "start work", **When** a matching event arrives, **Then** the run waits in `waiting_approval` and starts only after an auditable approval.

---

### User Story 3 — Observe runs and system health (Priority: P2)

As an operator, I see, in one panel, which accounts are connected, when each repository last polled, how much of each account's GitHub rate budget is spent, what the service is doing, whether the agent pin is holding, and every run with its source link and status — so that I can trust and explain unattended operation.

**Why this priority**: Constitution Principle IV makes unattended operation unacceptable without visibility; this story is what makes stories 1 and 2 operable over time rather than demo-able once.

**Independent Test**: With two accounts and three repositories running, open the panel after a service restart and confirm every health field renders from real state (service status, per-repo last poll, per-account rate usage, agent pin status), then trace one run from source issue to session using its correlation id.

**Acceptance Scenarios**:

1. **Given** a running system, **When** the panel opens, **Then** it shows per-account identity, per-repository last successful poll time and checkpoint age, per-account rate usage against budget, `serviceStatus()`, and the agent-pin verification result — with no secret material anywhere.
2. **Given** the extension is disabled, **When** polling stops, **Then** the panel (once re-enabled) reports the stopped interval honestly rather than masking it; while OpenChamber itself is not running, no polling occurs at all and this dependency is documented and surfaced as health.
3. **Given** a run in `blocked:agent-mismatch` or `blocked:project-missing`, **When** the operator inspects it, **Then** the panel states the exact cause and the manual step that clears it.

---

### User Story 4 — Recover safely from failure (Priority: P2)

As an operator, I want failures — a crashed service, a revoked token, a rate limit, a force-pushed PR head, a removed assignment — to stop work with a precise, auditable reason instead of silently retrying, duplicating, or guessing, so that I can fix the cause and resume without cleanup.

**Why this priority**: Unattended operation is only safe if failure handling is deterministic; this story is the operational half of constitution Principles II and III.

**Independent Test**: Kill the service mid-poll, revoke a token, and force-push a watched PR head; in each case confirm the checkpoint is preserved, the run states an exact blocked/retrying reason, no duplicate session exists, and clearing the cause resumes cleanly under the same run key.

**Acceptance Scenarios**:

1. **Given** a service crash, **When** the host reports `SERVICE_FAILED`, **Then** polling stops, checkpoints remain durable, the panel offers a manual retry, and no silent restart loop occurs.
2. **Given** a revoked or scope-insufficient token, **When** the next poll fails authentication, **Then** the affected streams block with the exact capability named, the token is never echoed, and other accounts continue unaffected.
3. **Given** PR head SHA drift or an assignment removed after discovery, **When** the service re-fetches before execution, **Then** the run pauses and requires a new trigger rather than acting on changed source state.
4. **Given** cleared causes, **When** the operator retries or replays, **Then** the original delivery identity and dedup rules are preserved and no duplicate work results.

### Edge Cases

- **Same issue reached by two triggers** (assignment + mention): two deliveries with distinct delivery keys normalize to one deterministic run key → one run, both source references preserved.
- **Clock skew / delayed GitHub indexing**: timestamp overlap (10 min) plus delivery-key dedup; never a single global cursor — each endpoint/stream keeps its own cursor.
- **IDs not globally ordered across endpoints**: endpoint-specific checkpoint state; ordering assumptions never cross streams.
- **Pagination interrupted mid-window**: prior checkpoint retained, full safe window re-scanned; checkpoint advances only after the whole window is durably represented.
- **Comment edited or deleted between discovery and execution**: re-fetch the current source object; deleted, inaccessible, or ambiguous content is non-actionable and never triggers new work.
- **PR head force-pushed after discovery**: SHA drift detected at re-fetch → run pauses, new trigger required.
- **Assignment removed after discovery**: re-check before any downstream action, record the discrepancy, do not proceed as if assigned.
- **Token revoked, expired, or missing a required scope**: that account's streams block with the exact capability named; no token bytes in any error surface; other accounts unaffected.
- **Rate limit (primary or secondary) hit**: checkpoint preserved, `retry-after`/reset obeyed, bounded backoff with jitter, delayed status shown, no catch-up burst.
- **304 responses unavailable or unsupported on some endpoint**: correctness identical — conditional requests are an optimization only, never a dependency.
- **Project not registered in OpenChamber**: binding enters recoverable `project_missing`, dispatch blocked with the manual Add-project guidance; the extension never creates a project.
- **Agent pin absent or verification inconclusive**: run marked `blocked:agent-mismatch` (fail-closed); a session may exist but is never reported as valid work.
- **Service capability not approved**: no token handoff, no polling, panel states the required approval (the in-panel consent step this edge case also named was removed by product-owner order at v1.9.0; the static Accounts disclaimer carries its warning).
- **Unsupported surface (VS Code, mobile)**: explicit unsupported/disabled state; no claim that polling runs.
- **Service process crashes**: `SERVICE_FAILED`, manual retry, no silent loop, durable state intact.
- **Extension uninstalled**: panel UI state in `host.storage` is wiped (documented); service-owned durable records are the audit home and their uninstall behavior is verified and documented — audit history is never dependent on `host.storage` alone.
- **Empty state (fresh install)**: panel shows the setup-prerequisites checklist and an empty run list, not an error.
- **Error state (4xx/5xx/timeout from GitHub)**: bounded retry with backoff, checkpoint preserved, exact reason surfaced in health with correlation id.
- **An assignment or review request whose actor the event does not name** *(re-cut at v1.12.0, FR-045/FR-052 — the v1.11.0 text read "no readable subject author"; superseded wording recorded in changelog.md → `### v1.12.0`)*: the naming event's `assigner` / `review_requester` is `null`, `''`, or a bot. There is no identity to attribute to, so there is **no event this cycle** — no run, no work, nothing written for a later gate to guess about. Treated as non-actionable exactly as an unreadable mention author already is. **Nothing is substituted**: not the same row's `actor`, not the issue author, not the `assignee`. Because the scan window overlaps, the candidate is re-detected next cycle and the event is created exactly once, if and when GitHub has propagated a readable actor — so this costs at most one cycle of latency and is self-healing, not lost.
- **An assignment or review request performed by a bot** *(re-cut at v1.12.0, FR-045)*: the mention triggers already refuse bot-authored text (FR-016); the same refusal covers the other two kinds, read from the `simple-user` `type` on `assigner` / `review_requester` by the **same** `isBotAuthor` predicate. A bot cannot be attributed into an allow-list match, and there is no binding field that makes one allowed.
- **An in-window event that names a different subject** *(new at v1.12.0, FR-050)*: a `bob`-to-`carol` assignment alongside a legitimate `dave`-to-`bound` one on the same issue. The `bob`→`carol` event is **a different act** and is not used, even when it is the newer of the two; the attribution comes from the naming event. Symmetrically, a `review_requested` event naming a reviewer other than the bound account is not this trigger's evidence.
- **A naming event older than the scan window** *(new at v1.12.0, FR-051)*: an issue still sitting in `assignees`, whose assignment happened long before `lastScanAt − overlapMs`. There is no in-window naming event, so **no event is enqueued**. This is the correction working rather than a loss — a stale assignment is not new work, and gating a session on a decision nobody made this week would be the worse error.
- **A naming event beyond the declared page bound** *(new at v1.12.0, FR-051)*: an issue with a very long event history whose in-window naming event the bounded walk never reaches. The item produces **no event for this cycle** and the exhaustion is **recorded** with the item and the bound. The walk's stop rule is deliberately one-directional — it only stops on a page *entirely* outside the window — so a wrong assumption about GitHub's ordering spends budget, never visibility.
- **App or bot automation acting for a human** *(new at v1.12.0, FR-049)*: an event whose `actor` is an automation account while `assigner` is the human who asked it to act. The attribution is the **human**, from `assigner`, because that is the actor of the act; recording the automation would put an app's login into an allow-list comparison as though a person had assigned the issue. Untested on this repository's data — which has only ever had one human actor — so this is specified from the field's documented meaning rather than from observation, and the conservative direction is preserved either way (FR-052).
- **A stored row carrying `subject-author`** *(new at v1.12.0, FR-044)*: a row the shipped build wrote before this correction, sitting in `events.json` under an account that never cleans its queue file. It **parses**, it is **admitted**, the gate reads its `actorLogin` normally, and every surface renders it **with its basis stated** — the union member stays readable precisely so this row is not orphaned (NFR-011). What it may not do is mislead: the surface says the row was attributed under the rule in force when it was written, and does **not** claim GitHub fails to record the actor, because GitHub does.
- **An event re-detected under a changed allow-list** (v1.11.0, FR-046): the allow-list is **not** part of the event id, so tightening a binding's list cannot split one already-queued event into two, and loosening it cannot resurrect a deduplicated one. The gate is evaluated when the dispatch is authorized, against the binding as it stands then — never twice, never at a different answer.

## Requirements *(mandatory)*

### Functional Requirements

#### A. Architecture and platform boundary

- **FR-001**: The production system MUST consist of exactly one OpenChamber extension package containing a panel and one OpenChamber-hosted local guest service ("Option B"). The panel MUST provide configuration, dispatch, and status/run surfaces; the service MUST provide multi-account credential custody, GitHub polling over its own outbound HTTPS, normalized event relay to the panel, and service-owned durable state. OpenChamber remains the sole owner of projects, worktrees, sessions, and agents (Constitution Principle VII).
- **FR-002**: The manifest MUST declare `contributes.service` together with the minimum capability set required to operate (`sessions`, `prompt`, `service` — the `network` this requirement used to name as "implied by the declared integration" left the set with that integration on 2026-09-30, per FR-011 as re-cut at v1.8.0). The host MUST spawn the service on first `serviceRequest`; the service MUST listen on `127.0.0.1` only, MUST require `Authorization: Bearer <service token>` on every request including `/health`, and MUST be observable through `serviceStatus()` (`stopped | starting | ready | failed`).
- **FR-003**: The supported service surfaces are OpenChamber **desktop and web**. On surfaces where services are not spawned (VS Code, mobile) the panel MUST present an explicit unsupported/disabled state and MUST NOT claim that polling, custody, or relay is operating.
- **FR-004**: The panel MUST NOT create, delete, or mutate projects, worktrees, sessions, or agents. Repository-to-project resolution MUST use `host.listProjects()`; "project not registered" MUST be a first-class recoverable state with operator guidance, never an error and never an implicit creation.
- **FR-005**: All dispatch MUST go through the documented `host.startSession()` with issue/PR attachment (source id, title, url, kind, text, data), the resolved `projectId`, and the configured worktree option. No private UI route, undocumented API, or direct worktree/session manipulation is permitted.

#### B. Accounts and credential custody

- **FR-006**: The system MUST support N GitHub accounts. Adding an account is: panel input pastes a token → one-shot handoff to the service via `serviceRequest` → the service verifies the token against GitHub `/user` using its own fetch → the service persists the credential in service-owned durable storage outside `host.storage` → the service returns the numeric user id and login to the panel.
- **FR-007**: The panel MUST NOT retain any token beyond the transient handoff. Tokens MUST NOT be written to `host.storage`, the ledger, logs, toasts, run records, audit entries, or error bodies at any point. Panel-side handling is write-through only, and every surface that renders request/response material MUST apply redaction.
- **FR-008**: A security gate MUST precede any token handoff, in two mandatory parts: (a) the operator has approved the extension's declared capabilities (including `service`) at install time; (b) the panel MUST present a **static disclaimer beneath the Accounts section**, always visible and rendered from the canonical block the token-handoff contract §1.1 pins, that states, in plain language, that the GitHub token goes to the local service over the loopback proxy, that the service is sandbox-advisory and an allowed service has the operator's full user access, that the token is stored outside extension storage at file permissions and unencrypted (plaintext) on disk, and that a connection is recorded in the service audit as an occurrence only — never the token. The disclaimer is informational: **no Accept/Decline control, no stored acceptance, no version to renew, nothing to click** (002 v1.9.0). The credential routes MUST be gated by their remaining protections only — bearer authentication before route resolution, the loopback-only listener, body/size caps, shape-before-network validation, the verify throttle, and the redaction/logging rules — and the panel MUST NOT send a `consentVersion` member. No consent occurrence is recorded, because none is given to record.
  - ***Was*** *(v1.1.0–v1.8.0, superseded 2026-10-01 by product-owner order at v1.9.0)*: "A security gate MUST precede any token handoff. The gate has two mandatory parts: (a) the operator has approved the extension's declared capabilities (including `service`) at install time, and (b) the panel presents an explicit consent step before the first handoff that states, in plain language, that service permissions are advisory in Phase 1 and an allowed service has the operator's full user access. The occurrence of consent MUST be recorded in audit without any token material."
- **FR-009**: Account identity MUST be keyed by the numeric GitHub user id discovered from `/user` (durable); the login is display-only and MUST NOT be used as a durable key. If an operator-supplied expected-login constraint exists and disagrees with `/user`, the account MUST be rejected (fail closed).
- **FR-010**: The system MUST document and validate the credential scope matrix: `Metadata: read`, `Issues: read`, `Pull requests: read` (and `Contents: read` only if repository metadata is passed to OpenChamber). Write scopes are NOT required. Missing permissions MUST block the affected stream with the exact capability named, never silently downgrade. The GitHub Notifications API MUST NOT be used as a discovery source.
  - **Single-verdict note (Wave 2, documented by T-009m — FR numbering unchanged, L5)**: today the matrix is emitted as **one shared verdict for all four capabilities**, because GitHub reports a single granted-scope set per token: each capability reads `ok`/`missing` from the classic scopes GitHub returned, or `unknown` when it returned none (fine-grained PATs, GitHub App tokens). The fail-closed rules are unchanged by that shape — `missing` still pre-blocks the affected stream with the capability named, `unknown` is resolved by the first real 403, and neither ever silently downgrades (FR-010's operative requirement). Per-capability divergence would need response-specific probing and is deferred to a later wave rather than implied by Wave 2 output.
- **FR-011**: **Manifest integration card — retired by product-owner order (2026-09-30).** The manifest MUST declare **no** `contributes.integration` card at all: the host-managed GitHub token card the first release shipped (`apiOrigin: https://api.github.com`, `account.path: /user`, `scheme: bearer`) is removed, and with it the two products FR-011 named at v1.1.0 — (a) a connected-login identity badge in the panel and (b) an optional read-only connectivity/identity diagnostic. There MUST be no second credential surface: GitHub credentials are service accounts under this document's own custody rules (FR-006, FR-007), and **all GitHub traffic for polling, discovery, and dispatch originates in the service** — this clause is unchanged from v1.1.0. The product MUST be fully functional with no card present, and the panel MUST NOT render a card-derived identity, badge, or diagnostic anywhere: a panel holding no card state must not report one. The panel MUST NOT make a GitHub request of its own either — `host.request()` has no caller in panel source — so `network` is no longer an implied capability; `service` still is, from `contributes.service`.
- **FR-012**: Credential rotation and revocation MUST be supported without data loss: revoke on GitHub, replace the token through the account handoff flow, and retain all existing checkpoints, deliveries, runs, and audit history for that account.

#### C. Repository binding and triggers

- **FR-013**: Adding a repository MUST follow the sequence: choose account → choose an existing OpenChamber project from the `listProjects()` picker → enable per-repository triggers. The supported target scale is fewer than 10 repositories per deployment.
- **FR-014**: Project creation is out of scope (no platform API exists). The picker MUST include a "not listed?" affordance that documents the manual steps (command palette → Add project, sidebar **+**, or folder browser) and MUST leave the binding in a recoverable state until a registered project is selected.
- **FR-015**: The trigger set MUST include, each independently toggleable per repository: (a) issue assignment to a configured account identity, (b) pull-request review request or review assignment for that identity, and (c) a configurable mention token appearing **either in a new issue/PR comment or in an issue body** — a mention in either place triggers (extended from comments only by operator decision, 2026-09-28; see `## Clarifications`). The mention token defaults to `@<login>` of the bound account, matches case-insensitively, and MAY be overridden per repository (for example a shared bot handle). Both placements share the same match, the same bot-authored-source exclusion (FR-016), and the same scan window; one issue body yields at most one mention event per bound account.
- **FR-016**: All trigger matching MUST be scoped to the identity bound to that repository. Events for other identities, bot-authored duplicates, and non-matching content MUST be ignored or audited as non-actionable, and MUST NOT create work.

#### D. Polling and discovery (service-side)

- **FR-017**: Discovery MUST be outbound HTTPS polling performed by the service, with a default interval of **60,000 ms** (configurable within 15,000–300,000 ms). No inbound listener, webhook endpoint, or webhook configuration exists in this feature. Discovery MUST use repository-scoped endpoints only.
- **FR-018**: For each account + repository + stream the service MUST persist a durable checkpoint containing endpoint/filters, last safely observed item id and timestamp, pagination position, conditional validators (`ETag`/`Last-Modified`) where captured, poll time, and credential/account scope. A checkpoint MUST advance only after the fetched page/window is durably represented in full.
- **FR-019**: Polling MUST overlap the last observed window by **10 minutes** by default (configurable) and MUST deduplicate by a stable **delivery key** scoped to provider, account, repository, source type, source id, and event kind. Identifier-only cursors MUST NOT be treated as sufficient.
- **FR-020**: Pagination MUST be processed completely or the prior checkpoint retained; `per_page` MUST NOT exceed 30, and responses MUST be paginated rather than fetched at provider page limits.
- **FR-021**: Because the service owns its own request and response headers, it MAY send conditional requests (`If-None-Match`/`If-Modified-Since`), read `ETag`/`Last-Modified`, and read `x-ratelimit-*` headers. Correctness MUST NOT depend on any of this: 304 handling is a feature-detected optimization, and every requirement in this specification MUST hold identically when conditional requests are unavailable.
- **FR-022**: Rate budget MUST be accounted **per GitHub account and shared across all repositories bound to that account**. The steady-state design point is approximately 600–1,500 requests/hour at the default interval for up to 10 repositories, within the documented 5,000 requests/hour authenticated limit. The service MUST honor primary and secondary rate-limit signals, `retry-after`/reset guidance, network timeouts, and transient 5xx responses with bounded exponential backoff plus jitter, and MUST expose next poll/retry time and remaining budget.
- **FR-023**: Polling schedules and checkpoints MUST survive restart, resume within the overlap window, and audit any replayed observation as duplicate or previously processed. A controlled operator rescan/replay from a chosen timestamp MUST be supported without weakening deduplication or altering source identity.
- **FR-024**: The system MUST fail closed for unconfigured repositories, identity mismatch, invalid or expired credentials, unsupported API responses, ambiguous event classification, missing policy, and unresolved projects — blocking with an explanation rather than proceeding or degrading silently.

#### E. Normalization, policy, and dispatch

- **FR-025**: Events MUST be normalized to the carried-forward event contract (**historical path**: `specs/001-agent-event-orchestrator/contracts/events.md` v1 — removed 2026-09-28 with the 001 directory, commit `110c0a2`; recover with `git show 110c0a2^:specs/001-agent-event-orchestrator/contracts/events.md`. The **live** record is `contracts/events-carry-forward.md`, which carries v1 forward as the reference schema and versions it additively to v1.1): kinds `mention`, `issue_assignment`, `review_request`, `review_assignment`; source identity scoped by provider/account/repository/type; untrusted, delimited content; correlation id. This feature may version the schema; the v1 record remains the reference.
- **FR-026**: Before any downstream action the service MUST re-fetch the current source object. Deleted, edited, inaccessible, or ambiguous content is non-actionable; assignment removal and PR head SHA drift MUST pause the run and require a new trigger, with the discrepancy recorded.
- **FR-027**: Policy MUST be autonomous-by-default for authorized actions, with per-action toggles (starting work now; future write/merge gates exist only as documented policy statements because this feature never writes to GitHub). A missing policy MUST fail closed for that action. Every policy decision MUST record policy version, actor/source, requested action, decision, timestamp, and reason.

#### H. The actor allow-list (added at v1.11.0; GitHub issue #9 — FR-044, FR-045, NFR-011, SC-005, AC-024, and AC-025 **re-cut at v1.12.0**, which adds FR-049 – FR-052 and AC-028 – AC-031)

- **FR-043**: The normalized event MUST carry the **triggering actor** as first-class members, on the base snapshot every trigger kind shares: `actorLogin` — the GitHub login the event is attributed to — and `actorAttribution`, the closed union naming **how** that attribution was made (FR-044). Both are credential-free by construction (a login is public repository identity, never a secret), both are validated on write and on read like every other member, and an unrecognized `actorAttribution` value MUST refuse the record rather than default to a guess (FR-024). The normalized-event schema is versioned **additively** to `schemaVersion 1.2` for this addition, exactly as `1.1` was for the delivery key and the run linkage: **no existing member changes shape, nothing is removed, and `contracts/events-carry-forward.md` remains the live record of both versions.** This document owns the model; the **gate** that decides what the actor may do is 003's, and the **rendering** is 005's.
- **FR-044** *(re-cut at v1.12.0 — the proxy rationale was a false premise; superseded wording recorded in changelog.md → `### v1.12.0`)*: `actorAttribution` MUST be one of exactly two values, and the union **remains closed** — an unrecognized value MUST still refuse the record rather than default to a guess (FR-024). What changed is which values this build **writes**:
  - **`'direct'`** — **GitHub itself named the identity that performed the act.** Nothing is inferred, nothing stands in, and this is now the basis for **all four** trigger kinds. For the two mention kinds GitHub names the author of the text that carried the token — the comment's author for a comment mention, the issue's author for an issue-body mention. For the assignment and review kinds GitHub names the actor in a **dedicated field on the issue's own event record**: `assigner` on the `assigned` event, and `review_requester` on the `review_requested` event, both on `GET /repos/{owner}/{repo}/issues/{issue_number}/events`, both nullable `simple-user` members carrying `login` and `type` (FR-049, FR-050).
  - **`'subject-author'`** — **readable, and no longer produced.** The value stays in the closed union because the shipped build already wrote rows carrying it to `events.json`, and a vocabulary a stored file still holds cannot be deleted without invalidating that file; **the reader MUST accept it** and every surface that encounters it MUST render it rather than refuse the row, because a row the panel cannot read hides an **entire** dispatch. **No row written under this amendment may carry it**, and no requirement, path, or code may introduce a producer for it. It survives as a **record of what shipped**, not as a sanctioned attribution.

    **Why v1.11.0 believed otherwise, stated plainly because the belief is instructive.** It read the **two list feeds the poller happens to call** — `GET /repos/{owner}/{repo}/issues` exposes `assignees`, the *current* assignee set, with no actor behind it; `GET /repos/{owner}/{repo}/pulls` exposes `requested_reviewers`, the *current* reviewer set, with no requester behind it — and generalized from those two endpoints to GitHub as a whole. The list feeds really do name no actor. **GitHub does.** The actors live one endpoint away, on the per-item **events** feed, in fields whose names are the whole answer: `assigner` and `review_requester`. This is a research failure, not a design failure — a two-endpoint sample generalized to a provider — and it is recorded here, and in `research.md` §R8, because a specification that hides how it was wrong cannot be checked for being wrong again.

    **What remains genuinely true**, and is why the closed union keeps a second member rather than collapsing to one: an attribution is a **claim about provenance**, and a stored row may carry a basis this build would not have written. That is exactly what the pre-v1.12.0 rows are. An unrecognized value still refuses; a known-but-unproduced one still reads.
- **FR-045** *(re-cut at v1.12.0 — the actor for the assignment and review kinds is now the event's named assigner/reviewer, the unreadable-actor clause is narrowed to that actor, and the sentence requiring `PollPull`'s author fields is **struck**; superseded wording recorded in changelog.md → `### v1.12.0`)*: Attribution is **mandatory and fail-closed**. Every enqueued event MUST carry a readable, non-bot `actorLogin`, judged by the two judgements this product already applies to mention authorship and reused rather than reinvented: the exported `isBotAuthor` predicate — a `[bot]` login suffix **or** the account's `type === 'Bot'` — and the mentionable-author check beside it, which additionally refuses an identity GitHub would not name at all (`''`). Both judgements read the `simple-user` shape unchanged, because that is where `login` and `type` live on **every** actor member of every feed this product reads, the new ones included. Consequently: **(a)** a bot-authored comment, issue body, **assignment, or review request** is non-actionable and creates no work, which **extends FR-016's exclusion from the mention triggers to all four trigger kinds**; **(b)** an event whose **actor** is unreadable or bot-authored creates no event at all — it is dropped as non-actionable rather than enqueued with an empty actor for a later gate to guess about — and for the assignment and review kinds **that actor is the one the event names**, `assigner` or `review_requester`, so a `null` on that field is the unreadable case and is refused rather than filled from `actor`, from the subject author, or from anyone else (FR-052); and **(c)** no binding field may be written to allow-list a bot, because no bot event is ever created to be allowed.

    **Struck at v1.12.0**, from the v1.11.0 text of this requirement: *"To make FR-044's `subject-author` basis possible at all, `PollPull` gains `authorLogin` and `authorType` mirroring `PollIssue` and `PollComment`; without them the review kind has no identity to attribute to."* The stated purpose no longer exists — the review kind's actor now comes from the event's `review_requester`, not from the pull request's author — so **no requirement at v1.12.0 asks for those two fields**, and whether the implementation keeps or removes them is Phase 6's business and not a specification question. What replaces them is FR-049 and FR-050, which say where the review kind's actor comes from instead. The strike is recorded here rather than made silently because a requirement that quietly stops needing a field is the kind of drift a reader of the code would find before a reader of the spec.
- **FR-046**: The actor MUST **not** enter the deterministic event id. `evt-<owner>~<repo>~<issueNumber>~<accountNumericUserId>` plus its optional discriminator — `~mention~<commentId>`, the fixed `~mention~body`, or `~review` — is **unchanged by this amendment**, for the reason 003 FR-012 already gives for the same identifier: it is simultaneously the delivery's dedupe key, its relay path segment, and the reference recorded in existing panel ledgers, audit rows, and the run history. The actor therefore **rides the record and never its identity**. An issue observed once before this amendment and again after it produces **one** event, not two; and an issue observed once under one allow-list and again under another produces **one** event, because the policy is evaluated once, when a dispatch is authorized (003 v1.8.0), not again on each detection.
- **FR-047**: A binding MAY carry **`allowedUsers`**, an array of GitHub logins, with exactly three states and no fourth:
  - **Absent** — no policy is configured and **any human actor may trigger** this repository. Absent is a complete, valid state: the key is omitted, never written as `[]`, `null`, or `''` (the same rule 004 FR-022 set for `startingPrompt`, and for the same reason — "unset" needs no sentinel).
  - **Non-empty** — **exactly** those logins may trigger. Comparison is **case-insensitive**, because GitHub logins are case-insensitive and this document's own mention token already matches that way (FR-015); the stored spelling is preserved verbatim and only the comparison folds case.
  - **Explicitly empty (`[]`)** — **a refusal**, not "any user" and not "nobody". An empty array is ambiguous in exactly the way this product refuses to be ambiguous, and it is refused by the fail-closed binding validator with a field-level remediation naming the two honest alternatives (remove the field to allow everyone, or name at least one login). The way to stop every trigger is to **disable the binding**, which the store already models.

  The field is validated on **every read and every write** of the bindings document, by the service, in the same per-field collect-every-refusal posture as `startingPrompt` (004 FR-013, 004 FR-022, 004 FR-071) — a hand-edited file and a panel save are judged by one rule set or by neither. It rides the **existing whole-file grant** `GET` / `PUT /v1/bindings`; no new endpoint, method, or error code is added, and the per-binding `PATCH /v1/bindings/:bindingId` this document records as deliberate MVP-DEBT is not reopened. **This document owns the field's rules**; 003 owns the gate that evaluates it and 005 owns its rendering — the same three-way split every other binding field follows, and the reason no two of them re-specify it.
- **FR-048**: **Exactly one repository per binding is retained; pluralizing it, or adding a wildcard, is forbidden.** A binding is the edge **`repo → project`**: `binding.projectId` flows to the enqueued event's `projectId`, then to the run record, then to `host.startSession({ projectId })` (002 FR-013, FR-028; 003 FR-010's run key; 005 FR-053). A binding spanning several repositories would make *"which project does this dispatch into?"* ill-defined, and the product owner considered and rejected both the plural `repository` and a wildcard on exactly that ground. The three scenarios GitHub issue #9 asks for are therefore expressed as **N bindings**, which is expressible today and needs no new structure:
  1. *A specific list of users on a specific list of repositories* → **one binding per repository**, each carrying that list. The list is repeated per binding; there is no shared-list object, because a shared list would be a second thing with a second lifecycle and a second validation rule.
  2. *A specific list of users on any repository* → **one binding per repository**, each carrying the **same** login list. "Any repository" means *every repository the operator chooses to bind*, not a wildcard — the binding is created per repository exactly as it is today, and the login list is repeated by the operator.
  3. *A specific list of repositories that allow any user* → **N bindings with no `allowedUsers`**, which is precisely today's shipped behaviour: absent means any human may trigger, and 005's rendering says so in words wherever the binding is listed.

#### H2. Naming the actor of an assignment or a review request (added at v1.12.0)

Four requirements, and they exist because FR-044's corrected premise is only half a specification. *That* GitHub names the actor says nothing about **how the poller reaches those fields**, **which event answers which candidate**, **what the scan window means against an endpoint with no window parameter**, or **what happens when the actor is not there**. Those four answers are FR-049 – FR-052, and none of them is a detail: each one is a place where the obvious implementation guesses, and each guess would be a wrong actor in the audit trail or a session started for someone nobody vouched for.

- **FR-049**: **The actor for the assignment and review kinds is read from the item's own event list, and only for an item already detected as a candidate.** When — and only when — the issues or pulls **list** feed has already identified an item as an **assignment candidate** or a **review candidate** for the bound account, the poller MUST read **`GET /repos/{owner}/{repo}/issues/{issue_number}/events`** for **that item** and take the actor from that response. Three rules bound it:
  1. **Per item, never repository-wide.** The repository-wide `GET /repos/{owner}/{repo}/issues/events` and the `GET /repos/{owner}/{repo}/issues/{issue_number}/timeline` MUST NOT be called for attribution. The reason is not tidiness and should be read as the design it is: a repository-wide read costs one to two requests **every cycle regardless of whether anything matched**, and — because these endpoints have no server-side window (FR-051) — it would need its **own** pagination-truncation concept, since a busy repository can push a rarely-scanned binding's in-window events past the page cap. Per-item reads cost **zero** when nothing matched, are small when something did, and introduce no second truncation surface. **A pull request is an issue** to GitHub and is served by the same path; the `issue.pull_request` member on the response is what distinguishes the two.
  2. **Read-only.** This read is a discovery read like every other the poll loop makes. It MUST NOT write to GitHub, and it inherits FR-031's read-only-to-GitHub rule verbatim.
  3. **Same budget, same discipline.** The read MUST be charged to the **same per-account rate budget** as every other request (NFR-003), MUST honour `retry-after` and the bounded backoff ladder on failure (FR-022), and MUST NOT be issued more than **once per candidate item per cycle**. Cost model, stated so the budget arithmetic is not a surprise: **zero** requests when no item matched; **one** request per matched candidate item per cycle, on top of the list-feed scan the cycle already performs.

  The response members this requirement reads, and nothing else: `event` (the kind word — the schema carries **no enum**, so an unrecognized word is ignored rather than treated as a known kind), `assigner`, `review_requester`, `assignee`, `requested_reviewer`, `actor`, `created_at`, and the `issue` member's `number` and `pull_request`. **`assigner` and `review_requester` are the fields to read, not `actor`.** In every row observed on this repository `actor` equalled the explicit field, but the explicit field is the correct one: `actor` is documented as *the person who generated the event*, while `assigner` and `review_requester` name the actor **of the act**, and the two can differ for app and bot automation — where the event is generated by the app and the assignment is performed by the human who asked it to. Reading `actor` would record the automation as the person who assigned the issue.
- **FR-050**: **The correlation is closed, and an event that does not name the bound account is a different act.** Given a candidate item, exactly one rule per kind selects the event that answers it, and there is no fallback to another event, another field, or another kind:
  - **Assignment candidate** → the event is an **`assigned`** event on that item whose **`assignee.login` is the bound account**. Its actor is that event's **`assigner.login`**. An `assigned` event naming a *different* assignee is a different act and MUST NOT be used, even when it is newer.
  - **Review candidate** → the event is a **`review_requested`** event on that item whose **`requested_reviewer.login` is the bound account**. Its actor is that event's **`review_requester.login`**. A `review_requested` event naming a *different* reviewer is a different act and MUST NOT be used, even when it is newer.
  - **Where several qualify** — a bulk assignment that touches the bound account more than once inside the window, or the same account re-assigned and re-unassigned — the answer is the one with the **greatest `created_at`** among the qualifying events (FR-051). The event word alone is not the filter: `unassigned`, `closed`, `labeled`, `referenced`, and `head_ref_deleted` are all kinds the endpoint returns, and none of them is an answer.

  **The asymmetry, stated because it is easy to read backwards.** The subject field is the one that must match the bound account — `assignee` for an assignment, `requested_reviewer` for a review request — because those are the identities FR-015 makes the trigger *about*: an issue assigned **to** the bound account, a review requested **for** it. The actor is read from the **other** field on the same event. Matching on `assigner.login` instead would be a different product: it would fire on *the bound account having assigned somebody*, which FR-015 does not specify and which the intake's own rule — *an event that does not name the bound account is a different act* — rules out, since such an event names the bound account as the **performer** and somebody else as the subject. Both fields are **nullable**, and a null on either fails closed under FR-052; neither may be defaulted from the other.

  **A consequence worth stating, because it is a behaviour change and not only a new capability.** Requiring an **in-window** naming event means an assignment made long before the window no longer enqueues anything, where the v1.11.0 list-feed-only build would re-fire on it every time the item re-entered the scan. That is the correction working: a stale assignment is not new work, and an allow-list evaluated against an assignment from months ago would gate a session on a decision nobody made now.
- **FR-051**: **The scan window is applied client-side on `created_at`, because the endpoints have no window parameter.** `GET /repos/{owner}/{repo}/issues/{issue_number}/events` accepts **only** `per_page` and `page`. It has **no `since`**. Neither does the repository-wide `GET /repos/{owner}/{repo}/issues/events`; nor does `GET /repos/{owner}/{repo}/issues/{issue_number}/timeline`, which adds only `exclude`. No requirement, plan, or implementation may therefore send a `since` parameter to any of them or assume one exists. The in-window test MUST be a **comparison the service makes** between the event's `created_at` and the same window start the list feeds are scanned with — `lastScanAt − overlapMs` — with the existing overlap semantics unchanged, including the replay case.
  - **Ordering is not relied upon.** Selection is by **maximum `created_at`** among qualifying events, never by position in the response. A fixture whose events arrive newest-first, oldest-first, or interleaved MUST produce the same actor. This is a deliberate choice against the cheaper "the last matching row wins" implementation, which is correct only as long as GitHub's undocumented ordering holds and silently picks the wrong actor the day it does not.
  - **The page walk is bounded, and its stop rule is conservative.** The walk uses the `per_page` bound the product already declares (≤30) and stops when a page arrives whose events are **all** older than the window start. Because the rule requires the *whole* page to be outside the window, an ordering assumption that turns out to be wrong can only cause **over-fetching** — more requests until the bound — and can never cause the walk to stop early and miss an in-window event. That asymmetry is the point: the failure direction must be wasted budget, never a silently unattributed trigger.
  - **Exhausting the bound fails closed.** If the walk reaches its declared maximum page count before such a page arrives, the item produces **no event for this cycle**, the exhaustion is **recorded** with the item and the bound (constitution IV — an operator must be able to explain a missing trigger), and the attribution MUST NOT be taken from the partially-seen list. The page bound itself is a planning constant; what this requirement fixes is the **behaviour at the bound**, which is the part a test can hold it to.
- **FR-052**: **An actor that cannot be read produces no event this cycle, and the next cycle asks again.** For an event that FR-050 selected, the actor is `assigner.login` or `review_requester.login`. If that member is **`null`**, or the account is **unreadable** (`''`), or the account is a **bot** (FR-045's `isBotAuthor`), then **no event is enqueued for this cycle** — no run, no work, and nothing written for a later gate to guess about. Specifically **forbidden** as substitutes, each of which was available in the v1.11.0 build and each of which would record a guess as a fact: the event's `actor` member, the issue or pull-request author, the `assignee` or `requested_reviewer` on the same event, and any previously recorded actor for the same item. This is the existing `isAttributableAuthor` posture — one judgement, now applied to the actor the event names — and it is FR-045(b) landing on the corrected actor.

  **The case is self-healing, and that is why refusing is honest here rather than lossy.** The scan window **overlaps** — it starts at `lastScanAt − overlapMs`, not at `lastScanAt` — so the same candidate is **re-detected on the next cycle**. A `null` because GitHub had not yet propagated the field is therefore asked again, and creates its event exactly once, on the cycle where the actor becomes readable. Refusing costs at most one cycle of latency; guessing would cost a permanently wrong attribution in the audit trail, which is what constitution IV forbids and what no latency is worth.

  **What is untested, stated rather than assumed.** Every behaviour above was verified against this repository's own data and against GitHub's OpenAPI description for the endpoint. Three cases were **not**, and none of them is guessed:
  - **Bot and app actors** on `assigner` / `review_requester` — unobserved here, this repository having only ever had one human actor. Handled by the existing bot predicate, which reads the `simple-user` `type` the same way it already does on every other feed; if a future row shows a bot that predicate does not catch, the outcome is a refused event, not a granted one.
  - **Bulk assignment** — several events naming the bound account inside one window. Handled by the maximum-`created_at` rule (FR-050), which is defined for it whether or not it has been seen.
  - **A `null` `assigner` or `review_requester`** — never observed. Handled by FR-052's refusal, deliberately, and the requirement is written so that a `null` fails closed **even though the `actor` member on the same row would usually have been readable** — because that is precisely the substitution that would make the correction cosmetic.

### Key Entities

- **Account**: GitHub identity used for matching and polling — durable `numericUserId`, display `login`, optional expected-login constraint, credential reference held only by the service, verified-at timestamp, scope check result, connection state.
- **RepositoryBinding**: one repository under one account — GitHub repository id/owner/name, bound account, resolved OpenChamber `projectId`, per-trigger enablement flags, mention token override, worktree option, **optional `allowedUsers` login list (FR-047; key absent when unset)**, policy profile, enabled state.
- **Checkpoint**: per account + repository + stream cursor — endpoint/filters, last observed id/timestamp, pagination position, validators, overlap window, last poll time, retry/backoff state, next poll time.
- **Delivery (normalized event)**: immutable normalized provider fact — schema version, provider, account id, repository, source type/id/updated_at/url, event kind, **triggering actor (`actorLogin` + `actorAttribution`, FR-043)**, subject (type/number/base ref/head sha), bounded content reference, correlation id, **delivery key**. The actor is a **record member and not part of the delivery key or the event id** (FR-046). **Updated at v1.12.0**: the actor is named by the event for **every** kind (FR-049, FR-050), and `'actorAttribution'` is written as **`'direct'` only** — `'subject-author'` remains a member of the closed union and remains **readable**, because rows the shipped build already wrote carry it, but it has **no producer** and no row written under v1.12.0 may carry it (FR-044).
- **Run**: work unit derived from one or more deliveries — deterministic **run key**, policy decision, lifecycle state, attempts, worktree option used, dispatch result, verification result, source links. A run **coalesces** its deliveries (003 FR-011), so it may carry more than one attributed actor; which of them authorized the dispatch is 003's rule, not this document's.
- **SessionRef**: pointer to the host-owned session — `sessionId`, title, source url, dispatch timestamp, observed agent/model, verification status. OpenChamber remains authoritative; the extension stores only the reference.
- **PolicyProfile**: per-action autonomy/approval configuration — action name, gate on/off, policy version, effective timestamp.
- **AuditEntry**: append-only record — timestamp, correlation id, event type, actor/source, decision/reason, redaction metadata; never contains a token.
- **ServiceHealth**: `serviceStatus()` value plus per-account rate usage, per-repository last poll/checkpoint age, and agent-pin verification status.

### States

- **Account**: `pending_handoff → verifying → active | rejected`, plus `revoked` and `error` transitions out of `active`. Only `active` accounts may poll.
- **RepositoryBinding**: `draft → project_missing → active | blocked | disabled`. `project_missing` is recoverable; `blocked` carries an explicit reason; `disabled` stops polling for that repository.
- **Checkpoint**: `uninitialized | active | backing_off | stale | blocked | disabled`. Advances only after a fully durable window.
- **Delivery**: `discovered → ignored | duplicate | queued → processing → dispatched | dead_lettered`, with `blocked` available before dispatch.
- **Run**: `created → dispatching → verifying_agent → dispatched`, or `waiting_approval`, `blocked` (incl. `blocked:agent-mismatch`, `blocked:project-missing`, `blocked:credential`, `blocked:policy`, and **`blocked:actor-not-allowed`**, added at v1.11.0 for the allow-list gate 003 v1.8.0 owns), `retrying`, `completed`, `dead_lettered`. Transitions out of `blocked` occur only when the cause clears, under the same run key.
- **Service**: `stopped | starting | ready | failed`, plus the panel-only `unsupported_surface`. Crashes map to `failed` with manual retry.

## Setup Prerequisites

Documented and shipped with the feature (FR-038); each prerequisite is also surfaced in the panel's first-run checklist.

1. **Default Agent pin (required for dispatch)**: In OpenChamber, set **Settings → Sessions → Session Defaults → Default Agent** to **the agent your dispatches should run on** — the value is yours to choose, and since v1.10.0 no agent name is prescribed here (the product owner's order: *"Default Agent pin should default to blank, not everyone is going to use project-manager"*). The platform does not let an extension name an agent per call, and the guest-send path checks this setting first, so this is the only deterministic pin (`001/research.md` §b.2 — **historical path**, removed in commit `110c0a2`; the same finding is researched and stamped in 002's own `research.md` §R3 and enforced by FR-029). Set the matching **`expectedAgent`** baseline on **Settings** as well: it is the value FR-029's verification compares against, and with it blank the read-back records the observed agent without comparing it. Side effect to document: new user sessions also default to the pinned agent until changed. The panel cannot read this setting, so the pin is enforced **post-dispatch** by verification against that baseline (FR-029), not pre-flight.
2. **OpenChamber must be running**: Unattended operation means "unattended while the operator's OpenChamber is up". Polling and dispatch stop when OpenChamber stops, when the extension is disabled, or when the service is not running (constitution v1.3.0, Security and Operational Standard 3).
3. **Desktop or web surface**: Guest services spawn on desktop and web only; VS Code and mobile do not spawn services, so those surfaces show the unsupported state (FR-003).
4. **GitHub PAT scopes**: fine-grained PAT preferred, with `Metadata: read`, `Issues: read`, `Pull requests: read` (+ `Contents: read` only if repository metadata is passed to OpenChamber). No write scopes. Organization approval policies for fine-grained PATs must be granted where the organization requires them. The Notifications API is not used (classic-PAT-only limitation, `001/research.md` §a.6 — **historical path**, removed in commit `110c0a2`; the rejection is carried as a requirement in FR-010 above and re-stamped in 002's `research.md` §R6).
5. **Registered project**: each bound repository's project must exist in OpenChamber (command palette → Add project, sidebar **+**, or folder browser). The extension cannot create it.

**~~6. Service capability approval~~ — removed at v1.9.0** (product-owner order, 2026-10-01): the line read *"approve the extension's declared capabilities at install; token handoff additionally requires the in-panel consent step (FR-008)"*. The consent clause went with the dialog, and with it the numbered line: **five prerequisites remain**, exactly the five the panel's first-run checklist renders (005 FR-037). Install-time capability approval itself is unchanged and still enforced — it is the host's own install gate under FR-002, and an unapproved `service` still refuses the first handoff with instruction (AC-002, token-handoff F1); it simply is not a numbered setup step any more.

## Non-Functional Requirements

- **NFR-001 Detection latency**: Under normal rate conditions, p95 from GitHub event timestamp to run creation MUST be ≤ 2 × the poll interval (default ≤ 120 seconds), measured with ≤10 repositories and no rate-limit pressure.
- **NFR-002 Idempotency**: Replaying any repository window 100 times MUST produce zero duplicate deliveries-in-run, duplicate runs, duplicate sessions, or duplicate external side effects.
- **NFR-003 Rate safety**: Steady-state polling MUST stay within the design point of ~600–1,500 requests/hour per account (≤30% of one account's 5,000/h budget at 10 repositories), MUST respect secondary limits, and MUST never enter a catch-up burst after backoff.
- **NFR-004 Secret containment**: Zero occurrences of any token value in persisted panel state, ledger, logs, audit entries, toasts, error bodies, or committed files, verified by automated scan in tests.
- **NFR-005 Fail-closed safety**: Every failure class listed in FR-024 MUST block rather than proceed, with an explanation naming the exact cause and no secret material.
- **NFR-006 Durability**: After any crash or restart in any state, checkpoints, deliveries, runs, and audit entries recover without silent loss and without duplicate side effects; the audit history home MUST survive extension uninstall.
- **NFR-007 Observability**: One correlation id MUST trace a source observation through checkpoint, routing, policy, dispatch, agent verification, and terminal state, in both the panel and the audit trail.
- **NFR-008 Compatibility**: The OpenChamber SDK version MUST be pinned exactly and re-pinned to the host's own release before execution (spike record: `@openchamber/sdk` `1.24.2`, `001/spike-evidence.md` §1 — **historical path**, removed with the 001 directory in commit `110c0a2`; recover with `git show 110c0a2^:specs/001-agent-event-orchestrator/spike-evidence.md`. The pin itself is live at `package.json` `dependencies` and re-stamped in 002's `research.md` §R7). Host capabilities MUST be adapter-abstracted and capability-checked at runtime; unsupported operations MUST fail safely instead of being reimplemented through private APIs.
- **NFR-009 Surface honesty**: On any surface where a required capability is unavailable, the panel MUST state what is disabled and why; it MUST never display healthy-looking state for non-operating subsystems.
- **NFR-010 Maintainability**: GitHub discovery and the panel↔service transport MUST be adapter boundaries with contract tests; a future webhook adapter MUST be addable without changing routing or policy semantics; strict type checking and linting apply with no suppressions (constitution, Development Quality Gates).
- **NFR-011 Attribution honesty** *(re-cut at v1.12.0 — the premise this requirement enforced was false; superseded wording recorded in changelog.md → `### v1.12.0`)*: **An attribution states a provenance, and no surface may state more than the provenance holds.** Every audit row, run record, source reference, status projection, and rendered surface that names an actor MUST name it **as GitHub named it**: for `'direct'`, the identity the provider recorded as the actor of the act, with no qualification, because there is nothing to qualify. For the one remaining member, `'subject-author'`, the surface MUST say that the row was attributed under the rule in force when it was written — the issue or pull-request author standing in for an actor the **list** feeds could not name — and MUST NOT claim that GitHub fails to record the assigner or the reviewer, because **GitHub does record both**, in `assigner` and `review_requester` (FR-044). No surface may present a proxy as a fact, and no surface may present a **corrected** rule as though it had always been the one in force. Verified by a test that drives all four trigger kinds and asserts the wording of each surface that renders an actor. This is the honesty half of the allow-list: a control that quietly guesses who acted is not a control, an audit trail that records a guess as a fact is worse than no audit row, and — the case v1.12.0 exists for — **a trail that states a falsehood about the provider is the same defect wearing the opposite hat.**

## Success Criteria

### Measurable Outcomes

- **SC-001**: A new operator connects their first account and binds their first repository end-to-end in under 5 minutes using only the panel (no CLI, no file edits).
- **SC-002**: At default settings, a matching GitHub event becomes a created OpenChamber session within 2 minutes (p95) of the event timestamp.
- **SC-003**: 100-window replay testing yields 0 duplicate runs, 0 duplicate sessions, and 0 duplicate external side effects.
- **SC-004**: Automated secret scans of persisted state, logs, audit, and error surfaces find 0 token occurrences across the full test suite.
- **SC-005**: With 10 repositories at the 60-second default, steady-state polling consumes ≤1,500 requests/hour per account (≤30% of that account's budget). *(Re-cut at v1.12.0: the ceiling is unchanged, and it now **includes** the per-item actor read FR-049 adds — the figure is base list-feed scan **plus** one events request per matched candidate item per cycle, which is zero when nothing matched. Stating that additively is the honest form; leaving the number to be read as scan-only would make the criterion quietly wrong on exactly the busy repositories where the extra read happens most.)*
- **SC-006**: 100% of runs in the panel display their source link, policy decision, current state, and correlation id — every run is explainable without reading raw logs.
- **SC-007**: After extension uninstall, service-owned audit history remains readable per its documented retention, and the operator can state exactly which panel UI state was wiped.
- **SC-008** (added at v1.11.0): For any dispatch in the panel, the operator can state **who it was attributed to** and **on what basis**, in the panel's own words, without leaving the panel or reading a log — and can restrict who may trigger a given repository with one field, in one save, through the surface bindings already use.

## Configuration Model

- **Accounts**: service-held credentials keyed by numeric user id, verified logins, expected-login constraints, scope check results.
- **Repository bindings**: account, project id, per-trigger enablement, mention-token override, worktree option, **the actor allow-list `allowedUsers` — absent by default, which means any human may trigger and is reported as such rather than as protection (FR-047, 005 v1.11.0)**, policy profile. **One repository per binding, permanently** (FR-048).
- **Policy**: autonomous default plus per-action approval toggles (start work now; future write gates documented only).
- **Polling**: interval (default 60,000 ms), overlap window (default 10 minutes), `per_page` (≤30), retry/backoff bounds.
- **Retention**: audit and payload retention defaults, configurable within documented bounds.
- **Health**: log level, correlation-id exposure, rate-usage reporting.

All of it is service-owned and, since feature 006, operator-editable through `config.json` on the Settings tab. Two surfaces carry **none** of it, and the cleanup review of 2026-09-28 removed the duplicates that pretended otherwise: the manifest carries **no integration card at all** since 2026-09-30 (FR-011 as re-cut at v1.8.0; the card that did exist declared no settings from 002 FR-041) — the one value that once lived there, the agent-verification baseline, now belongs to this configuration as `expectedAgent` (006 FR-100) and is read through `GET /v1/config` (FR-029) — and there is no environment-file configuration of any kind: no `.env`, no `MECHA_TURK_*` variable, and the service's only environment inputs are the host-provided bootstrap pair (006 FR-090, FR-091).

The implementation MUST avoid speculative per-provider or per-agent knobs until a supported capability requires them.

## Out of Scope

The following are explicitly **not** part of this feature:

- Discord or any non-GitHub provider.
- Export/restore of configuration or audit data (post-MVP).
- Label triggers, and any trigger outside the FR-015 set.
- Webhook ingress, webhook secrets, delivery acknowledgements, webhook replay (future adapter only).
- Automatic cleanup of sessions, worktrees, or projects (manual cleanup only).
- Docker packaging (may wrap individual pieces later per constitution Principle V; packaging is not the architecture).
- Hosted/multi-tenant operation, billing, or SaaS authentication.
- Any GitHub write by the extension or service — comments, reviews, reactions, acks, merges, closes, labels.
- Merge, deploy, repository administration, or permission changes under any policy.
- Project creation or registration from the extension.
- Per-call agent, model, or variant selection (platform-stripped; not an attemptable feature).
- Direct panel-side `fetch()` to GitHub (undocumented, unsupported).
- GitHub Notifications API as a discovery source.
- **Allowing a bot to trigger** (v1.11.0). There is no field, sentinel, escape hatch, or policy that admits one: bots are filtered at detection for every trigger kind (FR-045) and no bot event exists to be admitted.
- **Pluralizing a binding's `repository`, or adding a wildcard repository form** (v1.11.0). Forbidden and load-bearing, not merely unbuilt — see FR-048. A binding's purpose is the edge `repo → project`.
- **A shared / reusable allow-list object** across bindings (v1.11.0). The list is a field on one binding; N bindings repeat it. A shared list would need its own identity, lifecycle, validation, and audit story, and buys an operator typing the same two logins twice.
- **Any second actor gate, or any gate at detection time** (v1.11.0). 003 v1.8.0's authorization-time gate is the single enforcement point; a detection-time filter would be cheaper and would leave no audit row, which constitution IV requires.
- **The per-binding `PATCH /v1/bindings/:bindingId` route** — recorded MVP-DEBT above and explicitly not reopened by v1.11.0; `allowedUsers` rides the existing whole-file grant.
- **Any migration, back-compat shim, or fallback for a pre-`allowedUsers` `bindings.json`** (v1.11.0). The product owner ruled it directly: *"there are no migrations needed as we haven't released yet. keep it simple as I can delete my one local install and start over easily."* A stored binding without the key is the **absent** state, which is already specified — there is nothing to convert, and a stored binding whose key is an empty array is **refused**, not reinterpreted.
- **A repository-wide or timeline read to obtain the actor** (v1.12.0). `GET /repos/{owner}/{repo}/issues/events` and `GET /repos/{owner}/{repo}/issues/{number}/timeline` MUST NOT be called for attribution. Named here as forbidden rather than merely unbuilt: unlike the `repository` plural above, this is a *rejected design* with a stated reason — it costs requests on cycles where nothing matched and, with no server-side window on any of the three endpoints, it would need its own pagination-truncation concept on top of the one the scan already has (FR-049, FR-051).
- **Any producer for `'subject-author'`** (v1.12.0). The union member stays **readable** for rows the shipped build already wrote, and the closed union is not narrowed to one value, because a stored file that still contains it must not become unreadable. But no requirement, path, or code may write it, and no fallback path may reach for it when the actor cannot be read — the fallback for an unreadable actor is **no event** (FR-052). Collapsing the union to `'direct'` alone is the tempting cleanup and is exactly what is not being done here; it is recorded as rejected so a later reader does not "tidy" it.
- Phase 4 plan, data model, contracts, task breakdown, or application implementation.

## Assumptions

- **Worktree default**: per-repository worktree option defaults to `generated` (isolates autonomous work from the operator's working tree); `none` and `new:<branch-name>` are selectable. Both `none` and `generated` were exercised live in the spike; `new:` shares the same host-owned path.
- **Branch-name placeholder**: `new:<branch-name>` supports the single literal placeholder `{number}`, substituted with the source issue/PR number; no other templating exists.
- **Untrusted-context bounds**: ≤4,000 characters per source item and ≤12,000 characters per dispatch, with explicit truncation markers — chosen to stay far below host/service body limits and to keep prompts focused; tunable in planning without a spec change only within ±50%.
- **Retention defaults**: audit entries 180 days or 50,000 entries (whichever is reached first); raw/redacted payload excerpts 30 days; minimal audit references (ids, links, decisions) retained until the operator deletes the account/repository binding. Export/restore remains out of scope (see Gate Questions).
- **Mention token default**: `@<login>` of the bound account, case-insensitive; GitHub logins are case-insensitive, so matching must be too.
- **Agent verification mechanics**: reading `onSession().agent` requires the surface to be attached to the dispatched session, so verification opens the created session (a documented UI context switch). The pinned SDK has no silent alternative; planning MUST verify the exact mechanism against the pinned `dist/*.d.ts` and MUST NOT invent an undocumented one.
- **Service-owned storage durability**: service data written outside `host.storage` is expected to outlive extension uninstall because the host's documented uninstall action kills the service process and wipes extension storage, not third-party files; this MUST be verified in planning and documented before the claim appears in user-facing copy.
- **SDK pin**: `@openchamber/sdk` pinned exactly (spike: `1.24.2`), re-pinned to the host's release before execution if the host is newer (`001/spike-evidence.md` §1 — **historical path**, removed in commit `110c0a2`; live pin in `package.json`, re-stamped in 002 `research.md` §R7).
- **Scale**: fewer than 10 repositories, a handful of accounts, one local OpenChamber installation, one logical service instance; multi-instance leasing is deferred.
- **Provider**: GitHub.com REST API; GitHub Enterprise compatibility requires a later review.
- **Connectivity**: outbound DNS/TLS to GitHub only; no inbound Internet connectivity; OpenChamber's own endpoint is loopback.

- Q: **Where is the actor read from?** → A: **The item's own event list**, `GET /repos/{owner}/{repo}/issues/{issue_number}/events`, and **only** for an item the list feeds have already flagged as an assignment or review candidate. Zero requests when nothing matched; one per matched candidate per cycle; charged to the same per-account budget as the scan. **Not** the repository-wide events feed and **not** the timeline: both would cost requests on every cycle regardless of activity and — since neither has a server-side window — would need a second pagination-truncation concept on top of the one the scan already has. → FR-049, `## Out of Scope`
- Q: **Which event answers which candidate, and may a fallback answer instead?** → A: **One closed rule per kind and no fallback.** An assignment candidate is answered by an in-window `assigned` event whose **`assignee`** is the bound account, and the actor is that event's **`assigner`**. A review candidate is answered by an in-window `review_requested` event whose **`requested_reviewer`** is the bound account, and the actor is its **`review_requester`**. An event naming a different subject is a **different act** and is not used, however recent. The asymmetry is deliberate: FR-015 makes the trigger about the identity assigned **to** / requested **for**, so the *subject* field is what must match the bound account, and the actor comes off the same row's other field. → FR-050
- Q: **How is the scan window applied, when the endpoint has no window?** → A: **Client-side, on `created_at`.** The per-item events endpoint accepts only `per_page` and `page`; it has **no `since`**, and neither does the repository-wide events feed nor the timeline (timeline adds only `exclude`). The requirement therefore forbids sending a `since` anywhere, and compares `created_at` against `lastScanAt − overlapMs` itself. Selection is by maximum `created_at`, never by position; the page walk stops only on a page *entirely* older than the window start, so a wrong assumption about ordering spends budget rather than visibility; and exhausting the bound produces no event plus a recorded reason. → FR-051
- Q: **What if the event does not name the actor?** → A: **No event this cycle**, with **nothing** substituted — not the row's `actor`, not the issue author, not the `assignee`, not a previously recorded actor. The scan window overlaps, so the candidate is re-detected next cycle and the event is created exactly once if the actor has become readable. Refusing costs at most one cycle of latency; guessing would cost a permanently wrong attribution. → FR-052, FR-045 *(re-cut)*
- Q: **Why keep `'subject-author'` at all, if nothing writes it?** → A: **Because rows the shipped build already wrote carry it**, and a vocabulary a stored `events.json` still contains cannot be deleted without invalidating that file — which would refuse real stored rows and, at the panel, hide an entire dispatch. So it stays in the closed union, stays **readable**, and is rendered with its basis stated; and no row written under v1.12.0 may carry it. Collapsing the union to one value is the tidy-looking alternative and is **rejected**, recorded in `## Out of Scope` so a later reader does not "clean it up". → FR-044, `## Out of Scope`
- Q: **What is not known?** → A: **Three things, all stated rather than assumed.** Bot and app actors on `assigner` / `review_requester`; bulk assignment inside one window; and a `null` `assigner` / `review_requester` — none observed on this repository, whose data has only ever had one human actor. Each is handled by **refusing** rather than guessing, and the `null` case is specified to fail closed *even though* the same row's `actor` member would usually have been readable, because that substitution is precisely the one that would make the correction cosmetic. → FR-052, changelog.md → `### v1.12.0`
