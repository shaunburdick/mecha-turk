# Changelog — 002-agent-event-extension

Why a requirement changed, and when. Moved out of `spec.md` so that
document states only the current intended behaviour: a reader of

alone. Requirement ids are never renumbered here — other documents

changelog.md

Amendments to this specification follow the same procedure and shape as the project's constitution (`.specify/memory/constitution.md` §Governance): a version bump, a stated rationale, a requirement-by-requirement record, a migration-impact statement, and an approval status. **Amendment procedure**: a conformance gap found against this specification is either corrected in place (wording only, no behaviour change) or deferred to a successor feature, which must be named. Requirement text in this document is **never rewritten to describe behaviour that was not implemented** — the record of what v1.1.0 specified and what shipped is evidence, and erasing it would make the next conformance review impossible.

### v1.2.0 — 2026-09-28 (conformance amendment; corrections deferred to feature 003)

- **Rationale**: The post-implementation review recorded on 2026-09-28 (see `tasks.md` §Debt list, final pre-PR review entry) found **seven defects, five of which are conformance failures against requirements this document already states**. The product therefore contradicts its own specification in the place an operator checks first: how many agent sessions one piece of GitHub activity produces, and why. Leaving the text unchanged and unannotated would make this document assert guarantees it does not provide; rewriting the text to match the shipped behaviour would erase the evidence trail. This amendment therefore does neither: it **records the gap, names the requirement, and names the successor feature that carries the corrected requirement**.
- **Sequencing decision**: Feature 003 **supersedes** this document on the affected points, and this amendment is the index of that supersession. The alternative — restating the corrected requirements here and having 003 reference them — was rejected because it would duplicate normative text across two documents and invite drift, and because the corrected behaviour is materially larger than a wording fix (it introduces runs, leases, single-use dispatch authorization, a richer state model, and a dispatch-lifecycle audit vocabulary). 003 states the full model; this document points at it.
- **Principles reviewed, unchanged in substance**: Principle II (safe autonomy by default) supplied the fail-closed posture for the lost-report case — an unknown dispatch outcome is a stop condition, never permission to dispatch again. Principle III (durable and idempotent work) is the requirement the superseded text was written to serve; the defect is that the implementation did not meet it, so the principle is unchanged. Principle IV (human-visible auditability) is the requirement the missing dispatch-lifecycle audit rows failed. Principle VI (specification and verification before implementation) is the reason this amendment exists at all. No principle is weakened by this amendment.

### v1.3.0 — 2026-09-28 (extension amendment; feature 004 adds the per-binding starting prompt)

- **Rationale**: The product-owner brief of 2026-09-28 asked for a starting prompt per binding. The field cannot be added as an unstated detail, because on this document's own text a dispatch is fully specified by FR-028 — resolved project, source attachment, worktree option, bounded untrusted excerpt, delimiters, correlation id — and every one of those clauses is a security or durability clause. Operator text placed above that framing is a *new kind of input to that boundary*: it is read by the agent as instruction, not as quoted source, and this document's delimiter contract was written for the opposite case. Recording the extension here, in the document the constraint lives in, is what keeps the two from being read as independently true. What is *not* done — and this is the whole design of the amendment — is restating 004's requirement text here. Four requirements, one key entity, one configuration line, and one out-of-scope row are pointed at; the normative wording stays in one place so there is one thing to change when the cap, the refusal set, or the audit shape changes.
- **Sequencing decision**: 004 **extends** this document and **supersedes nothing** in it. The alternative — restating the prompt requirements in this file as the "production" spec — was rejected for the same reason v1.2.0 rejected restating 003's: duplicated normative text across two documents drifts, and a reader who consults this file for a guarantee would be reading a second, unsynchronised copy of it. 004 states the field; this document states the relationship.
- **Principles reviewed, unchanged in substance**: Principle II (safe autonomy by default) is the requirement the delimiter contract exists to serve, and it is what the extension has to be honest about: an operator prompt is trusted input, and the specification says so rather than implying the framing protects against it. Principle IV (human-visible auditability) requires the prompt to be referenceable after the fact without persisting the text on audit rows. Principle VI (specification and verification before implementation) is why the cap, the refusal set, and the snapshot point are requirements rather than planning details. Principle VII (thin orchestration boundary) is satisfied rather than strained: the prompt adds no host capability, no new service surface, and no new storage home — it is a field in a store that already exists. No principle is weakened by this amendment.

### v1.4.0 — 2026-09-28 (placement amendment; feature 005 replaces the panel surface)

- **Rationale**: this document stated two operator-guidance requirements that never reached the panel — FR-014's "not listed?" affordance and FR-038's setup-prerequisites section — and the v1.2.0 table below records both as **shipped conformance gaps**, deferred to 003 for the behaviour. 003 specified the behaviour (FR-070, FR-071–FR-073) and left placement open, because a specification that says *what* a surface must say has not yet said *where* it lives. 005 is that decision: six tabs, each answering one question, with both requirements given a home — FR-014 inside the Bindings tab's project picker, where the operator is when they discover the gap, and FR-038 on the Status tab, because prerequisites are live state rather than static identity. It also gives FR-036's health requirement an honest projection to render into: three members of the status document are hardcoded literals today, so the requirement that health "MUST be exposed and displayed" is displayed, but not truthfully.
- **Sequencing decision**: 005 **extends** this document and **supersedes nothing** in it. Unlike 003's amendment, this one touches a document that is **implemented and live-validated**, so the bar is different: nothing here may change what the shipped system does, and nothing may rewrite a requirement to describe behaviour the MVP does not have. The v1.4.0 delta is entirely about *rendering* — a surface, a placement, and a projection — plus one operator-facing vocabulary decision the owner made on 2026-09-28.
- **Principles reviewed, unchanged in substance**: Principle I (no secret in any store, log, or rendered surface) is served by 005's requirement that the Accounts tab render a credential-free DTO by construction, and by its refusal of credential-shaped operator text. Principle II (safe autonomy by default) is served by 005's rule that an unknown value renders as unknown rather than as a plausible default — the same fail-closed standard this document applies to services and credentials, now applied to what the panel claims about itself. Principle IV (human-visible auditability) is served by the Status tab making the service's real state legible, including the paused reason and the per-binding scan error, and by FR-038's prerequisites each carrying their own remediation. Principle VI (specification and verification before implementation) is the reason the conformance gaps below are recorded rather than quietly closed. No principle is weakened.

### v1.5.0 — 2026-09-28 (extension and reaffirmation; feature 006 makes the configuration operator-editable)

- **What each new requirement fixes, and why it is not a detail.** *That* GitHub names the actor is half a specification. FR-049 says **how the poller reaches the field** — per item, never repo-wide, read-only, on the existing budget, and reading `assigner` / `review_requester` rather than `actor`, because `actor` is documented as the person who *generated* the event and the two can differ exactly where it matters: app automation acting for a human would otherwise put the app's login into an allow-list comparison as though a person had assigned the issue. FR-050 says **which event answers which candidate**, and it is closed with no fallback because every fallback available in the v1.11.0 build is a guess wearing the costume of a lookup. FR-051 exists because **none of these three endpoints has a `since` parameter** — not the per-item one, not the repository-wide one, not the timeline, which adds only `exclude` — so any requirement phrased in terms of a server-side window would specify a capability GitHub does not have. FR-052 exists because "fail closed" is only a requirement if it says *closed to what*: the field's neighbours are readable, so a `null` `assigner` in a fixture where `actor` is populated is exactly the case that would silently reintroduce the guess the correction removed.

- **Why the page walk is bounded, and why its stop rule is one-directional**: with no server-side window there is no bound a single request can rely on, so a walk needs its own. Two failure directions exist — stop too early and miss an in-window event (a trigger that silently never fires), or over-fetch and spend budget. The stop rule is written to fail only into the second: it stops on a page whose events are **all** older than the window start, so any wrong assumption about GitHub's ordering costs requests up to the declared bound and can never cause an early stop. And selection is by **maximum `created_at`**, not by response position, so ordering is not load-bearing anywhere in the rule. Exhausting the bound produces **no event plus a recorded reason** (constitution IV: an operator must be able to explain a missing trigger) rather than an attribution taken from a partially-seen list. The bound's value is a planning constant; the behaviour at the bound is what this amendment fixes.

- **Why the refusal is honest rather than lossy, and why that is load-bearing**: the scan window **overlaps** — it starts at `lastScanAt − overlapMs` — so the same candidate is re-detected on the next cycle. A `null` because GitHub had not yet propagated the field therefore costs at most one cycle of latency, and the event is then created **exactly once** (FR-046 keeps the actor out of the identifier, so the retry cannot duplicate it). This is the same posture the product already took for mention authorship — `isAttributableAuthor` drops an unreadable author **at detection** rather than enqueueing a row for a later gate to guess about — now applied to the actor the event names, reusing one judgement rather than adding a second.

- **One intake ambiguity, resolved from the specification's own words and flagged for the product owner.** The intake's correlation sentence reads *"the newest in-window `assigned` event … whose **`assigner.login`** is the bound account"* and, in parallel, *"the newest in-window `review_requested` event whose **`requested_reviewer.login`** is the bound account."* Those two clauses name **opposite kinds of field** — one an actor field, one a subject field — and the assignment clause is specified here on the **subject** field (`assignee`), with the actor read from `assigner`, for three reasons drawn from already-approved text rather than preference. First, **FR-015** makes both triggers about the identity assigned **to** and requested **for**: *"issue assignment **to** a configured account identity"*, *"pull-request review request … **for** that identity"*. Second, the intake's **review** clause already matches on the subject field, so reading the assignment clause the other way makes the two halves non-parallel. Third, and decisively, the intake's own rule *"an event that does not name the bound account is a different act and must not be used"* is **only coherent** under the subject reading: matching on `assigner` would exclude the very event that constitutes the trigger, because the bound account would be the performer and somebody else the subject. > **v1.12.0 (2026-10-03) — the attribution premise corrected; the `subject-author` proxy loses its producer.** **GitHub records both actors, in named fields.** `GET /repos/{owner}/{repo}/issues/{issue_number}/events` — the feed v1.11.0 never consulted — carries `assigner` ("the person who performed the assignment") on every `assigned` event and `review_requester` ("the person who requested a review") on every `review_requested` event, each a nullable `simple-user` carrying `login` and `type`, so the existing bot predicate applies unchanged. v1.11.0 read only the two **list** feeds the poller happens to call — the issues list exposes `assignees` with no actor, the pulls list exposes `requested_reviewers` with no requester — and generalized from *those endpoints* to *GitHub as a whole*. The list feeds name no actor; the events feed names both. The claim "GitHub does not record who assigned" was **false**, and because a false premise cannot be corrected by rewording around it, this amendment replaces the mechanism rather than annotating it: **FR-044 and FR-045 are re-cut, NFR-011 is re-cut, FR-049 – FR-052 are added**, and the corrected research record replaces §R8. `'subject-author'` **remains in the closed union** — rows the shipped PR already wrote to `events.json` carry it, and a vocabulary a stored file still contains cannot be deleted without invalidating that file — but it has **no producer**, and **no row written under this amendment may carry it**. `'direct'` becomes the basis for **all four** trigger kinds, because GitHub names the actor in every case. The actor for the assignment kind is the event's `assigner`; for the review kind, its `review_requester`. The four new requirements are the per-item read that reaches those fields, the closed correlation rule that picks which event answers which trigger, the **client-side** window comparison that stands in for the `since` parameter **these endpoints do not have**, and the fail-closed duty that an actor which cannot be read produces **no event this cycle** — self-healing, because the scan window overlaps, rather than lost. **What is untested is stated, not assumed**: bot and app actors, bulk assignment, and a null `assigner` / `review_requester` are all unobserved on this repository's data, and each is handled by refusing rather than guessing.
