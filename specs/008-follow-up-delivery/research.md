## 2. The 2.x surface facts, field-level

1. **`prompt({ text, send? })` semantics are unchanged.** `send: true` sends on the **current** session; a busy current session answers `SESSION_BUSY`; composing into the chat box while busy still works. **No guest-reachable queue or steer exists** — the host's composer queue is UI-only, so there is no host-side mechanism a follow-up could hand its message to and walk away from. This closes the pm-handoff's "prefer host queue/steer if guest-reachable" branch: verified *not* guest-reachable.
2. **`openSession(sessionId)` is still a navigation** — the docs' own words, "explicitly opens the chat and closes the page." Because `prompt` only addresses the current session, addressing a session the operator is not viewing still requires this navigation.
3. **`onSessionLifecycle` is 2.x's host push** — session status `busy` / `retry` → phase `started`; `idle` → `completed`; `unknown` → `failure`. A late-subscribing listener receives the **last event** the bridge saw — and per §2.5 that last event is *current-session-scoped*, which is the load-bearing correction of round 2.
4. **Error codes are unchanged**: `NO_SESSION`, `SESSION_BUSY`, `HOST_UNAVAILABLE`, `HOST_TIMEOUT`, `HOST_REJECTED`, `DISABLED`, `NOT_GRANTED`, etc. remain as 002's §R13.2 recorded them. The amendment changes which of them the *ladder* treats as retryable (transient host errors only), not the code set.
5. **The lifecycle event carries an id — but is emitted only for the pane's current session** (PM-verified, `openchamber/openchamber@main`, read 2026-10-13):
   - `packages/sdk/src/contract.ts`: `SessionLifecycleEvent = { sessionId: string, phase: 'started'|'completed'|'failure' }` — the wire shape has the id, so nothing about the *event* forbids addressing a non-current session.
   - `packages/ui/src/components/layout/PluginPane.tsx:180-186`: the pane derives `currentSessionId` from `useSessionUIStore(state => state.currentSessionId)` and `sessionStatus` from that **same id** — there is no other session's status in the component's scope.
   - `PluginPane.tsx:948-956`: the post effect (deps `[currentSessionId, lifecyclePhase, postToGuest]`) posts `buildSessionLifecycleMessage({ sessionId: currentSessionId, … })` **and nothing else** — no other session's phase is ever posted.
   - `packages/sdk/src/host.ts`: the bridge's replay (`lastLifecycle`) keeps only its **last current-session event** — a late subscriber replays the last *current* session's phase, not a watched session's.
   - **Conclusion**: a **non-current target session's busy/idle state is unknowable to a guest.** `ready.session.busy` and `onSession` are current-scoped too (002 §R13.3), so they add no cross-session channel. The only ways to learn a non-current session's state are (a) wait for the operator to open it, or (b) navigate there — which is exactly the implementable option set in [spec.md](spec.md) §1 (B+ and A′).

## 4. What the amendment still cannot establish (kept plainly, as §R13 did)

- **How long the panel survives after the navigation** remains undocumented, and nothing guarantees `prompt`'s promise resolves before the frame unmounts. Relevant only under A′; the failure direction is unchanged — intent recorded before the call, at-most-once record after it, a lost result is an operator-resolved question, never an automatic re-send.
- **Under B+, a follow-up whose session the operator never opens is never delivered automatically.** This is the accepted cost of the **mandated** option (product owner, 2026-10-13) — bounded by visibility only (FR-036's waiting queue, the run row's waiting state), not by time. A time bound or a fallback navigation would be a **new** product-owner decision; A′ is the recorded, rejected alternative (spec.md §1, §5).
