## 1. The decision-ready option set: delivering to a session the operator is not viewing

`host.prompt({ text, send: true })` addresses **only the current session**, and the panel can observe the busy/idle state of **only the current session** (research.md §1 — the lifecycle push is current-scoped by construction). A follow-up for a session that is not the one on screen therefore cannot be *observed ready* without either waiting for the operator to open it or navigating the operator to it. The three recorded decisions fix what is forbidden (attempts while busy, navigation storms); this section lays out the two implementable readings. Both keep all three decisions. Both share the same retry-ladder shrink (§2.2), the same waiting-state vocabulary (`session-busy`, amended), and the same migration clause (§2.2).

### Option B+ — park + auto-rearm (**mandated** — product owner, 2026-10-13)

A follow-up whose target is not the current session **parks silently**: no navigation, no prompt, no toast, no consumed retry budget. The panel already learns the current session from `onSession` / `ready.session`; the moment the **operator opens the target session** and its lifecycle push reports it **idle**, the parked follow-up **re-arms by itself** and delivers exactly once under the at-most-once record. Autonomy (decision 1) is preserved at the first instant delivery is possible without a view-yank. **No new UI affordance of any kind** — the waiting state rides the existing reason vocabulary on the run row.

- **Cost, stated plainly**: delivery timing follows the operator — a follow-up for a session the operator never opens is never delivered automatically; it stays parked and visible. The yank is eliminated entirely, which is the strongest reading of "navigation must stop being a storm."

### Option A′ — navigate-once (recorded, rejected alternative — kept here with its cost, per the product owner's 2026-10-13 decision on B+)

For a non-current target, navigate **once** with `host.openSession(sessionId)` to make the target observable — then wait for the target's idle push *while it is the current session* — then prompt. Decision-complete, it works like this: the intent to navigate is recorded durably before the call; the navigation is withheld while the **current** session is observed busy (the one busy state the panel can know); once the target is current, the panel waits for its `onSessionLifecycle` idle push and then prompts under **the same every-prompt re-verification** FR-104 states — the target must still be current immediately before the prompt, or the follow-up returns to waiting — and under the same at-most-once record, in the same detection order. One view-switch per delivery, no toasts, no loops, and no re-navigation on retry. This is the honest shape of "navigate-once-at-idle": **the navigation cannot be timed on the target's idle state, because that state is unknowable before the navigation** — so A′ navigates to learn, and waits after.

- **Cost, stated plainly**: the single yank is real and its timing is not target-gated (research.md §4 — the panel may not even survive the navigation, so a navigation whose prompt never lands leaves the record **due**, never duplicated). It is a decided cost offered for approval, not a recommendation.

**Decision (product owner, 2026-10-13): B+ is the mandated delivery semantics.** Rationale as recorded: *"zero view-switches; autonomy preserved at the first moment delivery is possible without a yank."* The costs below remain on the record as the reason the choice went this way: the view-yank is the defect issue #48 was filed against, and A′ cannot schedule its one yank on any observable fact — a cost without a mitigation. B+ delivers autonomously the moment delivery is *possible* without harm, and its only loss — a follow-up waiting until the operator opens the session — is already the panel's honest posture (FR-036: waiting is reported as waiting, never as delivered).

## 2. Proposed in-place rewrites of 002's requirements (old → new)

The body below is written for the **mandated B+** (product owner, 2026-10-13) and contains **no marked in-body variant** — the whole surviving text is B+ text. A′ is the recorded, rejected alternative (§1); **if the product owner ever reopens that decision**, it is applied **at conforming-edit time as one rewrite**: the waiting-state delivery mechanics of FR-104, and the matching AC-050 assertions, are replaced with §1's A′ description — one decision, then one rewrite, with no marked paragraph left in the body to misapply.

### 2.1 `FR-104` — one paragraph replaced, remainder byte-identical

**Old (002 v1.17.0, spec.md:468 — the navigation portion; the replacement span ends here, and everything after it stands byte-identical):**

> When the target session is not the current one, delivery requires `host.openSession(sessionId)`, which switches the operator's view to the session and closes the panel — a user-visible side effect this product performs and MUST own, in three clauses: **no navigation when the target is already current**; the **intent to navigate recorded durably before the call**, so the operator's next view of any surface can explain why their view moved (constitution IV); and **no delivery while a dispatch attempt is in flight** — the relay's existing serialization, extended.

**New:**

> Delivery is gated on the current session and its lifecycle — the only session state a guest can observe. **A follow-up whose target session is not the current session MUST NOT be navigated to, prompted, retried, or toasted against**: the panel performs no `host.openSession` and no `host.prompt({ text, send: true })` for it, consumes no retry budget, and parks nothing — the follow-up enters the **waiting state** in the existing vocabulary (`session-busy`), visible on the run row and in FR-036's queue, and **re-arms by itself** the moment `onSession` (or `ready.session`) reports the target as the current session and `onSessionLifecycle` reports it **idle**. **The prompt is never issued on a stale observation**: immediately before **every** prompt — the first attempt, a re-armed attempt, and a retry alike — the panel MUST re-verify that the target session is still the current one, a rule stated once here (FR-105 names the retry path's outcome). On the waiting/re-armed path a mismatch means **no prompt, no navigation, no budget consumed, nothing parked**: the follow-up returns to the waiting state and re-arms again at the next current-and-idle observation, delivering exactly once under the at-most-once record. Re-armed follow-ups deliver in **detection order** — FIFO through the run's follow-up window order (FR-104's window) under the relay's existing serialization. This is the whole cross-session mechanism, and it exists in this shape because **a non-current session's busy or idle state is unknowable to the panel**: `onSessionLifecycle`, `ready.session.busy`, and `onSession` are all current-scoped by construction (`research.md` §1), so no clause of this amendment may wait on — or act against — a state the host never publishes. When the target **is** the current session and observed idle, delivery is one `host.prompt({ text, send: true })` with **zero navigation**. **No delivery happens while a dispatch attempt is in flight** — the relay's existing serialization, extended.

*(FR-104's remainder — composition bounds, the measure-before-call guard, and the FR-027 authorization clause — stands byte-identical to v1.17.0.)*

### 2.2 `FR-105` — full rewrite of the requirement's text

**Old (002 v1.17.0, spec.md:470):**

> **Failures retry within the bound, then park with a human-visible reason.** A delivery attempt that fails — the session is mid-turn, `NO_SESSION`, a rejected `openSession`, a host timeout or rejection, or an over-budget composition — MUST be retried under the bounded backoff the existing retry configuration already declares, and MUST NOT wait indefinitely for the session to become free (constitution VII: the host owns session scheduling, and an unbounded wait is Mecha Turk reimplementing the harness's own queue). **Every cause in that list has a writer, and the closed union carries no other word**: the host's `DISABLED` refusal (a paused extension) is **not** a cause of its own — it parks as a host refusal, because "the host refused or timed out the prompt" is what an operator can act on. **A closed panel is not a failure at all and parks nothing**: a mount that goes away mid-attempt fails the in-flight call like any other host refusal, and a mount that goes away between attempts leaves the record **due** — the durable record carries the attempt count and the next-attempt stamp, so the remount **resumes the ladder** (User Story 7's third scenario) rather than parking on a mount nobody can see. A "panel closed" park would be the one failure this panel could never recover from, and the reason word it would ride has no producer. On exhaustion the follow-up is **parked** — FR-037's dead-letter posture — with a reason naming the exact cause, visible on the run row and in the trail, excluded from automatic handling, and returning to waiting only through an **operator-initiated** re-offer under the same duplicate protection. **No new state name is minted**: the park reuses the existing dead-letter vocabulary and its reason words, and because the run document admits a session-carrying run in the `dispatched` state only (`research.md` §R14.2), the reason rides beside the run's session rather than in its state.

**New:**

> **Only a transient host error retries; every other stop parks with its human-visible reason.** The bounded backoff ladder — the retry configuration the existing knobs already declare — applies to exactly one class of failure: a **transient host error** (`HOST_UNAVAILABLE`, `HOST_TIMEOUT`, `HOST_REJECTED`, or a transport failure — the shipped `host-unavailable` reason). **A retry is subject to FR-104's pre-prompt re-verification — stated once there, not restated here**: immediately before prompting, the target session must still be the current one, and on mismatch the delivery stops with `navigation-refused` and **no prompt is issued** — under the one-navigation rule no second navigation is attempted. `navigation-refused` therefore covers two situations with one existing word: a navigation that could not be (re)issued under the one-navigation rule, and a retry that found the target no longer current. A retried delivery **MUST NOT navigate again**: under B+ no navigation exists at all; under A′ a navigation that already happened made the target the current session, and a retry prompts only. **A busy session is not a failure and is not a retryable class**: under B+ no attempt ever targets a non-current session and none is made while the current session is observed busy; a **raced** `SESSION_BUSY` — the session observed idle, then busy before the prompt landed — is an **observed-busy outcome, not a failure**: the delivery enters the waiting state, consumes no ladder budget, and is **never** parked for it. The waiting state is a wait with no host call behind it, which is the opposite of an unbounded wait reimplementing the harness's queue (constitution VII): the panel holds no queued send — the message is composed at attempt time under FR-104's measure-before-call clause — and schedules nothing; it reacts to the host's own current-session signals and attempts once. **Every other stop is terminal at once, with its reason word and no retry**: `NO_SESSION` parks as `no-session`; a refused or unissuable navigation parks as `navigation-refused`; an over-budget composition is refused before any host call and parks as `over-budget`. **Every cause named here has a writer, and the closed union of reason words carries no other word** — `no-session`, `session-busy`, `navigation-refused`, `over-budget`, `host-unavailable` — where `session-busy` is the FR-104 **waiting state** rather than an attempt failure (the shipped doc comment that calls it "a retryable refusal, never a queue" — `src/dispatch-record.ts:78` — is corrected by this amendment); the host's `DISABLED` refusal (a paused extension) is **not** a cause of its own — it parks as a host refusal, because "the host refused or timed out the prompt" is what an operator can act on. **A closed panel is not a failure at all and parks nothing**: a mount that goes away mid-attempt fails the in-flight call like any other host refusal, and a mount that goes away between attempts leaves the record **due** — the durable record carries the attempt count and the next-attempt stamp, so the remount **resumes the ladder** (User Story 7's third scenario) rather than parking on a mount nobody can see. A "panel closed" park would be the one failure this panel could never recover from, and the reason word it would ride has no producer. On ladder exhaustion the follow-up is **parked** — FR-037's dead-letter posture — with a reason naming the exact cause, visible on the run row and in the trail, excluded from automatic handling, and returning to waiting only through an **operator-initiated** re-offer under the same duplicate protection. **No new state name is minted**: the park reuses the existing dead-letter vocabulary and its reason words, and because the run document admits a session-carrying run in the `dispatched` state only (`research.md` §R14.2), the reason rides beside the run's session rather than in its state. **Migration, re-derivable from the existing record alone**: a pre-amendment record carrying `parked: true` with reason `session-busy` was a **refused attempt, not delivered work** — on the next read the panel re-arms it into the waiting state and it proceeds under the rules above — **with its recorded attempt history intact**, matching the shipped re-offer posture (`site/src/pages/use.astro:156-157`: a re-offer clears the park "never the … attempt history", and "the next relay poll gives it one more attempt, which parks it again at once if it fails"), so a re-armed record that hits a transient host error and exhausts the remaining ladder parks at once — that instant re-park is **by design, not a defect**; both facts (`parked`, `reason`) already exist on the record, so this migration adds no persisted field, no state name, and no store.

### 2.3 `AC-050` — the navigation and busy assertions (old → new spans)

**Old span (002 v1.17.0, spec.md:616):**

> Given the target session already current, delivery prompts with **zero** `openSession` calls. Given a different current session, the intent to navigate is durably recorded **before** the `openSession` call the fake host logs, and no delivery happens while a dispatch attempt is in flight.

**New span (B+ body):**

> Given the target session already current and observed idle, delivery prompts with **zero** `openSession` calls. Given a different current session, the fake host's log shows **zero** `openSession` calls and **zero** prompt calls, the follow-up carries the `session-busy` waiting state on the run row, and the record stays **due**; when the operator then opens the target session — `onSession` reports it current — and its lifecycle reports idle, the same delivery is prompted **exactly once**, into the run's own session, and the at-most-once record is written. **Re-arm race (FR-104's pre-prompt re-verification)**: given a re-arm observation — target current and idle — with the operator switching to a **different idle session** before the prompt fires (including when the relay's serialization deferral pushed the attempt to the next tick), the fake host's log shows **zero prompts into the non-target session**, no budget is consumed and nothing is parked, the follow-up is back in the `session-busy` waiting state, and it is delivered **exactly once** when the target is again the current session and observed idle. **Retry re-verification**: given a transient host error whose retry fires after the operator has switched to another session, the retry logs **zero prompts into the non-target session**, issues no second navigation, and the delivery stops with `navigation-refused`. **Raced busy**: given a prompt refused `SESSION_BUSY` after an idle observation, the log shows **no further prompt attempts**, **no** ladder attempt is consumed, and nothing is parked — the waiting state carries the follow-up and the next idle signal delivers it exactly once. **No delivery happens while a dispatch attempt is in flight** in any of these paths.

The remainder of AC-050 (FR-027's untouched reading, the `followUpsFrom` window assertions, the measure-never-truncate guard) stands byte-identical.

### 2.4 `AC-051` — the retry-shrink assertions (old → new spans)

**Old span (002 v1.17.0, spec.md:617):**

> Given the session mid-turn, `NO_SESSION`, a rejected `openSession`, a host timeout or rejection, and an over-budget composition — each retries within the declared bound and, on exhaustion, parks with its reason, visible on the run row and in the trail, with **no** unbounded wait in any case (a paused extension is not a class of its own: the host's `DISABLED` refusal parks as `host-unavailable`).

**New span:**

> Given a host timeout, rejection, or unavailability — each retries within the declared bound and, on exhaustion, parks with its reason, visible on the run row and in the trail; each retry re-verifies that the target is still the current session and, on mismatch, stops with `navigation-refused` and **zero** prompts; under A′ a retry after a successful navigation issues **no** second `openSession`. Given `NO_SESSION`, a refused navigation, and an over-budget composition — each parks **on the first refusal** with its reason word (`no-session`, `navigation-refused`, `over-budget`) and consumes **no** ladder attempt. Given the session mid-turn — **no attempt at all**: zero prompts, zero navigations, no toast, no ladder consumption; the waiting state carries the follow-up and the current-session idle signal re-arms it for exactly one prompt, and it is **never** parked for a busy outcome. Given a `SESSION_BUSY` refusal racing an idle observation — the refusal exists only because a prompt was issued, and **no prompt follows it**: the raced refusal consumed no ladder attempt, nothing is parked, and the waiting state carries the follow-up until the current-session idle signal re-arms it for exactly one further prompt (a paused extension is not a class of its own: the host's `DISABLED` refusal parks as `host-unavailable`).

The re-offer assertions of AC-051 stand byte-identical.

## 5. Closed decisions (product owner, 2026-10-13, via PM)

1. **Q1 — NFR-001's clock for the follow-up's queued → delivered leg: DECIDED.** The clock **arms at follow-up detection**; intervals in which the target session is observed busy are **excluded from the measured window**. Rationale (the product owner's recorded choice): *"keeps the bar honest about panel-caused delay without penalizing the host's schedule."* Written into the normative companion at §3.5; the waiting duration stays human-visible through the existing reason vocabulary, with no new persisted state.
2. **Q2 — A′ vs B+: DECIDED.
