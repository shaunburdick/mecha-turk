## 1. The decision, stated once

Today's approved delivery (002 v1.18.0, shipped from 008) is panel-only: the panel hands the composed message to `host.prompt({ text, send: true })` when it can observe the target as the current session and idle, and parks in the `session-busy` waiting state otherwise. The product owner has ruled (2026-10-14): that is **not the delivery to ship**. The primary path is the **always-on service talking to OpenCode's own API** with `delivery: "queue"` — autonomous, panel not required, zero navigation, zero operator action. B+ is kept, unmodified in its mechanics, as the **degraded mode** the product falls back to exactly when the engine path cannot make the attempt.

This is also the strongest available reading of constitution VII: Mecha Turk runs **no queue of its own** — the message is handed to the **harness's own engine queue**, which owns promotion on turn end. The 008-era worry (a guest-side queue-until-free against the host's scheduler) dissolves rather than weakens: there is no Mecha Turk-held pending send on either path (the service persists a **receipt**, not a buffered message; the fallback composes at attempt time as v1.18.0 requires). This reading is **owner-confirmed** (§7 Q5).

The flip procedure 008 established is retained: the body below contains **no marked in-body variant** — it is written unconditionally for engine-primary with B+ fallback. If the product owner ever reopens the demotion, it is applied at conforming-edit time as one rewrite, never by editing marked paragraphs.

## 2. Proposed in-place rewrites of 002's requirements (old → new)

All `Old` quotes are byte-exact against 002 **v1.18.0** (verified by script against `specs/002-agent-event-extension/spec.md`, and against the named target file for §3's out-of-002 companions, on 2026-10-14).

### 2.1 `FR-104` — four spans replaced, remainder byte-identical

**Old span A (the headline and the service-addressing bar):**

> **FR-104**: **Delivery goes into the original session, through the host, by the panel only.** A follow-up MUST be delivered by `host.prompt({ text, send: true })` into the session the run's dispatch created. The service MUST NOT address a session — it holds no host bridge — and the panel is the only party that calls the host. A follow-up MUST NOT start a session, MUST NOT create or join another run, and MUST NOT be delivered into any other session.

**New span A:**

> **FR-104**: **Delivery goes into the original session — by the service, through the engine's own API, when the engine path is available; by the panel, through the host, as the fallback when it is not.** On the engine path the service composes the follow-up message under FR-028's bounds, delimiters, untrusted-source preamble, and the run's correlation id — measured before any engine call, refused rather than truncated, exactly as the panel's composition is — and delivers it with **`POST /api/session/{sessionId}/prompt`**, body `{"text": …, "delivery": "queue"}` — flat top-level fields (research.md §2.1's three-source agreement; the fake 400s the nested shape) — where `sessionId` is the session the run's dispatch created (research.md §2). **The service addresses a session only through that one call, only to an id the run's dispatch already created** — never creating, joining, or deleting a session (AGENTS.md invariant 10); the engine's `404` is `NO_SESSION` and parks under FR-105. **Every engine send is preceded by an ownership pre-check** — `GET /api/session/{id}`, requiring the session's `location.directory` to match **the dispatch-reported session directory** — the directory the panel already records from `host.startSession()`'s result, selected by one unambiguous rule: **`worktree.directory` when the result carries one, else `result.directory`** — the value the host reports as the session's own directory, which for a `worktreeOption: 'none'` dispatch is the run's checkout directory — which the dispatch result carries to the service as **one new additive member, `directory` (string)**, and its `metadata.openchamber` to be present (the engine-side fields were observed live on an OpenChamber-managed session — research.md §2; the precise directory-match rule is fixed at plan time beside the version pin) — which refuses a session the engine says is not this run's and marks the delivery `engine-unavailable` (FR-105) rather than risking misdelivery across a shared data directory. **`steer` is never used for a follow-up**: it injects into the running turn, which is neither delivery-into-the-session nor the autonomy a queued admission gives (research.md §2) — `queue` is the only follow-up delivery mode. On the fallback path the panel is the only party that calls the host, exactly as v1.18.0 states. A follow-up MUST NOT start a session, MUST NOT create or join another run, and MUST NOT be delivered into any other session.

**Old span B (the window's structural rationale):**

> **The window is of the queue, not of the undelivered set, and that is structural rather than chosen**: the service holds no record of a delivery — the panel is the only party that calls the host and its durable record lives in host storage — so a delivered follow-up row is never pruned service-side, the projection cannot skip one, and the panel is what filters what it has already delivered against its own record.

**New span B:**

> **The window is of the queue, not of the undelivered set — unchanged at v1.19.0, with its rationale corrected**: the service now records **its own** engine-path deliveries (FR-105), but a **fallback** delivery's outcome still lives only in the panel's durable record in host storage, so a delivered follow-up row is still never pruned service-side on that path, the projection cannot skip one, and **each caller filters against the record it holds** — the service against its own engine records, the panel against its own record. **The service never prunes its queue rows on any path** — engine-admitted rows stay in the projection, carrying their state, which is what lets the panel advance the window honestly (span B2). No caller may filter with a record it cannot read.

**Old span B2 (the window's advance clause):**

> **Absence projects from the start exactly as it does today**, so every caller that omits the parameter — including every caller written before it existed — reads what it always read; the panel, which holds the durable record of what it has delivered, is the party that advances it, and advancing it past a delivered id is what puts the movements behind them back in range.

**New span B2:**

> **Absence projects from the start exactly as it does today**, so every caller that omits the parameter — including every caller written before it existed — reads what it always read; the panel, which holds the durable record of what it has delivered **and reads the projected engine state of what the engine holds**, is the party that advances it, and it advances past a delivered id — panel-delivered per its own record, or engine-admitted per the projection — which is what puts the movements behind them back in range; **a row projected `unavailable` or `unknown` is never advanced past by projection alone**, because neither means the movement was handled.

**Old span C (the whole cross-session gate, v1.18.0's B+ mechanism):**

> Delivery is gated on the current session and its lifecycle — the only session state a guest can observe. **A follow-up whose target session is not the current session MUST NOT be navigated to, prompted, retried, or toasted against**: the panel performs no `host.openSession` and no `host.prompt({ text, send: true })` for it, consumes no retry budget, and parks nothing — the follow-up enters the **waiting state** in the existing vocabulary (`session-busy`), visible on the run row and in FR-036's queue, and **re-arms by itself** the moment `onSession` (or `ready.session`) reports the target as the current session and `onSessionLifecycle` reports it **idle**. **The prompt is never issued on a stale observation**: immediately before **every** prompt — the first attempt, a re-armed attempt, and a retry alike — the panel MUST re-verify that the target session is still the current one, a rule stated once here (FR-105 names the retry path's outcome). On the waiting/re-armed path a mismatch means **no prompt, no navigation, no budget consumed, nothing parked**: the follow-up returns to the waiting state and re-arms again at the next current-and-idle observation, delivering exactly once under the at-most-once record. Re-armed follow-ups deliver in **detection order** — FIFO through the run's follow-up window order (FR-104's window) under the relay's existing serialization. This is the whole cross-session mechanism, and it exists in this shape because **a non-current session's busy or idle state is unknowable to the panel**: `onSessionLifecycle`, `ready.session.busy`, and `onSession` are all current-scoped by construction (`research.md` §1), so no clause of this amendment may wait on — or act against — a state the host never publishes. When the target **is** the current session and observed idle, delivery is one `host.prompt({ text, send: true })` with **zero navigation**. **No delivery happens while a dispatch attempt is in flight** — the relay's existing serialization, extended.

**New span C:**

> **Engine admission is the delivery act, and nothing waits for the engine to be idle.** The engine's own queue holds an admitted follow-up and promotes it when the session's turn ends — verified live end-to-end ([research.md](research.md) §2) — so the service sends at detection time **regardless of the session's current state**: one ownership pre-check (span A), one admission POST, and the admission's message `id` (`msg_…`) is recorded as the **at-most-once receipt** under FR-105's intent-before-send rule. **Admission is delivery**: once the receipt exists the service stops; an execution outcome the engine later reports is observability prose ([research.md](research.md) §2) and never a precondition, a gate, or a second delivery step. **The fallback gate is the service's, and only the service can fire it** — the service is the party that observes connection, token, ownership, and version failures; the panel observes none of them and knows nothing until it reads the projected row. A delivery the service marks **`engine-unavailable`** (the causes FR-105 names) is projected to the panel as an **absentable member on the follow-up row of the read the panel already performs** — additive within `/v1`, in the shape `followUpsFrom` established — and **from that mark the service never engine-attempts that delivery again** (permanent handoff; §5 shows how at-most-once survives two records with one writer each). The projected member's states are **`queued`** — engine-admitted, and **admission counts as reached**: the message is in the session's own engine queue, so no surface may show it as waiting-to-be-delivered or queued-forever; `queued` renders on the run row as the reason word `engine-queued` (§4, FR-105 span F) — **`unavailable`** — the only state the panel may auto-attempt — and **`unknown`** — displayed, and **never auto-attempted** (FR-105 span E). **The panel attempts a follow-up only when the projected member positively says `engine-unavailable`**: a member **absent** (a pre-amendment service) means today's v1.18.0 behaviour unchanged, and a member the panel **cannot read** (service down) means **no attempt at all** — a blind fallback could duplicate an admission the panel cannot see, and the failure direction is a missing follow-up the operator confirms, never a duplicate. **One exception exists, and it is not automatic**: an operator's **re-offer of an `unknown` row** (FR-105 span E) is the sole panel attempt that requires no positive `unavailable` mark — it is operator-initiated, offered only on the eligible rows companion 9 defines, and delivered by the same fallback prompt under the same every-prompt re-verification; auto-attempts remain barred on `unknown`. On the fallback path, v1.18.0's mechanism stands in full, scoped here: a follow-up whose target session is not the current session MUST NOT be navigated to, prompted, retried, or toasted against: the panel performs no `host.openSession` and no `host.prompt({ text, send: true })` for it, consumes no retry budget, and parks nothing — the follow-up enters the **waiting state** in the existing vocabulary (`session-busy`), visible on the run row and in FR-036's queue, and **re-arms by itself** the moment `onSession` (or `ready.session`) reports the target as the current session and `onSessionLifecycle` reports it **idle**. **The prompt is never issued on a stale observation**: immediately before **every** prompt — the first attempt, a re-armed attempt, and a retry alike — the panel MUST re-verify that the target session is still the current one, a rule stated once here (FR-105 names the retry path's outcome). On the waiting/re-armed path a mismatch means **no prompt, no navigation, no budget consumed, nothing parked**: the follow-up returns to the waiting state and re-arms again at the next current-and-idle observation, delivering exactly once under the at-most-once record. Re-armed follow-ups deliver in **detection order** — FIFO through the run's follow-up window order (FR-104's window) under the relay's existing serialization. This is the fallback's whole cross-session mechanism; the premise it was originally written against is corrected at v1.19.0, and the correction lives in [research.md](research.md) §3 and the changelog — it changes nothing in this span. When the target **is** the current session and observed idle, fallback delivery is one `host.prompt({ text, send: true })` with **zero navigation**. **No fallback delivery happens while a dispatch attempt is in flight** — the relay's existing serialization, extended.

*(FR-104's remainder — the composition bounds and measure-before-call guard, and the FR-027 authorization clause — stands byte-identical to v1.18.0; the window's mechanics stand except the advance clause, which is span B2 above.)*

### 2.2 `FR-105` — three spans replaced; the reason-word union gains one member (product-owner decision)

**Old span D (the retry-class opening):**

> **Only a transient host error retries; every other stop parks with its human-visible reason.** The bounded backoff ladder — the retry configuration the existing knobs already declare — applies to exactly one class of failure: a **transient host error** (`HOST_UNAVAILABLE`, `HOST_TIMEOUT`, `HOST_REJECTED`, or a transport failure — the shipped `host-unavailable` reason).

**New span D:**

> **On the fallback path only a transient host error retries — the v1.18.0 class, verbatim — and on the engine path only a failure that proves non-delivery retries; every other stop parks, falls back, or waits with its human-visible cause.** The bounded backoff ladder — the retry configuration the existing knobs already declare — applies to the **transient host error** class exactly as v1.18.0 states (`HOST_UNAVAILABLE`, `HOST_TIMEOUT`, `HOST_REJECTED`, or a transport failure — the shipped `host-unavailable` reason), and, on the engine path, to exactly one engine class — a **connection refused**, the only loopback failure that unambiguously proves the request never reached the engine — under the same ladder and the same bound. **A timeout or a 5xx from the engine is not retryable**: over loopback it does not prove non-delivery — the admission may have landed — so it enters the **unknown** state (span E) at once and is never auto-retried. **Non-transient engine-path failures neither retry nor park: they mark the delivery `engine-unavailable` and hand it to the fallback at once** — discovery failure (no registry file for a live pid), a pid cross-check mismatch (`/api/info`'s `pid` disagreeing with the registry file's), a `401`, an engine version outside the pinned `/api/info` range (the adapter fails safe — never a hard stop), a failed ownership pre-check, and any token-acquisition failure in the layered chain (env `OPENCODE_SERVER_PASSWORD`, then registry + `/proc/<pid>/environ` with pid-alive and ownerPid verification). **Ladder exhaustion on the engine path also marks `engine-unavailable` rather than parking**: engine-caused unavailability is precisely the condition the fallback exists for, so no follow-up is ever parked for it.

**Old span E (the terminal-stop list):**

> **Every other stop is terminal at once, with its reason word and no retry**: `NO_SESSION` parks as `no-session`; a refused or unissuable navigation parks as `navigation-refused`; an over-budget composition is refused before any host call and parks as `over-budget`.

**New span E:**

> **Every other stop is terminal at once, with its reason word and no retry**: a `NO_SESSION` — panel-side, or the engine's `404` for the run's session — parks as `no-session` on the first refusal; a refused or unissuable navigation parks as `navigation-refused`; an over-budget composition is refused before any engine or host call and parks as `over-budget`. **An unknown outcome is never auto-retried and never auto-resent**: the service persists send-intent **before** the admission POST and the receipt — the admission's message `id` — after it; a timeout, a 5xx, or a crash or restart between intent and receipt leaves the delivery's outcome unknown — the request may have been admitted — and the delivery enters the **`unknown` store state** (cause and intent stamp persisted, no receipt) projected as `unknown`: the panel **displays** it and **never auto-attempts** it. **Restart reconciliation**: a service restart over an intent-without-receipt leaves the row `unknown` — zero automatic re-POSTs, ever — operator-visible until resolved. **The one reachable resolution is the operator's re-offer, and its channel is the panel's fallback `host.prompt`** — the same host path the fallback already uses, zero engine POSTs, no new route — with the operator accepting, on the record, the possible duplicate that an unknown outcome implies (a missing follow-up the operator confirms, never an automatic duplicate). **Admission is delivery; execution is observation**: a `session.execution.failed`, or a session that after admission waits for a permission or a form, is **not** a delivery failure and never re-sends — it is visible waiting, and **nothing is ever auto-approved** (constitution II). **A paused extension/engine pair is not a class of its own** on either path — the existing `DISABLED`/host-refusal treatment stands. **The reason-word union gains exactly one member, by product-owner decision (2026-10-14), and it is a waiting state rather than a failure — the `session-busy` precedent applied again**: `engine-queued` — the follow-up was admitted engine-side and is engine-held until the engine promotes it; it is **never parked by that word**, and the panel never auto-attempts it (FR-104 span C). Engine-path stops otherwise land in existing words — `404` → `no-session`, over-budget → `over-budget`, transient exhaustion on the fallback path → `host-unavailable` — and **`unknown` keeps its rendered *unconfirmed* note and is deliberately not a seventh word** (product-owner interpretation, recorded §7). The six words are `no-session`, `session-busy`, `navigation-refused`, `over-budget`, `host-unavailable`, `engine-queued` — the first five exactly as v1.18.0 left them (`session-busy` still the fallback's waiting state rather than an attempt failure), the sixth the engine path's.

**Old span F (the union sentence, inside FR-105's body):**

> **Every cause named here has a writer, and the closed union of reason words carries no other word** — `no-session`, `session-busy`, `navigation-refused`, `over-budget`, `host-unavailable` — where `session-busy` is the FR-104 **waiting state** rather than an attempt failure (the shipped doc comment that calls it "a retryable refusal, never a queue" — `src/dispatch-record.ts:78` — is corrected by this amendment)

**New span F:**

> **Every cause named here has a writer, and the closed union of reason words carries no other word** — `no-session`, `session-busy`, `navigation-refused`, `over-budget`, `host-unavailable`, `engine-queued` — where `session-busy` is the FR-104 **waiting state** rather than an attempt failure (the shipped doc comment that calls it "a retryable refusal, never a queue" — `src/dispatch-record.ts:78` — is corrected by this amendment), and `engine-queued` (added at v1.19.0 by product-owner decision) is the **waiting state for an engine admission**, in the same precedent: the follow-up was admitted engine-side and is engine-held until the engine promotes it — never a park, never a panel auto-attempt, and nothing is ever re-sent for it while the word stands (FR-104, FR-105 as amended)

### 2.4 Data model — the two unavoidable persisted additions, stated (the service's engine-delivery member and the dispatch result's `directory`)

- **Service store (new fields on the follow-up's durable delivery record — the queue row the event already owns; no new file)**: an absentable `engine` member — `{ state: 'admitted' | 'unavailable' | 'unknown', messageId?: string, intentAtMs?: number, cause?: string }` — schema-versioned with the store it rides in. `messageId` is the admission receipt (present iff `admitted`); `intentAtMs` and `cause` carry the unknown state (present iff `unknown`, never a receipt). **This is new persisted state and it is unavoidable**: the service is now a delivery party and at-most-once for its sends must live where its sends live — the panel's record is in host storage the service cannot write. One writer: the service.
- **Projection (new absentable member on `HistoryFollowUp`, the follow-up row of `GET /v1/events`)**: `{ state: 'queued' | 'unavailable' | 'unknown', messageId?: string }` — `queued` = engine-admitted, **admission counts as reached** (the message is in the session's own engine queue; promotion is the engine's schedule); `unavailable` = handed to the fallback; `unknown` = displayed and never auto-attempted. Additive within `/v1` in `followUpsFrom`'s shape: absent, a caller reads exactly what it read before. **The member is retained, and the sixth reason word rides on the row (product-owner decision, 2026-10-14, §7 Q1)**: the member stays because it carries the `unavailable` (handoff) and `unknown` (unconfirmed) distinctness the reason union deliberately does not, while its `queued` branch **renders as the reason word `engine-queued`** in the reason slot (§4) — whose only writer is this service-owned member, so the single-writer rule is untouched and no queued-forever rendering exists (`engine-queued` means reached-and-engine-held, per §4's reconciliation).
- **Panel record (`FollowUpDeliveryRecord`, `mecha-turk:dispatches`)**: **no new field and no engine mirror** — a mirror would create the second writer this design exists to avoid; the panel's read path for engine state is the projection, and its own record stays the sole at-most-once key for panel-path attempts. **One type-level ripple, for vocabulary closure**: the closed `FollowUpFailure` union and its runtime validation list (`src/dispatch-record.ts`) gain `engine-queued`, and the human-readable reason map (`src/dispatches-detail.ts`) gains its label line — **no panel write ever produces the word** (the panel never attempts an `engine-queued` row; `src/follow-up.ts`'s waiting-reason constant remains the fallback's), so the enumeration grows for rendering/type closure while every writer stays where it was. These are named as plan-phase companion tasks (§7 Q1's ripple list).
- **Dispatch result (one new additive member)**: the panel-reported dispatch result — a `/v1` payload that already exists — gains **`directory` (string)**, the dispatch-reported session directory span A pre-checks against (`src/session.ts` already records it from `host.startSession()`'s result; the service persists it on the run's existing record — no new file, no new state name). Additive: a result that omits it, or a caller that ignores it, reads the payload exactly as before.
- **Run-model states, reason words, storage keys, capabilities, configuration fields**: zero additions (invariants 3, 4; FR-107's rewritten guard, §3.10, holds for everything else).

## 5. Two records, one delivery, one writer each — the at-most-once design, stated precisely

The brief's critical concurrency question, answered in full:

1. **The service's durable record** (the follow-up's queue row, §2.4) is the **sole authority** for the engine path. Writer: the service, only. Its write order per delivery is **persist send-intent → POST admission → persist receipt (`messageId`)**; a timeout, a 5xx, or a restart between any two leaves the §2.2 span-E **`unknown`** rule in force — displayed, never auto-attempted, never auto-resent, resolved only by the operator's fallback-prompt re-offer.
2. **The panel's `FollowUpDeliveryRecord`** is the **sole authority** for the fallback path. Writer: the panel, only — unchanged from v1.18.0.
3. **The handoff is a one-way, permanent mark**: `engine-unavailable` on the service row means (a) the service **never engine-attempts that delivery again**, and (b) the panel may fallback-attempt it — and only it. The two parties therefore **never attempt the same delivery**, which is how at-most-once survives with two records: no delivery is ever in both attempt paths, so no reconciliation, no report-back route, and no second writer exist. A panel-delivered fallback follow-up is recorded panel-side only; the service's row stays `unavailable` and is never re-sent engine-side. **This is the deliberate trade**: a re-covered engine does not reclaim handed-off deliveries (Q3, §7, recommended "no reclaim" — a reclaim path without a report-back route is exactly the duplicate risk this design refuses).
4. **Re-arm on both records stays as each path already has it**: fallback re-offer is v1.18.0's panel-local mechanics — and for an `unknown` engine row the re-offer **is** the fallback prompt itself (span E): one `host.prompt`, zero engine POSTs, the accepted duplicate on the record. Engine-side, "re-arm" does not exist — admission is one autonomous act; an un-admitted due follow-up is simply attempted on the next service cycle under the same deterministic-id dedupe (NFR-002 unchanged).
5. **The panel's blind-attempt bar**: the panel attempts only on a positive `unavailable` mark (§2.1, span C) once the projected member is present — a member absent falls to span C's carve-out (v1.18.0 behaviour). Service down → projection unreadable → **no attempt** — the panel shows the existing service-status vocabulary and waits. This is the rule that makes "one record, two writers" un-exercisable rather than merely unlikely.
