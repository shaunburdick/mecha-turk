## 2. The engine API surface, field-level

1. **Admission**: `POST /api/session/{id}/prompt` with body `{"text": …, "delivery": "queue"}` — **flat top-level fields, not nested** (corrected; the nested `{"prompt": {"text": …}}` notation earlier drafts showed traces to a protocol type's field naming, not the wire). **Three sources agree on the flat shape**: the live probe's own logged request (`{"text":…, "delivery":"queue"}` → 200 with `payload.text` echoed — the nested recipe had contradicted its own log), the instance's served `/openapi.json` (top-level `text` required), and OpenCode's own mock (`packages/app/e2e/utils/mock-server.ts` reads flat top-level `text` / `delivery`). The offline fake **400s the nested shape**, so an implementation attempting it fails loudly rather than silently. **Confirmed against a session in `running` state**: HTTP **200**, body `{"data":{"id":"msg_<…>","sessionID":"ses_<…>","time":{"created":…},"type":"user","payload":{…},"delivery":"queue"}}` — **no 409, no rejection for busy**. The receipt of record is the admission's message **`id` (`msg_…`)**; there is **no `admittedSeq` field** in the body (a draft that said so was wrong and is corrected everywhere). The SSE `session.inbox.enqueued` frame carries a monotonic `durable.seq` alongside the id — usable as evidence, never as the key.
2. **End-to-end queue trace** (same probe): the queued input sat at durable seq **49** while the run proceeded; `session.step.ended` at seq **142** with `"finish":"stop"`; `session.inbox.delivered` at seq **143** — only after the step ended; a fresh `session.execution.started` at **144**. The engine's queue **waits its turn and runs it**: admission is durable and promotion is the engine's own scheduling. Nothing in Mecha Turk needs to wait for or time that promotion.
3. **`steer` also returns 200 while busy** (admitted, injected into the running turn) — **prohibited for follow-ups** by this amendment: injecting into a turn in flight is neither delivery-into-the-session nor the autonomy a queued admission gives. `queue` is the mandated and only follow-up delivery mode.
4. **SSE**: `GET /api/event` emits `data:` frames whose JSON `type` field is the event name. Observed vocabulary: `session.inbox.enqueued`, `session.execution.started`, `session.execution.succeeded`, `session.execution.failed` / failure vocabulary, `session.step.ended`. **There is no `session.idle` event** (an earlier draft said so; corrected everywhere). **The stream is global** — all sessions on that server. No normative completion signal of any kind is claimed from this stream; the data-handling duty its globalness would impose on a future consumer is recorded in §5's future-work note.
5. **SSE and the execution events are observability prose ONLY — never a fallback-gate input, never a precondition, never a retry signal** (corrected in round 2; an earlier line here wrongly gave execution events one fallback-gate input — the spec never did, and the spec is right): because admission (§2.1) is the delivery act, the service does not wait for any event before sending, and the fallback gate fires on admission-path failures only (spec.md FR-105 span D's list). `session.execution.succeeded` / `failed` can tell an operator *whether a queued follow-up ran* — research completeness, nothing more. SSE absence degrades nothing normative at all; a status refresh may re-read `GET /api/session/{id}`.
6. **Discovery and identity**: `~/.config/openchamber/managed-opencode/<pid>.json` names the port — **per-boot random, so re-discovered on every attempt cycle**; Basic auth `opencode:$OPENCODE_SERVER_PASSWORD` (401 observed without it); `GET /api/info` → `{version:"2.0.29", pid}` — the `pid` **cross-checks the registry file** (a registry naming a live pid whose `/api/info` answers with a different pid is stale/mismatched → engine-unavailable), and the `version` is the fail-safe pin's input. `OPENCHAMBER_MANAGED_PROCESS_REGISTRY` env override points discovery at an alternate registry path for tests. **The pre-check fields were empirically observed**: `GET /api/session/{id}` on an OpenChamber-managed session returned `location.directory` equal to the session's directory **and** `metadata.openchamber = {…}` (provenance: the 2026-10-14 live probe report, PM-relayed, research track 2) — the ownership pre-check (spec.md FR-104 span A) rests on observed fields, not inference. **The comparison source is an in-tree fact, not a probe fact**: the dispatch-reported session directory — `src/session.ts` records `directory` and `worktreeDirectory` from `host.startSession()`'s result and reports it on the dispatch result (spec.md span A, §2.4).
7. **Client-id replay does not exist (checked; negative)**: a check of the engine's public API surface and route code (2026-10-14, GitHub code search over the engine's public tree) found **no client-supplied idempotency key** on the prompt body and **no engine-side dedupe on a client id** — the response's `id` is engine-generated. Idempotent replay therefore cannot be specified, and Gate 1 round 1's H1 alternative is closed with this negative: the **unknown-state rule** (spec.md FR-105 span E) is the at-most-once guarantee for ambiguous failures (timeout, 5xx, crash-between-intent-and-receipt).
8. **Contract-checking resource**: the instance serves **`/openapi.json`** — available to the adapter's contract tests; the runtime fail-safe remains the `/api/info` version range (fail outside it, never a hard stop).
9. **`DELETE /api/session/{id}` → 204 confirmed** — **tests only** (fixture teardown in the fake/real engine harness). Production paths never create or delete sessions (invariant 10).

## 4. Testability (carried from the reports; re-verifiable in tree)

- **Fake OpenCode via stdlib `node:http`** — the repo's existing fake-service pattern (tests/support fakes) extends: one server exposing `/api/info`, `/api/session/{id}`, `/api/session/{id}/prompt`, `/api/event` (SSE with controllable release signals), `/api/session/active`.
- **Injectable token source** — the layered acquisition (env `OPENCODE_SERVER_PASSWORD` → registry-file + `/proc/<pid>/environ` chain, pid-alive and ownerPid-verified) is a seam; tests inject each layer and each failure.
- **`OPENCHAMBER_MANAGED_PROCESS_REGISTRY`** env override makes discovery point at a fixture registry (stale-pid and mismatch cases become table tests).
- Session fixtures can be created/`DELETE`d against a real engine in the operator-gated live suite only; offline tests never require a live engine (AGENTS.md testing philosophy).

## 5. What this amendment still cannot establish (kept plainly, as 008 §4 did)

- **Engine-side durability across an engine restart** was not probed: whether an admitted-but-unpromoted message survives the engine process itself dying is unverified. The failure direction is the safe one — a lost admission is a **missing follow-up the operator confirms**, never a duplicate; the service's receipt exists but promotion is engine-owned.
- **The supported `/api/info` version floor/ceiling** is an observed single point (`2.0.29`); the pinned range is fixed at plan time against the API surface the adapter actually uses, failing safe outside it. The ownership pre-check's precise **directory-match rule** (exact match vs prefix match against the run's checkout directory) is likewise a plan-phase pin beside it — the fields are observed (§2.6), the comparison rule is not yet exercised against symlinked or nested checkouts.
- **`metadata.openchamber`'s exact member set** was observed only as present (`{…}`) on a managed session; the pre-check requires presence, not particular members, so nothing normative waits on the set — recorded so a future round does not over-read it.
- **Permission/form stalls after admission**: a queued prompt that lands on a session which then waits for a permission or form was reasoned about, not probed; the amendment's stance (visible waiting, never auto-approved — constitution II; AC-050 asserts zero approve/resolve calls) needs no probe to hold.
- **Plan-phase / assumption notes (Gate 1 round-1 lows, recorded per disposition)**: (L1) the engine's `404` → `NO_SESSION` → park mapping is spec-level and confirmed at the live pass, to be re-asserted in the operator-gated live suite; (L2) the NFR-001 fallback-leg ladder bound is verified at plan (reuse of the existing knobs, per 002's follow-up-retry-bound rule); (L3) a v1.18.0-era panel running against a v1.19.0 service is **assumed lockstep-packaged** — AGENTS.md invariants 1–2 ship both committed bundles in one extension, so no cross-version skew matrix is owed; if a skew ever exists, the projection member's absence (pre-amendment behaviour) is the safe default.
- **The worktree field equality is inference, not observation (Gate 2 final check, deferred to the live suite)**: span A asserts the selection rule's worktree half — the engine session's `location.directory` equals the `worktree.directory` the host reported — from field names and API.md, not from a probe (§2.6 saw `location.directory` on one managed session without recording its worktree shape). One operator-gated live-suite assertion at implementation start confirms a worktree dispatch's equality; the failure direction is fail-safe fallback, never misdelivery.
- **Future work (not normative here)**: should any future amendment make the service consume `GET /api/event`, its consumer must filter the global stream (§2.4) to the session ids its own runs dispatched and never record the rest.
