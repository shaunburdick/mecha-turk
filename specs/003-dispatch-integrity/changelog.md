changelog.md

Amendments to this specification follow the same procedure and shape as the project's constitution (`.specify/memory/constitution.md` §Governance) and as 002's own changelog.md: a version bump, a stated rationale, a requirement-by-requirement record, a migration-impact statement, and an approval status. Requirement text in this document is **never rewritten** — not to describe behaviour that was not implemented, and not to absorb a successor feature's requirements. The record of what v1.0.0 specified, and of what was approved on 2026-09-28, is evidence; erasing it would make the next conformance review impossible.

### v1.1.0 — 2026-09-28 (extension amendment; feature 004 adds the per-binding starting prompt)

- **Rationale**: Feature 004's field is a per-binding starting prompt that the operator's agent reads first. The moment it exists, four questions in *this* document acquire an answer they do not currently have, and answering them here rather than only in 004 is what keeps the two documents from being read as independently true. (1) **A retry** must compose the same message it composed the first time, or a run's history stops being a record of what happened. (2) **A correlation read** must be able to say *which* prompt a run used without the audit trail persisting operator text. (3) **The dispatch-lifecycle vocabulary** is this product's answer to "every state change has a reason the operator can read"; a configuration change that silently alters what every future dispatch for a repository will say is exactly the kind of state change that sentence is about. (4) **The run history projection** is what the operator reads to find out what a run was told, and it is the natural place for presence, fingerprint, and length — never the text. None of these four is a change to 003's model. All four are changes to what a run *carries*, and 003 is the document that defines what a run carries.
- **Sequencing decision**: 004 **extends** this document and **supersedes nothing** in it. 003 is also **unimplemented** as of this amendment — it is approved and cleared for Phase 4, and no code has been written against it. So this amendment is a **record amendment, not a conformance correction**: there is no shipped behaviour to invalidate, no gap to defer, and no operator reading a document that describes unimplemented software. The v1.0.0 → v1.1.0 delta is the entire difference between what the planner would otherwise have designed and what 004 now requires, and it is recorded while it is still free to be designed around. The alternative — leaving 003 frozen at v1.0.0 and describing the interaction only in 004 — was rejected because this document's vocabulary table and run-history projection are the canonical lists for this product, and a feature's spec is the wrong home for an addition to a table another document owns.
- **Principles reviewed, unchanged in substance**: Principle III (durable and idempotent work) is the principle the retry requirement serves, and the snapshot that makes a retry byte-identical is its application — the same principle, applied one field further. Principle IV (human-visible auditability) is the principle the vocabulary table exists for, and a fingerprint with no text is the form of that principle the project's secret-containment invariant forces. Principle II (safe autonomy by default) is served by the refusals 004 places on prompt content: the prompt is instruction-shaped input and is bounded, validated, and refused rather than trusted because it is operator-authored. Principle VII (thin orchestration boundary) is satisfied rather than strained: 004 adds no host capability, no new operation on the wire, and no new store. No principle is weakened by this amendment.

### v1.3.0 — 2026-09-28 (record amendment; feature 006 records a decision about the automatic requeue budget)

- **Rationale**: This document's FR-033 requires that "the number of automatic requeues for one run MUST be bounded", its `## Assumptions` records "**Maximum automatic requeues**: 3 … **Confirmed by the product owner 2026-09-28**", and its `## Resolved Gate Questions` entry 3 confirms that value and adds one sentence: "No alternative was recorded at the gate; **the value is operator configuration, so it remains adjustable without a behavioural change.**" Feature 006 is the first feature to make the service configuration operator-editable, so that sentence has to be either honoured or explicitly set aside. Left unexamined it would read as an eleventh field, and adding it would have handed the operator a dial wired to a sweep that does not exist. The decision belongs on the record, and it belongs in 006, which is the document whose scope is the configuration surface — but the reading of *this* document's text is what the decision turns on, so it is indexed here too.
- **The decision, in short**: the requeue budget is **not** added as a configuration field. FR-033 states the bound **behaviourally** — bounded, park, exclude, resolve — and names no field, no bound, no default, no store location, and no consumer. The `3` exists only as a confirmed assumption. Adding a field would **invent** it, and it would be **inert**: its consumer is this document's unimplemented lease-expiry sweep (FR-030 – FR-032), so an operator who set it would see nothing happen. The full reading, the two reasons, and the condition for lifting the decision are in 006 `## Deferred`.
- **Sequencing decision**: this is a **record amendment**, and it is the second in this document. It **supersedes nothing**, amends no requirement, and adds no requirement. It exists so that a future reader of FR-033 does not have to reconstruct this reading from 006 to know that the field was considered and deliberately deferred. Like this document's v1.1.0 for 004, and 005's for 006, there is no deployed state to invalidate and no gap to defer — 003 is unimplemented, so the decision was free to be made and is now free to be overturned.
- **Principles reviewed, unchanged in substance**: Principle IV (human-visible auditability) is served by the decision being written down rather than left implicit — an operator who reads the audit trail for a dead-lettered run will find `attempts consumed` there, and this amendment ensures the reason that number is not yet operator-tunable is on the record next to it. Principle II (safe autonomy by default) is served by declining to add a control with no effect behind it. Principle III (durable and idempotent work) is served by keeping the bound behavioural, where the dispatch state model owns it. Principle VI (specification and verification before implementation) is the reason the deferral has a stated lifting condition rather than an open end. No principle is weakened.
- **Requirements explicitly unchanged by this amendment**: **FR-001 – FR-075 in full**, including FR-030, FR-031, and FR-032 (the lease-expiry sweep, still unimplemented), FR-033 (the bound and the dead-letter park, unchanged), FR-036, FR-041, FR-042, FR-052, FR-053, and FR-062. The whole of `## Dispatch State Model`, `## Correlation Model`, `## Audit Vocabulary`, and `## Architecture Impact` is unchanged. NFR-101 – NFR-112, SC-101 – SC-111, and AC-101 – AC-129 are unchanged. In particular **FR-033 is neither relaxed nor extended**: it already says *bounded*, and this document's `## Audit Vocabulary` already names `run.dead_lettered` with "attempts consumed" as its detail, so nothing here needs rewriting to accommodate the field when the sweep lands.
- **Migration impact**: none, and again the cheapest kind. 003 is unimplemented, so there is no deployed state, no file format, and no stored row to convert. Nothing in the dispatch state machine, the audit trail, or the correlation model changes shape: a `config.changed` row written by 006 mints its own identifier and carries no run reference (this document's FR-052), so a run-filtered audit read excludes it and no dispatch row is affected.

FR-076's gate reads the run's **`actorLogin`** and the binding's **`allowedUsers`**, and compares them. Neither member's *name*, *type*, *validation*, nor *presence* changed — only **which login** the detection stage now puts in `actorLogin` for two of the four kinds. The comparison is identical; its input is correct. So this amendment moves **no decision**: not the gate's location, not the refusal code, not the single row, not the fifth `blocked:` cause, not the value-free `actorPolicy`, not the truncation accounting, not the inherited bot judgement. What it moves is a **rationale clause** and two pieces of **contract prose** that repeated the falsehood to whoever reads them next.

- **Why the gate is untouched, stated so the amendment is auditable rather than asserted.** FR-077's row and FR-079's detail are written in terms of *what shape of thing* was recorded, never *which login it held*: `actorPolicy` is `'open' | 'restricted'` and names no login by design (NFR-113), and `deniedAttributions` carries the **closed union** rather than a claim about its distribution. So a codebase or a document that correctly handles *both* members of a closed union continues to handle them correctly when the producer stops emitting one of them. **This is the property that made the correction cheap**, and it is not an accident — it is what v1.11.0's own NFR-011 bought by insisting the basis be a first-class member rather than a rendering convention: the union was modelled, so a producer could be corrected without the reader changing shape.

- **What does get stronger, and it is the point of the exercise.** Before this amendment the gate compared a **proxy**: an allow-list of `['alice']` on a binding was satisfied by the issue author, so **any third party who could assign an issue or request a review on a pull request authored by `alice` obtained a session** — the risk 002's `orchestration-allow-list.md` §R-2 recorded and this document's v1.8.0 rationale inherited. After it, the gate compares the identity the event recorded as having performed the act, and the membership comparison in `service/bindings-allow-list.ts` finally answers the question it was written to answer. **No requirement of this document changes to achieve that**, which is the strongest available evidence that the gate was specified correctly the first time: the defect was in 002's detection stage, and the separation this project has kept between "what to record" (002), "whether to allow" (003), and "how to say it" (005) is what kept the fix to one document.

It is kept for the same reason 002 keeps the union member: **rows the shipped build already wrote carry it**, and a detail key removed from a reader's vocabulary makes those rows unreadable — here it would refuse the `dispatch.refused` row of a refusal an operator can see the run for, and would take 003's own *"a refusal a reader cannot attribute is not an explainable refusal"* (FR-077) with it. The member is **read**, never **written**, and that asymmetry is the specification.
