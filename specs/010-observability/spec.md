## Constitution Alignment

- **IV — human-visible auditability (the principle this feature serves).** The operator can see what the service is doing *during* the session, on the surface they are already watching, instead of hunting stdout; redaction runs before a line is ever retained, so no secret can appear in the ring, the answer, or the tab (AGENTS.md invariant 9, constitution IV); and FR-006's restart note is what keeps a memory window from ever being mistaken for a record.
- **V — minimal, self-hosted.** One loopback read on the local service, one in-memory buffer, zero new capabilities, zero new infrastructure, no control plane: everything this adds runs inside the operator's own OpenChamber environment.
- **VI — specification and verification before implementation.** This document is written before any code, and every acceptance criterion is checkable offline — against the fake host, a temp-directory service, and the existing visual harness (005 FR-086's floor), with no live instance, real token, or network.
- **Tension named — III (durable and idempotent work).** The ring buffer is deliberately **not** durable: it survives no restart, holds no checkpoint, and is not attributable history. That is accepted by product-owner decision (issue #53) because the durable record remains the audit trail (`GET /v1/audit`'s append-only rows) — the viewer is a watch surface, and FR-006 exists so no operator can read it as one. Nothing here writes to the store, so III's storage rules are untouched rather than weakened.
- **I and VII, in one line each.** I (polling-first, contract-first): this feature adds only outbound polling — the tab polls one versioned loopback read on its own cadence — and nothing pushes; webhooks and every other push mechanism stay a future adapter rather than a dependency, which is exactly what `## Not doing`'s no-push-transport line rests on. VII: the panel and the service stay inside their boundary — the tab is a read of a service route through the host and adds no host capability.

## Problem Statement

The service already writes a structured, redacted JSON line for everything it does — poll cycles, scan decisions, dispatch lifecycle, errors — to stdout, and stdout goes wherever OpenChamber captured it. So when something is happening *right now*, the panel has no answer: the only queryable history is `GET /v1/audit`, the durable decision record, which is a different question ("why was this decided?") from the one an operator watching a stuck scan asks ("what is it doing this minute?"). The gap surfaced while working #36 — the blank-panel investigation bought console logging at startup, but "what is the service doing right now" still had no in-panel home, and the log-viewing half was deliberately cut out of #36 to become this feature (005 `## Clarifications` row 63).

## Done when

An operator with the panel open clicks **Logs** and reads the service's most recent structured log lines — newest first, redacted, refreshing while the tab is open — and is told in words when the stream stopped (the service cannot be read) or started over (the service restarted), never left to infer either from silence.

## Functional Requirements

- **FR-001**: **The service retains its own emitted lines in a bounded in-memory ring.** Every line the logger writes — post-threshold, post-redaction, exactly the line stdout receives — is appended to a ring of at most **1 000** lines held in the service process. When the ring is full the **oldest line is dropped** to make room, and sequence numbers keep counting: they are per-process and monotonic, so a dropped line's number is never reused and a surviving cursor still resumes correctly. Nothing is written to disk for this, no file exists for it, and a service restart empties the buffer.

- **FR-002**: **The service answers `GET /v1/logs` with its retained stream.** The route is read-only and registered like every other loopback route, so the transport's bearer authentication, response-size guard, and error catalog apply unchanged — no manifest, capability, SDK, or storage change rides on it. Its answer is `{ entries, startedAt, intervalMs }`: `entries` are the retained lines as sequence-numbered `{ seq, line }` pairs in ascending `seq`, each `line` the line as the logger serialized it — no re-encoding, no second redaction pass; `startedAt` is the service process's start stamp; `intervalMs` is the effective polling interval, the same value `GET /v1/status` reports. Query semantics are bounded and fail closed under `## Wire Surface Delta`. This is a read of memory, not of the store, so an unusable store does not refuse it.

- **FR-003**: **The panel presents a seventh top-level tab, `logs`, labelled *Logs*, last in the strip after *About*.** It joins the shell's declared tab set, so every shell rule applies to it unchanged: mount on first activation, exactly one active body, a last-read stamp, 005 FR-019's read state, keyboard reachability with an accessible name, and disposal on teardown (005 FR-010, FR-013, FR-014, FR-016, FR-017 as amended at 005 v1.22.0). **Status remains the landing tab** (005 FR-015); Logs is reached in one click like every other tab (005 SC-111).

- **FR-004**: **The tab renders the stream as text, newest line first.** The line that just arrived is the first line on screen — visible without scrolling, which is the whole job of a watch view. Each line shows its timestamp, level, message, and remaining fields through the non-HTML path (005 FR-080), with the level carried by text and never colour alone (005 FR-083); a buffered line that does not parse as a JSON object still renders its own text rather than being dropped, because a viewer that hides a line it cannot parse falsifies the stream. Each answer's entries are added to the lines the tab already holds, and the tab holds **at most the same 1 000 lines** FR-001's ring holds, dropping its own oldest first — the panel's bound mirrors the service's bound. Every read the tab issues leaves `limit` unset — the default page, the newest 200 lines the wire section justifies — and carries only its own cursor, because a screenful per period is all a watch view needs and one bounded page is all a cadence should move. The tab carries 005 FR-019's states: loading, loaded with the last-read stamp, failed with the exact cause named and a retry offered — the last lines kept and marked stale, or the tab stating plainly that there are none.

- **FR-005**: **The tab reads on activation and polls on an activation-scoped cadence, in the shape of 005 FR-100/FR-101.** Every activation of Logs — including re-activation of the already-active tab — issues a read. While Logs is active a repeating tick re-reads `GET /v1/logs`: armed when Logs becomes active, **disarmed the moment any other tab is activated** (a backgrounded Logs issues no reads), cleared on teardown, and **at most one tick per panel**. A tick that fires while a read is in flight issues no second request and queues nothing; a tick that fires late reads once, with **no catch-up burst**; the cadence re-reads on schedule whatever the last read's outcome and never sooner — **a cadence is not a retry loop** (005 FR-100's distinction; 002's `SERVICE_FAILED` rule is uncontradicted). The period is the `intervalMs` the last logs answer carried, and it follows a later answer's new value; an answer with no readable `intervalMs` arms nothing, and then the tab states in words that it is not refreshing itself — **the panel invents no period** (005 FR-100 rule 3, 005 FR-101). While a tick is armed, the tab states in words that it refreshes itself and when, and that statement is text, never colour alone. *Why the period rides this route's own answer: a fixed panel-chosen period was rejected for the reason 005 records for Status — it would be a number the service never reported — and reading the interval out of `GET /v1/status` from this tab was rejected because each cadence tab must follow **its own** document (Logs reads `GET /v1/logs` and nothing else; Status reads status and nothing else), which keeps each rendered cadence statement true of its own timer and the two cadences independent of each other. **Reconciled with 005's own record:** 005 clarification row 53 and 005's Refresh-cadence wire row rejected *a new status field* carrying a panel-facing interval, because a second copy **on the same document** is two numbers that can disagree (005 NFR-112); what this feature adds is a second copy of the same effective value served by a second route, not a new configuration field, and the disagreement case is bounded — each tab's cadence statement is only ever about the answer that armed its own timer, a disagreeing copy changes the **next** period rather than any statement already rendered, and no requirement reads the two documents against each other.*

- **FR-006**: **A service restart is stated, never silently absorbed.** When an answer's `startedAt` differs from the one the tab holds, the tab discards its cursor and the lines it holds, reads the new stream from the tail, and states in words that the service restarted and that lines from before the restart are not kept — the buffer is memory and memory dies with the process, while the audit trail remains the durable record (constitution III; accepted in issue #53).

- **FR-007**: **When the service cannot be read, the tab degrades honestly.** A refused transport, a refused document, or an over-large answer renders 005 FR-019's failed read exactly: the exact cause named, a retry offered, the last lines kept and marked stale (or the tab stating plainly that there are none), the last-read stamp unmoved, no error stacked per tick, and no change to any period. Recovery needs no reload: when the service answers again, the next activation or the next scheduled tick restores the stream and clears the stale marker — and if no cadence could be armed because no interval was ever read, it is the operator's retry or re-activation that arms it, because the panel never retries automatically in order to discover a period.

- **FR-008**: **Every surface outside the `specs/` tree that states the tab count names seven — exhaustively, by category.** The `specs/` tree itself is `## Amending 005`'s business (005 re-cut, 002 corrected, 006/007 left as records), and root `CHANGELOG.md`'s *"A six-tab panel"* line is release history and stays. (a) **The visual tools' tab lists**: `tools/visual/shot.js`'s `TABS` and `tools/visual/panel-a11y.js`'s `TABS`, each holding six entries today. (b) **The site**: `site/src/pages/index.astro`'s *"six tabs in this order"* sentence and its `<dl>`, together with the assertions that pin them — `site/tests/landing-page.assertions.mjs`, whose comments, hardcoded label list, and hardcoded count all read six. (c) **Root documents that state the count**: `DESIGN.md`'s two current places — the panel description and the tested-behaviour list — **plus its measured-coverage line** (*"36 tab/width reviews (6 tabs × 560/320 × 3 fixtures)"*), which is a record of what was reviewed and **stays as it stands**; and `AGENTS.md`'s two places — the `npm run shot` comment and the *six-tab shell* line under *Where things live* (its *six gated phases* counts phases, not tabs). `README.md` was verified to name no tab and does not change. (d) **Tab-count prose — comments, help strings, and shipped-HTML copy — in any file the change touches or that describes the strip**: `src/` (the shell, state, and tab-body headers, the *one rule across the six tabs* comments, the `TabId`/body-list literal notes), `panel/index.html` (strip and body comments, the 320px fit prose), and `tools/visual/` (`shot.js`'s help string and capture comment, `panel-a11y.js`'s header, `browser.js`, `assert-body.js`, `host.js`) — each a **one-word change inside an existing line, no comment line added** (AGENTS.md comment discipline). (e) **The count-bearing comments and helper or type names in the test files the change touches** — the *"six-tab shell"*, *"all six tabs"*, *"six bodies"* header and inline prose across the suites, and identifiers such as `renderSixTabs` and `SixTabs` — caught up in those same files; the count **assertions** are AC-004's. Every one is a count catch-up only: no copy, layout, or behaviour changes with it.

## Wire Surface Delta

| Operation | Surface | Change |
| --- | --- | --- |
| Log read | `GET /v1/logs?cursor=&limit=` → `200 { entries: [{ seq, line }], startedAt, intervalMs }` | **One new read, additive within `/v1`** — a loopback read between this repository's own panel and service, registered like every other route (bearer auth, `401 unauthorized`, the 256 000-char `500 response-too-large` guard, `422 validation` all inherited from `contracts/panel-service.md` §1/§4). Nothing else on the wire moves: no existing route, member, status code, or contract changes meaning. |

- **`cursor`** — the sequence the answer must start **after**. **Absent or blank: the newest `limit` entries** — a watch view opens on the tail, and this is the one deliberate departure from `GET /v1/audit`, whose absent cursor starts at the oldest row. Present: entries with `seq` greater than it. Anything that is not a non-negative integer is refused `422 validation` naming `cursor` with a remediation, and the received value appears nowhere in the answer (invariant 8; `GET /v1/audit`'s rule, its cursor semantics excepted).
- **`limit`** — absent, blank, or non-numeric takes the default **200** (a screenful of watch context — the very page the tab requests, FR-004); a number is **clamped into 1…1 000** rather than refused, again per `GET /v1/audit`, and 1 000 is the ring's capacity (FR-001), so the clamp never hides a retained line behind a second request — any retained line is within reach of one bounded `limit`. The transport's inherited 256 000-char guard still measures the whole body: an over-large answer (a full 1 000-entry page of long real lines can be one) is refused `500 response-too-large`, **never truncated**, and the tab shows that as a failed read (FR-007).
- **`startedAt`, `intervalMs`** — the restart signal FR-006 keys on, and the only source of the tab's period (FR-005). `intervalMs` is read from the same effective config the status document reports, so both cadence tabs are fed by one number; it renders on this tab only as 005 FR-101's cadence statement, never as a configuration value (005 FR-039), and FR-005 states how that reconciles with 005's own no-second-field record.
- **Versioning** — the `/v1` prefix under contract §1's additive-within-v1 rule, and nothing more: **this is an internal loopback surface, not a published contract**, so there is no per-answer version, etag, or schema id to maintain or to break.
- **Documentation** — the shape is specified here and gains one row plus one dated amendment note in `specs/002-agent-event-extension/contracts/panel-service.md` §2.5, attributed to 010 rather than to a 002 version bump, following the additive-note pattern that file already carries for `allowedUsers`, `historyScope`, and `followUpsFrom`.

## Acceptance Criteria

- [ ] **AC-001** *(the ring is bounded, and the boundary is honest)*: Given one process emitting 1 005 lines, then `GET /v1/logs` with `limit=1000` answers with 1 000 entries — the newest 1 000 — the 5 oldest are absent, and the sequence numbers of the survivors are contiguous across the drop with no number reused; a second answer after further emissions still starts after the caller's cursor — asserted over the fixture's own short lines, so the 1 000-entry page stays inside the transport's 256 000-char guard (a real-world page of long lines need not, which is FR-007's case, not this criterion's).
- [ ] **AC-002** *(redaction holds on every path to the operator)*: Given a log line whose field value carries token-shaped material (`ghp_…`, `github_pat_…`, an `Authorization:`-shaped value), then neither the ring nor the `GET /v1/logs` answer nor the rendered tab contains the matching bytes — only the `[redacted:…]` placeholders the logger already wrote — and the line still renders with its level, message, and fields.
- [ ] **AC-003** *(the query surface fails closed)*: Given `?cursor=abc`, then the answer is `422 validation` naming `cursor` with a remediation and the received value appears nowhere in the response; given `?limit=99999`, entries are clamped to 1 000 rather than refused; given `?limit=banana`, the default 200 applies; given no parameters, the newest entries are returned — and in no case does an answer carry a credential-shaped member.
- [ ] **AC-004** *(seven tabs, everywhere the product counts them)*: Given a fresh mount, then the strip shows exactly seven tabs in order — Status, Dispatches, Bindings, Accounts, Settings, About, Logs — with Status active, each body labelled by its tab and keyboard-reachable; the shell's tab-count assertion and the suites' tab enumerations enumerate seven; and **both visual tools' tab lists** — `tools/visual/shot.js` and `tools/visual/panel-a11y.js`, each holding its own — carry seven entries, with `shot.js` capturing each tab at 720px and 560px as it does today: six tab captures become seven.
- [ ] **AC-005** *(the cadence's lifecycle, on a driven clock)*: Given an answer carrying `intervalMs: 60_000`, then Logs issues exactly one read at activation and exactly one more per 60 s while Logs is the active tab; given three periods with **Dispatches** active, Logs' read count does not move (zero reads); given a tick that fires during an in-flight read, exactly one request exists and the tab reports one read; given a throttled period, the late tick reads once with no catch-up burst; given teardown, the timer count returns to its pre-mount value; and given three consecutive refused ticks, the last lines stay on screen with exactly one stale marker, the cause named, the stamp unmoved, and the period unchanged.
- [ ] **AC-006** *(no interval means no tick and no invented number)*: Given answers that never carry a readable `intervalMs`, then no tick is armed over three advanced periods, no period string renders anywhere on the tab, and the tab states in words that it is not refreshing itself; given a later answer that carries one, the tick arms without a remount and the statement names the period.
- [ ] **AC-007** *(a restart is stated)*: Given a service restart between two reads of a mounted panel, then the next answer's `startedAt` differs: the tab drops its cursor and its held lines, reads the new stream from the tail, and states in words that the service restarted and that lines from before it are not kept; no line from the previous stream remains rendered as current, and the failure is not rendered as an empty-but-fresh stream.
- [ ] **AC-008** *(down, then up — with no reload and no auto-retry)*: Given the service stopped, then the tab names the exact cause, offers a retry, keeps the last lines marked stale (or states plainly there are none), arms no tick if no interval was ever read, stacks no error per tick, and changes no period; given the service started again while the panel stays mounted, then the operator's retry or re-activation succeeds, the stale marker clears, the stream resumes, and a cadence is armed from the answer — with zero `host.startSession()` calls, zero panel reloads, and no request issued between the failure and the operator's or the cadence's own next read.
- [ ] **AC-009** *(the threshold governs entry, not display)*: Given `PUT /v1/config` raising `logLevel` to `error`, then `debug` and `info` lines emitted afterwards appear in neither stdout nor the ring nor the tab, while lines buffered before the change still render — asserted over one sequence straddling the change, so an implementation that filters at read time or buffers pre-threshold lines fails it.
- [ ] **AC-010** *(a burst changes what is shown, not how the panel behaves)*: Given 500 new lines between two ticks, then the panel issues exactly one request per period (no request burst), each answer carries at most `limit` entries, and the tab's held set never exceeds the service's retained lines — the ring's drop is the only loss, and the tab claims nothing about completeness.
- [ ] **AC-011** *(the render)*: Given a mixed stream, then the newest line is the first rendered line without scrolling; each line shows timestamp, level, message, and fields as text through the non-HTML path with no `innerHTML` sink; a buffered line that is not valid JSON renders its own text rather than disappearing; and no state is conveyed by colour alone.

## Edge Cases

- **Service restart mid-session** (FR-006, AC-007): the answer's `startedAt` changes, the cursor resets, the tail is re-read, and the tab says the restart out loud — the pre-restart history is gone and the tab must not render the gap as if those lines had never existed.
- **`logLevel` changed through the already-shipped `PUT /v1/config`** (AC-009): the threshold governs **entry into** the buffer, not display — the ring holds exactly what the logger emits, so from the change's next line the buffer gains only what passes the new level, lines already buffered stay and keep rendering, and the viewer never re-filters, re-sorts by level, or removes a line retroactively. A level change can decide *whether* a line reaches the buffer, never *what* a buffered line says (the same sentence 005 records for `setLevel`).
- **A huge burst between two polls** (AC-010): the ring drops its oldest past 1 000 and the answer is capped at `limit` (default 200), so during a sustained burst the tab trails; it issues one request per period, shows what it fetched, and never claims the stream is complete — lines dropped or not yet fetched are simply not shown, and the honest object here is a tail, not a transcript.
- **Panel mounted while the service is down; the service comes up later** (FR-005, FR-007, AC-006, AC-008): the first read fails and carries no interval, so no tick can be armed and the tab says so rather than guessing a period; the cause stays named with a retry offered and no per-tick error churn; when the service returns, the operator's retry or re-activation reads successfully, arms the cadence from that answer's `intervalMs`, and the stream resumes without a panel reload. The panel never auto-retries to discover a period.
- **Across the 1 000-line boundary** (FR-001, AC-001): the oldest line is dropped while sequence numbers keep counting, so a cursor taken before the drop still resumes correctly — entries are `seq > cursor`, whichever of them survive — and the tab never holds more lines than the service retains.

## Not doing

- **No log file on disk, no rotation policy, no durable retention.** The audit trail (`GET /v1/audit`) remains the durable history; the ring is memory that dies with the process (the constitution III tension is recorded above and accepted in issue #53).
- **No panel-side event merge.** The Logs tab shows **service** lines only; panel-side startup milestones stay console-only per 005 FR-142, as #36's cut recorded.
- **No dispatch or status watch panes** — the Dispatches and Status tabs already exist and Logs duplicates neither.
- **No buffer-size or log-view settings dial** — no new service configuration field (006's field count is unchanged), no new `host.storage` key, and nothing about the Logs tab persisted across teardown: a reopen re-reads the tail.
- **No manifest, capability, or SDK change** — `capabilities[]` stays `sessions` + `prompt`, `contributes.service` gains no `permissions` (AGENTS.md invariant 3), the panel still makes no GitHub request; no `SERVICE_VERSION` change (invariant 5), no SDK re-pin (invariant 6), no package `version` bump (invariant 2's pre-1.0.0 posture).
- **No push transport** — no SSE, websocket, or long-poll for logs; the issue's own reasoning (*the service cannot push to the panel*) makes polling the shape, and the cadence rules in FR-005 are what keep it honest.
- **No `README.md` change** — checked: it names no tab. The documentation surfaces that do name them (`site/src/pages/index.astro`, `DESIGN.md`, `AGENTS.md`'s shot line) are in scope under FR-008 and are named there.
