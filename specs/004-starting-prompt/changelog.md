### v1.1.0 — 2026-09-28 (extension amendment; feature 005 places the field on the Bindings tab)

- **Rationale**: 004 landed the field and named its renderer: the roadmap says 004 "lands before 005 so the Bindings tab renders the prompt field **exactly once**", and 004's own dependency line records that 005 "renders this field exactly once". This amendment makes that placement a requirement with a reason, rather than a note in a predecessor's header. The reason is specific and not stylistic: a starting prompt is an instruction, and **two renderings of one instruction is how two versions of it start to disagree** — an operator who edits the field in one place and reads it in the other cannot tell which is authoritative. The same reasoning applies to the fingerprint: the row may show presence and length, and must never show the fingerprint or the text, because a fingerprint presented beside an editable field invites the operator to believe it is editable.
- **Sequencing decision**: 005 **extends** this document and **supersedes nothing** in it. 005 is **unimplemented** and so is 004, so this is a **record amendment**: there is no deployed field to migrate and no rendered surface to correct, only a design still free to be made around the placement.
- **Principles reviewed, unchanged in substance**: Principle I (no secret in any store, log, or rendered surface) is served by the single-rendering rule together with the refusal of credential-shaped prompt text — 005 adds a rendering case to the existing secret-scan suites rather than an exemption. Principle IV (human-visible auditability) is served by the row's presence-and-length display: the operator learns that a prompt is set and how long it is, without the audit trail ever holding the text. Principle II (safe autonomy by default) is unchanged — the prompt is still operator-authored instruction placed above untrusted source text, and 005 changes where the field sits, not what may be typed into it. Principle VII (thin orchestration boundary) is unaffected — the panel still composes the message it already composed and sends it through the call it already makes. No principle is weakened.

### v1.4.1 — 2026-10-02 (the gate corrections; FR-085's arithmetic corrected, NFR-129 reworded)

- **Rationale**: two corrections the product owner approved at the 4–5 gate on 2026-10-02 — approved as *"Correct the prose"* and *"reword NFR-129's one sentence"* — that were never routed into the text until this entry. **(1) FR-085's arithmetic was off by a few.** The owner's words, verbatim: *"FR-085's arithmetic is off by a few. Quoted 6,002 / 9,006; its own blank-line gap rule gives 6,004 / 9,004. → Correct the prose. ### v1.4.2 — 2026-10-02 (pre-PR review correction; FR-085's floor has two ways in, not one)

- **Rationale**: an independent pre-PR reviewer found this document's prose false in four places — the combined-block edge case, FR-085's floor clause, `## Clarifications` row 24, and contract [`layered-prompt.md`](./contracts/layered-prompt.md) §4 rule 3 each said an over-budget composition is *"reachable only by a store hand-edited past its own validators"*. It is not, because **the two halves of the budget are counted in different units**. `service/prompt.ts` validates each tier with `countCodePoints(text) > STARTING_PROMPT_MAX_CODE_POINTS` (code points) and bounds the stored body with `promptStackMaxCodePoints` the same way, while `src/relay-attempt.ts` refuses the composed message on `composed.length > CONTEXT_MAX_CHARS` and `promptBlockChars` reserves the block on `prompt.length` — both **UTF-16 code units**. A **legal** three-tier prompt that is mostly supplementary-plane text — inside 2,000 code points per tier, inside the 6,004-code-point stack bound, past every save-time validator — composes past `CONTEXT_MAX_CHARS` and is refused at the floor on **every** dispatch, with no hand-edit anywhere; three maximal astral tiers alone stack to ≈12,000 UTF-16 units before fence, frame, and excerpt.

- **The resolution, decided and recorded**: **the floor stays in UTF-16 — the prose is what was wrong.** `CONTEXT_MAX_CHARS` budgets the message the *host* receives, and the host measures it as a JavaScript string: the pinned SDK validates with `z.string().max(GUEST_ATTACH_TEXT_MAX)` and clamps with `String.prototype.slice(0, GUEST_ATTACH_TEXT_MAX)` (`contract.js`), both UTF-16. Counting code points at the floor would let a message whose UTF-16 length exceeds the host's own limit through (12,000 code points can be 24,000 UTF-16 units), trading a refusal that names the contributing tiers for the host's clamp or rejection — divergence from the host's limit, not accuracy against it.
