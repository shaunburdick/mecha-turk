## Q1 — Audit-trim cost per cycle: full read every boundary, or a gate? *(engineering question; default decided)*

- **The problem, stated plainly.** FR-055 requires the pass to run **(a)** once at store open and **(b)** at every poll-cycle boundary, reading the stored configuration each time. At the default `auditMaxEntries` of 50,000 the trail can be ~15 MB of NDJSON; a naive implementation parses all of it once per cycle (once per 60 s at the default interval) even when nothing is removable. The pass is *correct* either way — the question is whether the per-cycle cost is acceptable for a self-hosted, unattended service (constitution V).
- **Decision (default, implemented unless measurement overturns it)**: **run the full read every boundary.** Three facts make it cheap enough in the shipped scale (constitution V's "few bound repositories, one operator machine"): (1) the cap bounds the file *by construction*, so the worst case is the cap, not unbounded growth — and unbounded growth is precisely the defect this pass exists to end; (2) the write is skipped entirely when nothing is removed (FR-053 mandates this anyway), so the common steady-state pass is read + decide + no write; (3) a trail at the cap with nothing aged out is a *read-only* pass, and reading 15 MB of already-parsed JSON lines is tens of milliseconds, not seconds, on a desktop Node process.
- **The documented escape hatch** (recorded so it can be added without redesign): a per-store-handle gate holding `{lastFullPassAt, auditRetentionDays, auditMaxEntries}` in memory — run the full read when any of *no pass has run yet*, *either configured limit differs from the last full pass*, *`auditMaxEntries` is already exceeded by the in-memory append counter*, or *a periodic recheck interval has elapsed*. **The config-change arm is mandatory**, because the confirmation copy promises "at the next trim pass" after a lowered limit (FR-052) — a gate that ignored a config change would break that promise. The periodic arm is the only soft one.
- **Alternatives considered**: (a) gate every cycle and only re-read hourly — rejected as the *default* because it makes the age-window check eventually-consistent in a way the confirmation copy does not promise; (b) maintain a running count in `appendAudit` and never read the file — rejected because trimming changes the count and the cache is not a durable record of the file; (c) trim inside the `PUT` handler — rejected outright by FR-047.
- **Not a blocker**: the default is correct and spec-shaped; the gate is a contained optimisation inside `service/audit-trim.ts` if `npm run verify`'s timing or an operator's CPU observation says otherwise.

## Q2 — Atomicity of the NDJSON rewrite *(engineering question; default decided, pattern already exists)*

- **The problem, stated plainly.** The audit trail is NDJSON, but the store's atomic writer (`writeJsonAtomic`) serialises a JSON *document*. FR-055 requires the trim's file replacement to be atomic ("either the pre-trim one or the post-trim one, never a torn file"), and the store exposes only `writeJson` (document) and `appendLine` (single line). There is no "replace the whole NDJSON file" operation today.
- **Decision**: add `ServiceStore.writeLines(relativePath, entries)` implemented with the **exact pattern `writeJsonAtomic` already uses** — temp sibling at mode `0600`, `fsync`, `rename` over the target — plus the directory-mode correction the store already performs. It is the NDJSON sibling of `writeJson`, which keeps invariant "one IO path per file kind" true rather than adding a second, hand-rolled writer inside a trim module.
- **Why the question is nearly closed already**: the atomicity *mechanism* is settled and shipped (`service/store/json.ts` documents it line by line); only its application to a line file is new, and the application reuses the same three syscalls. The crash semantics FR-055 asks for fall out of the rename: a crash leaves the old file or the new one.
- **Interaction with `seq`**: because the `audit.trimmed` row is written **in the same rename** as the removals (plan D4), there is no window in which a restart could re-seed `nextSeq` below a number already used — which is the only way a trim could renumber. A two-step remove-then-append would reintroduce exactly that window, so the single-write design is not a style preference but the answer to this question.
- **Alternatives considered**: (a) append the trim row first, then rewrite without it — rejected, it writes a row describing a removal that may not happen (FR-053 forbids this literally); (b) rewrite with `writeJson` and a string body — rejected, it would change the file's shape to a JSON array and break `readLines` and every existing consumer; (c) delete and re-append — rejected, non-atomic and loses `seq` order on a crash.

## Q3 — The verification-baseline fallback is one panel-side literal, which AC-106 scans for *(confirmation requested; default decided)*

- **The problem, stated plainly.** **002 FR-029 as amended** requires the panel to post a baseline on `POST /v1/runs/:runKeyHash/verification`, and its contract note says: *when the config read fails, the panel posts the documented default `project-manager` with its provenance*. **006 AC-106** says the panel source contains **no** configuration *default* literal, and **006 FR-022** says the panel carries no copy of any default. These are both true requirements of the same build.
- **The escape that already exists**: whenever *any* `GET /v1/config` read has succeeded, the default is available from `fields[...].default` — including the "field absent from the document" case FR-100(b) describes, which is why `defaultsApplied` exists. So the literal is needed **only** for a verification that runs before the panel has ever read the configuration successfully.
- **Decision (default, implemented unless overturned)**: keep `DEFAULT_EXPECTED_AGENT` where it already lives (`src/config.ts`, it predates this feature), **pin it to `service/config.ts`'s `DEFAULT_CONFIG.expectedAgent` by a test that fails if either moves**, and record it as the **single named entry** in AC-106's scan allow-list — with the scan asserting the allow-list has exactly one entry, so the exception cannot quietly grow. This is the same enforcement pattern 005 used for its stand-in (a copy that a test compares against the service), inverted: the copy cannot drift, and it is visibly the only one.
- **Alternatives considered**: (a) omit `expectedAgent` from the verification body when unreadable — rejected, 002 FR-029's contract mandates the default with provenance and 006 AC-155 restates it; (b) read the default from `GET /v1/status.agentPin.expectedAgent` — rejected, that member is itself sourced from `GET /v1/config` and fails with it; (c) ship no fallback and warn without a baseline — rejected, it changes a verification semantic the owner has already fixed twice (002 FR-029 as re-cut, 006 FR-100(e)).
- **Confirmation requested from the product owner**: *is one pinned, asserted, single-entry exception to AC-106 acceptable for the no-read verification fallback, given that every other default is read from the projection?* If the answer is no, the fallback must move into a non-`src/` artefact (a manifest-level constant) — a copy change, not a redesign.

## Q4 — Is FR-027 / AC-115's "field the panel does not recognise" reachable in a co-shipped build? *(confirmation requested; default decided)*

- **The problem, stated plainly.** **FR-027** and **AC-115** require a `config` member the panel does not recognise to render as *field this version does not show* and to block the save. But `GET /v1/config` serves a document that passed the **same** whole-file validator the projection is built from, and panel + service are one committed bundle (`AGENTS.md` invariant 1). In a co-shipped build the document and the descriptor list therefore cannot disagree — the rule looks unreachable through the live wire.
- **Where it *is* reachable**: version skew (an operator's panel bundle paired with a newer service — the invariant says builds ship together, but nothing on disk enforces it), and a **future** field added by another feature while an older panel renders. It is also the same defensive rule 005 FR-041 applies to an unknown dispatch state: forward compatibility beats a tidy rendering of something the panel cannot reason about.
- **Decision (default, implemented unless overturned)**: implement FR-027 as a **panel-side fail-closed rule tested against a seeded fixture** (a response whose `config` carries a member absent from `fields`), and keep the **service's stored-document read strict** — a hand-edited key the service does not know still quarantines (AGENTS.md invariant 8, NFR-103). The alternative — relaxing `parseStoredConfig` to serve unknown members so the case becomes live — would make a hand-edited unknown key *persist and round-trip*, which is exactly the drift the whole-file rule exists to refuse.
- **Note for the record**: the live-service path for this AC exists only under skew; the requirement is on the **panel**, and it is tested on the panel. This is stated rather than papered over, because a reader checking AC-115 against the wire will otherwise conclude the suite is missing a case.
- **Confirmation requested from the product owner**: *confirm that AC-115 is satisfied by the panel-side rule plus its fixture, and that the service's whole-file read stays strict (an unknown stored key still quarantines) rather than being relaxed to make the case live.*
