## Problem Statement

The panel can already **tell an operator what the service is configured to do**, and it cannot change any of it. Feature 005 landed the Settings tab as a deliberately read-only list of ten rows, each with its effective value, unit, bounds, and a plain statement that editing arrives with feature 006 (005 FR-070 – FR-073). The product owner then chose, at intake, **full CRUD over all service settings** rather than a reduced read-mostly surface. That decision is why this feature exists, and it is the reason 006 is a write capability and not a documentation change.

The surface it needs to write already exists and already works. `GET /v1/config` and `PUT /v1/config` ship in `service/routes/config.ts`; `service/config.ts` holds the ten-field `ServiceConfig`, the `NUMERIC_BOUNDS` table that gives every field its bounds and unit, the additive `ConfigIssue` list that reports **every** bad field in one pass, and the whole-file replacement rule that refuses unknown keys rather than ignoring them. The validator is careful, the remediation text names the field and its range and never echoes what was submitted, and a `422` answers with a complete list rather than the first failure. Nothing about the service's contract needs designing. What is missing is the operator-facing half, and it is missing in a way that is easy to get quietly wrong:

1. **Only one of the ten fields does anything today.** `service/poll/timer.ts` re-reads `config.json` after every poll cycle and schedules the next one with the value it just read, so `intervalMs` is genuinely live. The other nine have **no consumer anywhere in the service**: `perPage` is not read because `service/poll/poller-github.ts` hardcodes `PAGE_SIZE = 30`; `logLevel` is not read because `service/main.ts` hardcodes `createLogger({ level: 'info' })` and `service/log.ts` captures the severity threshold in a closure at construction and never re-consults it; `auditRetentionDays`, `auditMaxEntries`, and `excerptRetentionDays` are not read because `service/audit.ts` records that retention trimming "belong[s] to task T-027" and no trimming pass exists; `overlapMs`, `retryMaxAttempts`, `retryBaseMs`, and `retryMaxMs` have no reader at all, because the checkpoint, lease, and backoff machinery that would read them is recorded as MVP-DEBT in `service/poll/loop.ts` and 003's state model is not implemented. A panel that says *Saved* on all ten is a panel making ten promises the machine does not keep — which is precisely the class of defect 005 existed to end. **At the phase gate the product owner chose to close that gap rather than label it** (`## Resolved Gate Questions` entry 1): this specification therefore does not merely render the nine fields, it **specifies the consumer for each of them** — a trimming pass over `audit.ndjson`, a trimming pass over the stored payload excerpts, a bounded backoff on the poll request path, the overlap that widens the scan window, and the page size every list request carries — with the states, failure behaviour, and acceptance criteria that follow from each.

2. **"Live" is a per-field fact, not a per-feature one.** `intervalMs` takes effect at the **next scheduled cycle**, not immediately: a change made while a scan is running is used when that scan ends, and the already-armed timer keeps the delay it was given. `logLevel` is the one field where *immediate* is cheap, because the only thing standing between it and the sink is a captured constant. Every other field is honest-restart-or-nothing **in the shipped build**, and for nine of them it is nothing. This feature gives those nine the `next-cycle` boundary and a consumer that reads the stored configuration at the cycle boundary, so the per-field story the panel tells stays true: what the row says is what the machine will do.

3. **The panel cannot learn any of this from the service.** `GET /v1/config` returns `{ config }` — ten values and nothing else. It carries no bounds, no units, no defaults, no effect classes. So 005 FR-071's rule, "each bound is the service's own, not a re-typed copy that can drift from it," has no mechanism behind it: the only way for the panel to label `intervalMs` as 15,000–300,000 ms today is to **type those numbers into the panel**, which is a copy that will drift the moment a bound moves. The drift this project spends whole requirements preventing is currently guaranteed by the wire shape.

4. **The shared service-call wrapper names the wrong thing.** `src/service-calls.ts` maps a `422` to the string `service refused the bindings list` and discards the refusal body, so a configuration refusal rendered today would name bindings and show the operator nothing.

5. **The three retention knobs read like storage controls, and today they are not.** An operator who lowers `auditRetentionDays` has been told the audit trail is bounded to N days. Today nothing trims it: `service/audit.ts` defers trimming to task T-027 and `audit.ndjson` grows without bound. Once this feature specifies the trimming pass (FR-055, FR-057), the knob becomes the truth — and lowering one **will delete**, at the next cycle boundary. The confirmation must then tell the whole of it: what will be removed, when, and what survives (FR-052), because a confirmation that claims no trimming runs would become false the moment the pass ships, and a silent one would delete history the operator did not expect to lose.

This specification turns 005's ten read-only rows into ten editable fields inside the tab 005 already built, with a **write path the service already honours**, a **take-effect contract per field grounded in what the code actually does**, **destructive-knob confirmation that tells the truth about what will and will not be deleted**, and **two audited rows** so that a settings change is explainable months later. It also widens one wire response — the read — so that the panel can render bounds, units, defaults, and effect classes **from the service's own declaration** instead of from a second copy of it. That single widening is what makes "the panel cannot drift from the service" an enforced property rather than a stated intention.

## Architecture Impact

006 changes **what the panel does with the configuration surface**, and makes one small service-side change that the live-apply contract requires. It adds no store, no manifest capability, and no host call.

| Module | Today | After 006 |
| --- | --- | --- |
| `service/config.ts` | `ServiceConfig`, `NUMERIC_BOUNDS`, `LOG_LEVELS`, `DEFAULT_CONFIG`, additive `validateConfig` | **Unchanged as the single declaration.** A **projection** of that same declaration is exposed so the wire can carry it; the validator and the projection read one source, so a bound cannot move in one place and not the other (FR-020 – FR-022). |
| `service/routes/config.ts` | `GET` returns `{ config }`; `PUT` validates then writes atomically | `GET` returns `{ config, fields }` — the effective document plus the declared field schema. `PUT`'s **semantics are unchanged**: whole-file, additive 422, no partial write, no value echo. It additionally writes an audit row (FR-040 – FR-045, FR-070 – FR-072). |
| `service/main.ts` / `service/log.ts` | `createLogger({ level: 'info' })` hardcoded at line 115; `const threshold = SEVERITY[options.level]` captured in a closure at line 90 | The logger adopts the **stored** `logLevel` once the store is open, and the threshold becomes adoptable again without a restart — the one field whose boundary is `immediate` rather than `next-cycle` (FR-033, FR-037) |
| `service/audit.ts` | Write path only; line 13 records that "**Retention trimming** and the correlation-indexed read API belong to task T-027", so `audit.ndjson` grows without bound | **A trimming pass is added** for `auditRetentionDays` and `auditMaxEntries`, run at store open and at every cycle boundary, removing oldest-first past a protected set and appending one `audit.trimmed` row when it removes anything (FR-055 – FR-057, FR-073). | `service/poll/events.ts` (`events.json`) | Dispatched tail capped by count (`MAX_DISPATCHED_EVENTS = 500`); no age bound on the stored `issueBodyExcerpt` | **An excerpt trimming pass is added** for `excerptRetentionDays`: the payload text of terminal rows older than the window is cleared, row identity and dedupe untouched, pending and in-flight excerpts never touched (FR-057) |
| `service/poll/loop.ts` (`windowFor`) | Returns the recorded `lastScanAt` verbatim as the `since` stamp — no overlap, so 002 FR-019's configurable 10-minute overlap has no reader | Returns **`lastScanAt − overlapMs`**, read from the stored configuration at cycle start; the widened window re-observes and the deterministic event id drops the replay (FR-034, FR-059) |
| `service/poll/poller-github.ts` | `const PAGE_SIZE = 30` (line 51) and `const MAX_LIST_PAGES = 2` (line 54) hardcoded | `PAGE_SIZE` is replaced by the configured **`perPage`**, always ≤ 30 (002 FR-020's ceiling, enforced by the field's own maximum). **`MAX_LIST_PAGES` stays 2** (FR-059; `## Out of Scope`) |

The **poll timer is not touched**. It already re-reads the interval per cycle; `next-cycle` is the behaviour, not an implementation 006 introduces (FR-032). What this feature adds on the service side is five **configuration readers** — the scan window, the page size, the poll backoff, and two trim passes — each reading the stored configuration once at the cycle boundary, plus the logger's adoption of `logLevel`. No trigger detector, no dispatch path, no relay loop, and no store format other than the two files a trim pass rewrites is otherwise changed.

## Per-Field Contract

This table is **normative** and is what FR-030 – FR-036 and FR-055 – FR-059 govern. Every row names the consumer that reads the field and the code evidence its take-effect boundary was read from, so a later reader can check the claim rather than take it. **As of v1.1.0 no row reads `none`:** the gate answer of 2026-09-28 accepted wiring all nine fields that v1.0.0 left inert (`## Resolved Gate Questions` entry 1), so each field now has a specified consumer.

| Field | Bounds / unit | Default | Consumer (what reads it, and where) | Take-effect boundary |
| --- | --- | --- | --- | --- |
| `intervalMs` | 15,000 – 300,000 milliseconds | 60,000 | `service/poll/timer.ts:48` awaits `currentIntervalMs(deps.store, deps.log)` **after** `runScanCycle` resolves and schedules with the returned value; `service/poll/loop.ts:109-123` re-reads `CONFIG_FILE` on every call and falls back to the default on an unreadable file | **`next-cycle`** — the new value is used when the cycle currently running ends, to schedule the *following* one. A cycle already armed keeps the delay it was given, so the worst case is one full cycle at the old value plus the cycle in flight |
| `logLevel` | `debug` \| `info` \| `warn` \| `error` | `info` | The logger itself: it adopts the **stored** `logLevel` once the store is open, and its severity threshold becomes adoptable again at runtime. **This is a service change 006 requires**, not shipped behaviour: `service/main.ts:115` passes a literal level and `service/log.ts:90` captures `const threshold = SEVERITY[options.level]` once, so today the configured value has no effect even across a restart (FR-033 states the gap and the fix) | **`immediate`** — the first log line emitted after the save is acknowledged is judged at the new threshold. **No restart.** Confirmed as encoded at the gate (answer 3) (FR-033, FR-037) |
| `overlapMs` | 60,000 – 7,200,000 milliseconds | 600,000 | The scan window: `windowFor` (`service/poll/loop.ts:156`) returns **`lastScanAt − overlapMs`** as the `since` stamp instead of the bare stamp, read from the stored configuration at cycle start. The widened window re-observes, and `enqueueEvents` (`service/poll/events.ts:347-358`) drops the replay by deterministic event id, so no second event, dispatch, or session can result. **Closes 002 FR-019's conformance gap** — FR-019 has required a configurable overlap and nothing read it | **`next-cycle`** — the window is computed once at cycle start; the cycle in flight keeps the window it was given |
| `perPage` | 1 – 30 items per page | 30 | Every GitHub list request, replacing `const PAGE_SIZE = 30` (`service/poll/poller-github.ts:51`): `per_page = <configured value>`, always ≤ 30 — 002 FR-020's ceiling is the field's own maximum. `const MAX_LIST_PAGES = 2` (`:54`) is **unchanged**, so one scan still reaches two pages and the reachable history is `2 × perPage` | **`next-cycle`** — the page size is read with the rest of the polling configuration at cycle start, so requests inside the running cycle keep the page size they started with |
| `retryMaxAttempts` | 1 – 10 attempts | 5 | The poll request path (FR-058): one list request may be attempted up to this many times, **the first attempt included**, before the binding's scan ends as a skip with one honest reason and the cycle walks on to the next binding | **`next-cycle`** — read with the polling configuration at cycle start; a retry ladder already in flight keeps the parameters it started with |
| `retryBaseMs` | 1,000 – 60,000 milliseconds | 5,000 | The backoff computation: delay before attempt *n* is `min(retryMaxMs, retryBaseMs × 2^(n−2)) × jitter`, jitter uniform in `[0.5, 1.0]`, so every delay lies in `[cap/2, cap]` | **`next-cycle`**, as above |
| `retryMaxMs` | 5,000 – 300,000 milliseconds | 60,000 | The ceiling on that computation; `retry-after`/reset guidance that asks for longer **wins** and is logged as the reason for the wait. The cross-field rule `retryBaseMs ≤ retryMaxMs` **is** still validated and still refused (`service/config.ts:149-160`) | **`next-cycle`**, as above |
| `auditRetentionDays` | 7 – 3,650 days | 180 | The audit trimming pass (FR-055): at store open and at every cycle boundary it removes the oldest `audit.ndjson` entries that fall outside the day window, **skipping the protected set** FR-056 defines, and appends one `audit.trimmed` row when it removes anything | **`next-cycle`** — the pass reads the stored configuration at the boundary, so a save acknowledged mid-cycle applies at the next boundary (and, for a stopped service, at the first boundary after the next start) |
| `auditMaxEntries` | 1,000 – 1,000,000 entries | 50,000 | The same pass, whichever limit trips first (002's data model: days **or** entries). The pass counts the `audit.trimmed` row it is about to append, so the trail lands at or below the cap instead of oscillating around it | **`next-cycle`**, as above |
| `excerptRetentionDays` | 1 – 365 days | 30 | The excerpt trimming pass (FR-057) over the stored payload excerpts in `events.json`: rows older than the window **and** already `dispatched` have `issueBodyExcerpt` (`service/poll/events-parse.ts:59`, bounded at enqueue by `service/poll/triggers.ts:41`) cleared; `pending` and `in-flight` excerpts are never cleared at any age | **`next-cycle`**, as above |

**All ten fields have a consumer, and the boundary each row states is the boundary that consumer delivers.** Three consequences follow, and this specification states all three rather than resolving them away:

- The panel **renders each field's declared boundary next to the field, in the product's own words**. The closed vocabulary is `immediate | next-cycle | restart | none` (FR-030), and **as of v1.1.0 nine fields declare `next-cycle` and `logLevel` declares `immediate`** — no field declares `none` and none declares `restart`. `none` stays defined in the vocabulary because a schema vocabulary is a contract and removing a value from it is a wire change, not an editorial fix; but the *stored-not-applied* class this specification carried at v1.0.0 no longer exists here, so no row can say "this value changes nothing in this build" about a field this feature has wired.
- **One read, once per cycle.** Each of the nine `next-cycle` fields is read from the stored configuration at the cycle boundary — the window, the page size, the retry ladder, and both trim passes all take the values one read produced — which is why a single save changes all of them at the same boundary and why no consumer can see a half-updated configuration (FR-055, FR-057 – FR-059).
- **No field may declare `restart` in this feature.** `logLevel` *could* legitimately have been scoped that way — the logger is built once at startup — and 006 chose `immediate` instead. If Phase 4 finds `immediate` infeasible, the field is reclassified to `restart` **only by coming back to the product owner**, never silently (FR-037); the same rule governs **any** change to any field's declared class, because the panel's copy, the confirmation text, and the test that backs a declaration all follow from it. That rule is what makes the declared boundary trustworthy.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Change a setting and know exactly what it did (Priority: P1)

The operator opens **Settings**. The same ten rows 005 renders are now fields, each labelled with its unit, its bounds, and — in words on the row itself — whether changing it takes effect immediately or at the next poll. Every one of the ten has a consumer, so no row has to apologise for itself. The operator changes the poll interval from 60,000 to 120,000 and saves once. The save is accepted, the row says *in effect from the next poll*, and the **Status** tab's effective interval still reads 60,000 for the rest of the running cycle and shows the difference by name rather than pretending either number is wrong. The operator changes the log level to `debug` and saves once; the very next service log line is at debug verbosity, with no restart and nothing else to do. The operator lowers the audit retention to 30 days and is told, before anything is written, that entries older than 30 days will be deleted at the next trim pass, what survives that trim, and that the trim will leave a row of its own recording what it took.

**Why this priority**: this is the feature. The product owner chose full CRUD over all service settings; a write path that cannot tell the operator what its write did would deliver the surface without the substance, and would repeat the exact dishonesty 005 was written to end.

**Independent Test**: mount the Settings body against a fake host and a temp-directory store; drive a scan cycle with a driven clock, save `intervalMs` mid-cycle, and assert the *armed* timer keeps the old delay while the *next* scheduled one uses the new value; capture the logger's sink, save `logLevel: debug`, and assert the next emitted line is at debug without restarting anything; save `overlapMs` and assert the next cycle's `since` stamp equals the recorded stamp minus the new overlap, and save `perPage` and assert the next list request carries the configured `per_page`.

**Acceptance Scenarios**:

1. **Given** the Settings tab with the service running, **When** the operator reads it, **Then** each of the ten fields shows its name, unit, bounds, current value, and its take-effect boundary in words — and no field shows a boundary the service did not declare.
2. **Given** `intervalMs` at 60,000 with a scan in progress, **When** the operator changes it to 120,000 and saves, **Then** the cycle in flight completes at the old cadence, the row reads *in effect from the next poll*, and the following cycle is scheduled at 120,000 — with no restart and no manual poll.
3. **Given** the Settings tab with the service running, **When** the operator sets `logLevel` to `debug` and saves, **Then** the first log line emitted after the acknowledgement is at debug verbosity and no restart occurred.
4. **Given** the retention rows with their limits, **When** the operator reads each one, **Then** it names what the limit governs and states that lowering it deletes at the next trim pass while the protected references survive — and no row anywhere on the tab claims that its value changes nothing in this build.
5. **Given** a saved `intervalMs` that the scheduler has not adopted yet, **When** the operator reads **Status**, **Then** Status shows the effective 60,000, Settings shows the configured 120,000 marked pending, and both name the difference and the boundary.
6. **Given** an unchanged field, **When** the operator edits a different one and saves, **Then** the unchanged field is sent unchanged and is not reported as modified.

### User Story 2 — Be refused by the service, in the service's words (Priority: P1)

The operator mistypes a field, or clears one, or pastes a token into a field name. The panel sends the whole document, exactly as it does for any save. The service answers with a complete list — every bad field, not just the first — and the operator sees each one named with its own remediation in the service's own words. **The panel never shows what they typed back to them**, never invents a second message, and never silently drops one entry from the list. Nothing was written: the ten fields are byte-for-byte what they were, and the fields the operator did not touch are still showing what the service holds.

**Why this priority**: the validator is the best thing in this service and the whole reason to route through it. If the panel re-validates, it will disagree with the service eventually, and the operator will be the one who finds out — by getting a message the service never sent, or worse, a save that the service would have refused.

**Independent Test**: submit a document that violates every documented rule at once — a fractional value, a value below its minimum, a value above its maximum, a missing field, an unrecognised log level, `retryBaseMs` above `retryMaxMs`, and a foreign key — and assert the rendered refusal contains each issue the service returned, in the service's order, that no submitted value appears anywhere in the rendered surface, and that the stored document is unchanged.

**Acceptance Scenarios**:

1. **Given** a document with three bad fields, **When** the operator saves, **Then** all three issues render, each naming its field and its remediation, and none is omitted or reordered.
2. **Given** a refusal, **When** it renders, **Then** the string `service refused the bindings list` appears nowhere and the problem names the configuration.
3. **Given** a refusal, **When** the operator looks at the form, **Then** every field shows the value the service last reported — including the fields they did not touch — and no field shows an optimistic local value.
4. **Given** a value outside a field's bounds, **When** the operator types it and saves, **Then** the panel sends it and the service refuses it; the panel's own bounds affordances **do not** suppress the submission.
5. **Given** an unrecognised log level, **When** the operator saves it, **Then** the service's remediation naming the four accepted levels is what renders.
6. **Given** `retryBaseMs` greater than `retryMaxMs`, **When** the operator saves, **Then** the service's cross-field issue — named against `retryMaxMs` — renders, and the panel does not reword it.

### User Story 3 — Know before anything is deleted (Priority: P1)

The operator lowers `auditRetentionDays` from 180 to 30. The panel arms a confirmation that names the field, the current limit, the new limit, what the limit governs — and, in the same breath, the truth of what that change now does: **entries older than 30 days will be deleted at the next trim pass**, the pass runs at the poll-cycle boundary (and once at service start), the minimal references that keep a run explainable are never deleted, and the trim appends an `audit.trimmed` row recording exactly what it took. One click arms; nothing is written. The operator clicks again, the write happens, and an audit row records what changed. Raising a limit deletes nothing and is said to delete nothing. Changing a *non*-retention field does not arm anything, because there is nothing there to confirm.

**Why this priority**: retention limits are storage controls now. An operator who believes they shortened their audit history is right — and entitled to know what that costs before it costs it. The honest answer is not a scary dialog; it is a complete one: the loss, the timing, and the survivors.

**Independent Test**: assert that a save lowering any of the three retention fields cannot complete in one activation; that the armed confirmation names the field, both limits, what will be deleted, when it will be deleted, and what survives; that a save raising a retention field completes in one activation; and that after a driven trim pass the trail holds one `audit.trimmed` row, still holds every protected row, and has no renumbered `seq`.

**Acceptance Scenarios**:

1. **Given** `auditRetentionDays` at 180, **When** the operator sets it to 30 and activates save once, **Then** nothing is written and a confirmation is armed naming the field, 180, 30, that the limit governs audit history, that entries older than 30 days will be deleted at the next trim pass, and what survives that trim.
2. **Given** the confirmation is armed, **When** the operator activates the armed control, **Then** the write happens, the confirmation closes, and the panel renders the configuration the service returned.
3. **Given** the operator raises `auditRetentionDays` from 30 to 90, **When** they save, **Then** one activation writes it and no confirmation is armed.
4. **Given** a non-retention field, **When** the operator changes it and saves, **Then** no confirmation is armed and one activation writes it.
5. **Given** an armed confirmation, **When** the operator navigates away or activates Cancel, **Then** nothing is written and the fields return to the last-read values.
6. **Given** `auditMaxEntries` at 50,000 with 400,000 rows already on disk, **When** the operator sets it to 100,000 and arms the confirmation, **Then** it states that the oldest unprotected entries beyond the new cap will be removed at the next trim pass, that nothing protected is ever removed to satisfy a cap, and that the trail may exceed the cap by exactly the protected set that was deliberately kept.

### User Story 5 — Explain a settings change months later (Priority: P2)

The operator changed the poll interval on a Tuesday. A month later something is dispatching more often than expected, and the question is *when did this change and who changed it*. The service's audit trail holds one row for that write, naming the operator as the actor, the fields that changed with their previous and new values, and the effect class each one carries — with **its own** correlation identifier, because a configuration change belongs to no run. A refused write also left one row, naming the fields that were refused and carrying **no submitted value**. If retention trimming runs — and with FR-055 it runs at every cycle boundary the trail is over its limits — the rows it removes leave a row of their own, and the rows that explain a run are never among them.

**Why this priority**: constitution IV — an operator must be able to explain why the machine behaves as it does. A settings write is the single most likely cause of "why is it doing that", and today it leaves no trace whatsoever.

**Independent Test**: drive an accepted write, a no-op write, and a refused write against a temp-directory store and assert exactly one row per event, with the shapes in `## Audit Rows`; assert a row for a run and a row for a configuration write carry **different** identifiers and neither adopts the other's.

**Acceptance Scenarios**:

1. **Given** an accepted write changing two fields, **When** it completes, **Then** exactly one audit row exists, with actor `operator`, decision `applied`, and one `field`/`from`/`to` triple per changed field.
2. **Given** a write whose document is identical to what is stored, **When** the operator saves, **Then** the panel reports *already saved*, and **no** audit row is written.
3. **Given** a refused write, **When** it is refused, **Then** exactly one row exists with decision `refused`, naming the documented fields refused, containing **no submitted value**, and containing no foreign key name.
4. **Given** a configuration row and a dispatch-lifecycle row, **When** both are read, **Then** each carries its own correlation identifier and neither carries the other's, and neither is forced onto a run.
5. **Given** a row was written and the audit trail is later trimmed, **When** the operator reads the trail, **Then** the trimming left its own row recording what it removed and why.

### Edge Cases

- **The operator edits a field and the service has never been read successfully.** There is no baseline to replace, so no write is offered and none is attempted. Offering a save here would mean the panel inventing the nine values it did not read.
- **The operator edits a field, then navigates to another tab and back.** 005 mounts a tab body once and keeps it mounted, so unsaved edits are still there; the tab says it has unsaved changes and offers an explicit discard that names what will revert. Leaving a tab is not a discard, because leaving a tab is not something the operator did to discard anything.
- **Two panels, one service.** The second write wins and overwrites the first. The panel states that a whole-file save replaces everything before it saves, and the confirmation names the fields it is about to change. A revision precondition is not added — confirmed as encoded at the gate, see `## Resolved Gate Questions` entry 2.
- **A config write races a scan cycle that reads the interval.** The scan finishes and the timer schedules with whatever it read. If the write landed first, the new interval is used; if not, the old one is, and the change applies at the cycle after that. The panel's `next-cycle` wording covers both.
- **A hand-edited `config.json` that fails validation.** The store quarantines it and the service answers with the documented defaults, exactly as it does today. The Settings tab renders those defaults and says the stored configuration was unusable and set aside — **not** that the operator's values are current. A quarantined configuration is a fact the operator must see.
- **A hand-edited `config.json` that is valid but holds a value the panel has never seen.** An eleventh field appears in the document. The panel renders it as *field this version does not show*, refuses to send a document containing it, and says why — because sending a document that silently drops an unknown field is exactly the drift this feature exists to remove.
- **The operator pastes a token as a field name.** The service withholds it (`<withheld>`) rather than echoing it; the panel renders that placeholder as ordinary text, never copies it into `host.storage`, and never logs it. A redaction refusal blocks the write rather than being logged past.
- **The operator pastes a token as a *value*.** There is no field for it — every field is an integer or one of four level names — so the value is refused by type and the remediation names the field and its range. The submitted text appears nowhere in the refusal.
- **`logLevel` is set to `error` while a poll cycle is failing.** The cycle's `warn` and `info` lines stop being emitted from that point on. That is what the operator asked for, and the confirm copy for `logLevel` says so, because a silent transition to "no output" reads as a broken service.
- **The operator sets `intervalMs` to the maximum, 300,000, while four bindings are active.** Nothing else changes: the cadence applies at the next cycle, no binding is paused, and no scan is cancelled. A configuration write never touches a binding, an account, a run, or a checkpoint (FR-049).
- **The operator sets `auditMaxEntries` to 100,000 with 400,000 rows already on disk.** The confirmation states what will be removed (the oldest unprotected entries beyond the new cap), when (at the next trim pass), and what survives (the protected minimal references, which are never removed to satisfy a cap — so the trail may exceed the cap by exactly that set). The value is accepted; the trim that follows is bounded by FR-055 – FR-056.
- **The protected set alone exceeds `auditMaxEntries`.** The cap applies to the trimmable remainder and no protected row is removed to satisfy it. The pass records `minimalReferencesPreserved` on its `audit.trimmed` row, so a trail larger than its own cap is an explained fact rather than a bug — this is 002 FR-035's floor meeting the bounding clause, and the floor wins.
- **A trim pass and an audit append run at the same moment.** They serialize on the same chain as `appendAudit`, so a pass can never remove a row appended while it was computing, and the pass accounts for its own `audit.trimmed` row before it decides how many to remove — a cap of N cannot oscillate around N one row per cycle.
- **A trim pass crashes mid-write.** The file is replaced atomically: the trail is either the pre-trim one or the post-trim one, never a torn file, and no `audit.trimmed` row exists for a removal that did not complete.
- **`retry-after` asks for longer than `retryMaxMs`.** The guidance wins — waiting longer than the operator's ceiling is what a secondary rate limit punishes — the wait is logged as a structured line naming its length and its source, and the next cycle is scheduled from the moment this one ends, so a long wait delays one cycle and never becomes a catch-up burst.
- **A credential GitHub refuses (401/403) during a scan.** It is never retried: `auth-failed` is a stop condition, not a transient error (002 FR-024; constitution II). The binding's scan ends with that skip reason, the checkpoint keeps the stamp it had, and the remaining bindings are still walked.
- **A `pending` event older than `excerptRetentionDays`.** Its excerpt is kept, whatever its age: the dispatch that will use it has not been sent yet, and a retention limit may not silently empty a message the operator has not dispatched. Excerpt trimming touches terminal rows only.
- **The operator widens `overlapMs` after a queue recovery cleared a binding's stamp.** The first cycle after the recovery still replays with no window at all (there is no stamp to widen); the cycle after that opens `lastScanAt − overlapMs`. The widened window re-observes items the previous cycle already saw, and the deterministic event id drops them — no second event, no second dispatch, no second session.
- **The operator raises `perPage` to 30 with `MAX_LIST_PAGES` at 2.** One scan reaches two pages of 30 rather than two pages of the old size; the row copy says the reachable history is `2 × perPage` and does not imply the page count grew.
- **A save is refused because the service is unwritable, not because the document is wrong.** The panel distinguishes *the service refused these values* from *the service could not be reached or could not write*, because conflating them teaches the operator to re-edit a document that was fine.
- **The operator presses save twice quickly.** One write runs; the second is refused by the existing busy gate; no field flips optimistically before the service answers.
- **The audit trail cannot be written when the configuration is written.** The configuration write itself still succeeds — it is the durable record — but the missing row MUST be surfaced as a visible warning and recorded in the service's structured log. The panel MUST NOT imply complete traceability it does not have (003 FR-063's rule, applied here).
- **A refusal arrives for a field the panel has no control for** — an unknown field name or `body`. It renders as a read-only line with its remediation, offers no affordance, and does not drop it.
- **The operator's last read predates a service restart.** The values on screen are the pre-restart ones and the tab marks them with when they were read. A save replaces the whole document from that baseline; the last-writer-wins rule applies and is stated.
- **The extension is running on a surface that spawns no service.** 005's unsupported-surface notice shows and the Settings tab renders its static content only, with no edit affordance — an edit control that cannot possibly work is worse than none.
- **`host.storage` was wiped.** Nothing about the configuration is lost: the durable configuration is `config.json` in the service store, and the panel's unsaved edits are not durable state (FR-005).
- **The operator closes the panel with an unsaved edit.** The edit is gone; nothing was written and nothing is claimed to have been written.

#### A. Authority, scope, and invariants

- **FR-001**: This specification is the **authoritative** text for the Settings edit capability, the take-effect contract for every configuration field, and the configuration audit rows. It **supersedes** exactly two requirements of `specs/005-panel-ia/spec.md` v1.0.0 — **005 FR-070** (the tab is read-only) and **005 FR-073** (the tab states it is read-only) — and **extends** 005 FR-011, FR-013, FR-014, FR-016, FR-019, FR-039, FR-059, FR-071, FR-072, FR-078, FR-080 – FR-085, FR-088; 002 FR-007, FR-024, FR-031, FR-035, FR-036, FR-039; and 003 FR-052, FR-061, FR-063. Every other requirement of 002, 003, 004, and 005 stands unchanged and is **referenced, not restated**. Where the documents could be read as disagreeing about **whether the Settings tab is editable**, this document prevails; 005 remains authoritative for the tab's composition and the six-tab shell, 003 for the run model, and 002 for credential custody and the read-only-to-GitHub posture.
- **FR-002**: The extension and the service MUST remain **read-only with respect to GitHub** (002 FR-031, 003 FR-002, 005 FR-002). A configuration write is a local durable-store write and nothing else. No requirement in this specification may be satisfied by a GitHub write, and no setting may be expressed as a GitHub mutation.
- **FR-003**: The system MUST fail closed in the way 002 FR-024 and 005 FR-003 require. A write the service refuses MUST change nothing. A save with no current baseline MUST be refused **before** any request is sent, naming the cause. A configuration write MUST NOT be applied partially, optimistically, or speculatively: the only rendered configuration after any outcome is the one the service last reported.
- **FR-004**: This specification MUST NOT introduce a host capability, API, permission, or private interface (005 FR-004, 003 NFR-110, `AGENTS.md` invariant 3). `capabilities[]` remains exactly `sessions` and `prompt`; `contributes.service` gains no `permissions` key; the manifest id remains `mecha-turk`; the SDK pin and engine floor (`>=1.24.0`) are unchanged.
- **FR-005**: A configuration write MUST touch **exactly one** durable file: `config.json` in the service store. It MUST NOT quarantine, discard, or reset any binding, account, checkpoint, event, dispatch, run, audit row, credential, or `host.storage` entry, and MUST NOT add, rename, or remove a `host.storage` key. Unsaved edits are panel memory and are **not** durable state; a wiped `host.storage` therefore costs the operator nothing here, and the durable configuration remains the operator-backable store the constitution's durability standard names.

#### B. The edit surface inside 005's tab

- **FR-010**: The ten read-only rows 005 FR-071 renders **become editable fields in the same rows, the same tab, and the same order**. This feature MUST NOT add a tab, a sub-tab, a drawer, a dialog-per-field, or a second configuration surface, and MUST NOT move a row to a different tab. The rows 005 renders and the fields this feature renders are one list, not two.
- **FR-011**: **The transition is explicit and two-way.** Before this feature's capability is present, or whenever no write is possible (FR-060), the tab is 005's read-only rendering and states so. Once the capability is present and the service is answering, the same rows render as fields. There MUST NOT be a state in which the tab shows editable-looking controls that cannot save, and there MUST NOT be a state in which it shows read-only text while a save is available.
- **FR-012**: **There is one save, not ten.** The tab MUST NOT offer a per-field save, a per-field apply, or an implicit save on blur. A write is a whole-document write (FR-040, FR-041), so a control implying per-field granularity would be a lie about the mechanism.
- **FR-013**: The tab MUST display its **save state** distinctly from 005's **read state** (005 FR-019): idle, editing with unsaved changes, saving, saved with the service's returned configuration, refused with the service's reasons, or failed with the transport cause. A save in progress MUST be visible, and a second activation during it MUST be refused rather than queued (FR-046).
- **FR-014**: Each field MUST carry, in its own row: the field's **documented name**, its **unit**, its **bounds**, its **current effective value**, and its **take-effect boundary in the product's own words**. Every one of the five is rendered from the service's declaration (FR-020, FR-022) and none from a value typed into the panel.
- **FR-015**: The tab MUST show which fields have unsaved changes and MUST offer an explicit **discard** that states what will revert. Discarding MUST be explicit and MUST NOT be a side effect of navigating, refreshing, or switching tabs (005 FR-013 keeps the body mounted, so there is no unmount to hang a discard on).
- **FR-016**: **Restore defaults** MUST be offered as a whole-document write of the service's declared defaults for all fields, MUST name every field it will change, and MUST use the two-step confirmation of FR-051. It MUST NOT be the primary control on the tab and MUST NOT be offered in a state where no save is possible.
- **FR-017**: The tab MUST NOT render any credential, token, scope, or account control. Token and credential configuration is Accounts, owned by 002 FR-006 and 005 FR-060 – FR-069; nothing here moves it (FR-082).
- **FR-018**: Every field, the save control, the discard control, the reset control, and both confirmation steps MUST be operable by keyboard alone with visible focus and no trap, and MUST expose an accessible name that carries the field's name and unit (005 FR-016, FR-081, FR-082).
- **FR-019**: **The Status/Settings split 005 FR-039 establishes is unchanged and load-bearing.** Status states the **effective** value the scheduler is running with; Settings states the **configured** value. Neither tab may present a value the other owns, and when they differ both MUST show and name the difference (FR-038). The Bindings tab MUST NOT render service tuning (005 FR-059), and this feature adds nothing that would tempt it to.

#### C. One declaration: field schema, units, bounds, and no duplicated validation

- **FR-020**: **`GET /v1/config` MUST widen to carry the configuration's declared schema alongside the effective document.** The service MUST return the effective `ServiceConfig` **and** a projection of the **same declaration the validator reads** — one bounds table, one level set, one default document — rendered as a per-field list. The requirement is *one declaration, read twice*; the mechanism is deliberately unconstrained here and is Phase 4's to fix, provided the two reads cannot diverge. The delivered service is `GET /v1/config → { config, fields }`; the field's exact member names are finalized in Phase 4's contract work. This is the only wire change this feature makes to a **read**.
- **FR-021**: Each entry in that projection MUST carry: the field's **name**; its **kind**, from a closed set (`integer` or `enum`); its **unit** where one applies; its **minimum and maximum** for a bounded integer; its **accepted values** for an enum; its **documented default**; and its **take-effect class** from the closed vocabulary `immediate | next-cycle | restart | none`. Every vocabulary this feature introduces is closed: a value outside it MUST be refused or passed through verbatim, never mapped to a guess (005 FR-003).
- **FR-022**: **The panel MUST carry no copy of any bound, unit, default, accepted-value set, or take-effect class.** Every label, hint, minimum, maximum, step, and option list the Settings tab renders MUST come from the service's projection. This is 005 FR-071's rule ("each bound is the service's own, not a re-typed copy that can drift from it") given an enforcement mechanism: a suite-level assertion that the panel source contains no configuration bound literal fails if one appears.
- **FR-023**: **The service is the only validation gate.** The panel MUST NOT reject a value for being out of range, fractional, of the wrong type, or outside the declared enum **before** sending it. Declared minimum, maximum, step, and option lists are **presentation affordances** — they shape the control and the hint text and nothing else. The panel MUST NOT pre-emptively accept a value the service would refuse by suppressing it, silently coercing it, or rounding it into range (005 FR-052). A client-side guard that changes what the service is asked is a second validator, and two validators drift.
- **FR-024**: **A refusal is rendered as the service wrote it.** On a validation refusal the panel MUST render the service's own issue list: every `field` and its `remediation`, in the order the service returned them, with none omitted, none added, and none reworded. The panel MUST NOT synthesize a second message, MUST NOT merge two issues into one line, and MUST NOT replace the service's remediation with its own wording. It MUST NOT echo the value the operator submitted anywhere — not in the issue list, not in a field hint, not in a log, not in `host.storage` (002 FR-039; 005 FR-085).
- **FR-025**: **A refused write applies nothing.** After any refusal the panel MUST return every field to the configuration the service last reported, MUST present the previous values as still in force, and MUST NOT report the operator's edit as saved, partially saved, or pending. Because the write is whole-document, "partially saved" is not a reachable state and the panel must not let the operator believe otherwise.
- **FR-026**: A service issue whose `field` is an **unknown key name** — which the service echoes for ordinary-looking names and replaces with a withheld marker for a secret-shaped one — MUST be rendered as ordinary text through the non-HTML path, MUST NOT be interpreted as a configuration field, MUST NOT become a control, and MUST NOT be copied into `host.storage`. An issue that names no known field is information about the submission, never an editable surface.
- **FR-027**: **Forward compatibility.** A field the panel does not recognise MUST render as *field this version does not show*, with its remediation, and MUST be offered no affordance. The same rule 005 FR-041 sets for an unrecognised dispatch state applies verbatim: forward compatibility beats a tidy rendering of something the panel cannot reason about.
- **FR-028**: A configuration document the panel cannot fully parse MUST render every field that did parse, render every field that did not as *unreadable* with the remediation, and MUST NOT fall back to showing a documented default as though it were configured. The document's fields are **never** filled in from the projection's `default` values on the panel's initiative (005 NFR-112).
- **FR-029**: **Every string the Settings tab renders from the service declaration is untrusted.** Field names, units, remediation text, accepted-value labels, and echoed key names all originate in a service response or in operator input and MUST render through the SDK's non-HTML path — no markup interpolation, no attribute assembled from source text (005 FR-080). The remediation text is the sharpest case in the whole panel: it is free-form prose chosen by the service about a value the operator submitted, and it is the one string on this tab that is not a fixed label.

#### D. Take-effect boundaries

- **FR-030**: **Take-effect is a per-field, service-declared, closed-vocabulary fact.** Each field's declared class MUST be `immediate`, `next-cycle`, `restart`, or `none`, and the panel MUST render it in the product's own words **next to its field** and as part of that field's accessible name. The panel MUST NOT invent a class, MUST NOT infer one, and MUST NOT render a class the service did not declare (005 FR-072; 005 NFR-112).
- **FR-031**: **A declared class is a tested claim.** Every field's declared take-effect class MUST be backed by an automated test that observes the actual behaviour of the running service, and every **consumer** this specification specifies MUST be observed doing its job: a test for `next-cycle` observes two cycles against a driven clock and the consumer actually reading the new value — the timer scheduling with the new interval, the window computed as `lastScanAt − overlapMs`, the list request carrying the configured `per_page`, the backoff computed from the configured base, ceiling, and attempt count, a trim pass removing what the new limit says it removes while every protected row survives; a test for `immediate` observes the first log line after an acknowledgement without a restart; and a test for `none` — a class **no field in this feature declares as of v1.1.0** — observes that a value change alters nothing over at least one full cycle, and its harness stays in the suite for the day a genuinely inert field is added. A field whose class is declared and not delivered MUST **fail the suite**. This is what makes the declaration trustworthy rather than decorative, and it is the requirement that would catch a future code change silently invalidating a label an operator reads.
- **FR-032**: **`intervalMs` is `next-cycle`.** The new value MUST be used when the cycle in flight ends, to schedule the following one. A timer already armed MUST keep the delay it was given; the worst case between a save and the new value being in force is one full cycle at the old interval plus the running cycle. The panel MUST state *in effect from the next poll* and MUST NOT state that the change has already taken effect. **No restart is required and no manual poll is required** — the poll loop re-reads the interval itself, which is why this field needs nothing new from the service (evidence in `## Per-Field Contract`).
- **FR-033**: **`logLevel` is `immediate`, and this feature requires the service to deliver it.** The first log line emitted after a save of `logLevel` is acknowledged MUST be judged at the new threshold, with no restart, no re-read of the whole document, and no operator action beyond the save. **Today the service delivers neither this nor `restart`**: `service/main.ts` constructs the logger with a hardcoded level before the store is opened, and the threshold is captured once at construction, so the configured value has no effect at all. Closing that gap is a requirement on the service, not a nicety, and it is the reason this field is `immediate` rather than `restart` — the whole change is to stop treating the threshold as a constant (FR-037).
- **FR-034**: **`overlapMs` and `perPage` are `next-cycle`, each with a real consumer (FR-059).** `overlapMs` widens the scan window backward from the recorded stamp; `perPage` is the `per_page` of every list request and is bounded at 30 by its own maximum. The panel MUST state each boundary in the product's own words and MUST NOT overstate either: raising `overlapMs` widens the look-back the service will re-observe — and it is **dedupe**, not new dispatches, that handles the re-observation — while `perPage` changes the size of a page and not the two-page cap that bounds what one scan reaches. Neither row may describe the other's effect, and neither may claim an effect the other's consumer has.
- **FR-035**: **`retryMaxAttempts`, `retryBaseMs`, and `retryMaxMs` are `next-cycle`, with exactly one consumer: the HTTP-poll retry path (FR-058).** The three configure a bounded, jittered exponential backoff over a single list request inside a scan, read with the rest of the polling configuration at the cycle boundary. The cross-field rule that the retry ceiling may not sit below the retry base **is** enforced and **is** refused by the service, and the panel MUST reflect that the constraint is real. **The panel MUST label these rows as poll-request retry** — *requests*, *attempts per request*, *backoff between attempts* — and MUST NOT use the vocabulary of 003's run model: not *requeue*, not *run attempts*, not *retry budget*. 003 FR-033's automatic requeue bound, 003 FR-041's operator retry, and this ladder are three different mechanisms with three different owners, and one label covering two of them is exactly how a reader comes to believe a dial does something it does not (FR-058's disambiguation clause).
- **FR-036**: **`auditRetentionDays`, `auditMaxEntries`, and `excerptRetentionDays` are `next-cycle`, each consumed by a trimming pass (FR-055, FR-057).** The three knobs do what their names say: the audit trail is bounded by the first two and the stored payload excerpts age out under the third, at the cycle boundary (and once at store open). The panel MUST say so plainly on each of the three rows, MUST name what each limit governs — the audit trail, the entry cap, the stored payload excerpts — and MUST NOT state a retention fact it cannot verify: in particular it MUST NOT promise a trim outcome for a state it has not read, and it MUST NOT claim that nothing is deleted (FR-052, NFR-112).
- **FR-037**: **No field may declare `restart` in this feature, and `immediate` may not be downgraded silently.** `logLevel` has a plausible `restart` boundary — the logger is built once at startup — and `immediate` was chosen deliberately: it is the cheapest field to make genuinely live, and as of v1.1.0 **every field in this feature is live**, so the take-effect contract is demonstrable rather than theoretical. If Phase 4 finds `immediate` infeasible for that field, it MUST reclassify it to `restart` **and return the change to the product owner**, because the panel's copy, the confirmation text, and the test that backs the declaration all follow from the declared class, and an owner-visible promise changed by the implementer is the failure mode this document exists to prevent. Any *new* field may not declare `restart` here either: a `restart` boundary is a real operational cost to an operator and is a product decision, not an engineering default.
- **FR-038**: **Configured and effective are distinguished everywhere they can differ.** After a save that changes a field whose class is `next-cycle`, the panel MUST mark that field as **pending**, naming the boundary that governs it, until a read reports the new value as effective. In the interim, Status shows the effective value and Settings shows the configured value, each owning what it owns, and **both name the difference** (005 FR-039). The pending marker MUST clear when the effective value catches up and MUST NOT be cleared optimistically on save.
- **FR-039**: **The take-effect statement is not a footnote.** Each row's boundary MUST be visible without opening anything, MUST be part of that field's accessible name, and MUST NOT be collapsed into a single tab-level disclaimer — a per-field promise that lives once, at the bottom of the tab, has effectively been made about nothing.

#### E. The write path

- **FR-040**: **The panel writes with `PUT /v1/config` and nothing else.** There MUST be no `PATCH`, no per-field endpoint, no partial document, and no second write path introduced or composed (005 FR-088's single-path rule; 002's recorded MVP-DEBT decision against a per-binding `PATCH`, which this feature does not reopen for configuration either). The service's shipped semantics — whole-document replacement, validation before any storage access, atomic write, additive refusal — are the semantics this feature relies on and MUST NOT relax.
- **FR-041**: **The write is a whole-document replacement built from the last read.** The panel MUST hold the configuration the service last reported and MUST send that document with the operator's edits applied. It MUST NOT send a partial document, MUST NOT send a document assembled from fields it has not read, and MUST NOT infer any field's value from a documented default to fill a gap. The service refuses unknown keys and missing fields precisely so that a partial or invented document cannot be applied; a panel that assembled one anyway would be working against a guard that exists for its benefit.
- **FR-042**: **A save requires a current baseline and refuses to guess one.** When the configuration has never been read successfully, or the latest read failed, or the document is unreadable in any field, the tab MUST NOT offer a save and MUST name the reason. No request is sent in that state. Offering a save the panel cannot honour would produce a whole-document write containing values the panel invented, which the service would refuse at best and apply at worst if every default happened to be in range.
- **FR-043**: **A configuration refusal names the configuration, and its body is preserved.** The shared service-call layer currently maps a validation refusal to a message naming the **bindings** list and discards the refusal body, so a configuration refusal rendered through it would both misname the resource and hide the very issues this feature exists to show. The layer MUST be extended so that a configuration write's refusal retains its machine code and its issue list, and its operator-facing problem string names the configuration. It MUST be **extended, not forked**: one wrapper set, one place that classifies a service answer (005 FR-088).
- **FR-044**: **After a write the panel renders what the service returned.** On success the tab MUST render the configuration the service's own response carries — not the submitted document, not a local merge, and not an optimistic update applied before the answer arrived. On failure the tab renders the last configuration the service reported. The panel MUST NOT report a save it has not been told succeeded.
- **FR-045**: **Last-writer-wins is the documented concurrency rule, and it is stated.** A write replaces the entire document, so two panels — or a panel and a hand-edit — produce a last writer and a lost update. The panel MUST state that a save replaces the whole configuration before the operator commits it, MUST name the fields it is about to change, and MUST NOT imply a merge, a field-level lock, or a conflict detection it does not perform. This is consistent with `PUT /v1/bindings`, which 005 FR-058 already accepts on the same basis, and with the documented deployment of one operator, one panel, and one service instance (005 `## Assumptions`).
- **FR-046**: **One save, one call.** Activating save MUST issue exactly one write. A second activation while a write is in flight MUST be refused by the existing busy gate rather than queued or coalesced, and no field may flip optimistically before the service answers (005 FR-049's rule applied to this tab).
- **FR-047**: **A configuration write MUST NOT do anything else.** It MUST NOT change a binding, an account, a credential, a dispatch, a run, a checkpoint, a scan window, or the poll loop's armed schedule beyond the interval re-read the loop already performs each cycle. It MUST NOT trigger an immediate scan, MUST NOT pause or resume polling, MUST NOT run a retention trim — trimming is a cycle-boundary consumer (FR-055, FR-057), so a save changes the limit and the *next* pass applies it — and MUST NOT invalidate any cached projection another tab renders. The only durable files it may write are `config.json` and — as an audit record of the write — the audit trail (FR-005, FR-049).
- **FR-048**: **A no-op write is reported as one and leaves no trace.** A write whose document is identical to the stored one MUST be accepted, MUST render as *already saved* rather than *changed*, and MUST NOT append an audit row. An audit trail that records every double-click as a configuration change stops being evidence of anything.
- **FR-049**: **A write MUST NOT be triggered by looking.** Opening the tab, switching to it, refreshing it, completing a read, or returning to it MUST issue no write. A panel that changes configuration because it was read is a panel that cannot be read.

#### F. Retention knobs, confirmation, and the five wired consumers

- **FR-050**: `auditRetentionDays`, `auditMaxEntries`, and `excerptRetentionDays` are **retention knobs**: each governs a bound on stored history. Lowering any one of them MUST be treated as a change with a named consequence, distinct in the panel's treatment from every other numeric field.
- **FR-051**: **Lowering a retention knob requires a two-step confirmation.** A write that **lowers** any of the three retention knobs MUST NOT complete on one activation. One activation arms a confirmation that names the field, its current limit, its proposed limit, and what the limit governs. A second activation on the armed control performs the write. **Raising** a retention knob, and changing any non-retention field, MUST complete in one activation and MUST NOT arm anything — a confirmation that appears for an action with no consequence trains the operator to click through the one that matters.
- **FR-052**: **The confirmation MUST tell the truth about what will be deleted.** It MUST state the field, the current limit, the proposed limit, and what the limit governs; and because lowering a retention limit **now deletes**, it MUST also state, in the product's own words: **what** will be removed (audit entries older than the proposed window, or the oldest unprotected entries beyond the proposed entry cap, or stored payload excerpts older than the proposed window — whichever limit the change trips); **when** (at the next trim pass, which runs at the poll-cycle boundary after the change is in force, and once at service start); and **what survives** — the minimal references FR-056 protects (the row that opens a run's chain, the row that records its outcome, account/binding rows, and decision rows) are never removed, so a run remains explainable, and the trim appends an `audit.trimmed` row recording exactly what it took (FR-073). It MUST additionally state that **raising** a limit deletes nothing, and that trimming is irreversible because this feature adds no restore path (`## Out of Scope`). A confirmation that names only the danger is as untrue as one that names only the safety; the operator is entitled to the whole of it — the loss, the timing, and the survivors — before they commit.
- **FR-053**: **Any removal that retention causes MUST be audited.** The trimming passes FR-055 and FR-057 append one row recording the entries removed, the oldest and newest sequence numbers removed, which limit was reached (the day window, the entry cap, or the excerpt window), and the count of minimal references deliberately preserved (002 FR-035; 003 FR-065; this feature's FR-056 and FR-073). The row is appended **after** the removal succeeds; no row may be written for a trim that did not happen, and a pass that removed nothing writes no row.
- **FR-054**: **The confirmation is a panel affordance, not a browser dialog.** It MUST use the existing arm-then-act idiom (005 FR-084, 005 FR-055) and MUST NOT reintroduce `confirm()` or any equivalent through another route. It MUST be dismissible, MUST return the fields to their last-read values on dismissal, and MUST be reachable and completable by keyboard alone. Its text MUST render through the non-HTML path, because it is composed partly from service-declared units and bounds.

> **FR-055 – FR-059 were added by the v1.1.0 gate revision** (answer 1: *"Also wire all fields (~3× size)"*), inside block F's reserved numbers. Each is the consumer a `## Per-Field Contract` row points at; each MUST be observable by a test (FR-031) and each is bounded by the predecessors' text it serves.

- **FR-055**: **`auditRetentionDays` and `auditMaxEntries` are consumed by a real trimming pass over `audit.ndjson`.** The pass runs **(a)** once when the store opens and **(b)** at every poll-cycle boundary, reading the **stored** configuration each time, so a saved limit is in force from the first boundary after the acknowledgement (`next-cycle`). It removes the **oldest** entries first, skipping the protected set FR-056 defines, until both limits are satisfied — the day window and the entry cap, **whichever trips first** (002's data model: 180 days or 50,000 entries at the defaults). The pass MUST account for the `audit.trimmed` row it is about to append: after the pass and that append the trail MUST sit at or below the entry cap, so a cap of N cannot oscillate around N one row per cycle. Surviving rows keep their original **`seq`** — a trim never renumbers — and `seq` gaps after a trim are an expected, readable fact. The file MUST be replaced atomically, so a crash leaves either the old trail or the new one and never a torn file, and the pass MUST serialize with appends on the same chain `appendAudit` uses, so it can never remove a row appended while it was computing. Until v1.1.0 no trimming pass existed and `audit.ndjson` grew without bound; this requirement discharges the deferral `service/audit.ts:13` records for **trimming** — the correlation-indexed read API that shares that sentence is **not** added (see `## Out of Scope`).
- **FR-056**: **What a trim preserves: 002 FR-035's floor, written as a rule the pass cannot violate.** Retention MUST NOT delete the minimal references required to explain a run. A row is **protected** — never removed by a trim, at any age and at any cap — when it is any of: **(a)** the **opening** row of a correlation chain that contains a run-scoped row, which says what the work was and where it came from; **(b)** the **outcome** row of that chain, which records the decision that ended it; **(c)** a row whose entity is an `account` or a `binding` (credential identity, consent, binding decisions) while that account or binding still exists — 002's data model: "minimal references (ids/links/decisions) kept until the account/binding is deleted"; **(d)** a row recording a policy or configuration decision (`policy.decision`, `config.changed`). **How a run's chain survives**: the opening and outcome rows share the chain's correlation identifier and are never removed, so a correlation read still answers *what this run was* and *what happened to it* even when the observations between them are gone — and the gap is explained rather than mysterious, because the `audit.trimmed` row that removed those entries records the oldest and newest `seq` it took (FR-073). Operator-visible run history is unaffected in any case: it is read from the runs store (003), not from the trail. **Where the floor meets the cap**: if the protected set alone exceeds `auditMaxEntries`, the cap applies to the trimmable remainder and the trail may exceed the cap by exactly the protected set; the pass MUST NOT remove a protected row to satisfy a cap, and `details.minimalReferencesPreserved` on the trim row records what was deliberately kept. A trim that would leave a chain with an outcome but no opener (or the reverse) MUST remove neither.
- **FR-057**: **`excerptRetentionDays` is consumed by a trimming pass over the stored payload excerpts in `events.json`.** The stored excerpt is `QueuedEvent.issueBodyExcerpt` (`service/poll/events-parse.ts:59`), bounded at enqueue (`service/poll/triggers.ts:41`, 600 characters) and read only by the dispatch path (`src/relay.ts:207`); `GET /v1/events` never returns it, so no rendered surface depends on it. The pass runs on the same boundary and from the same stored configuration as FR-055's, and it clears the excerpt **only** on rows that are **(i)** older than the configured window **and (ii)** in the terminal `dispatched` state — rows no read and no dispatch can reach again, since a `dispatched` event answers `409` to `POST /v1/events/:id/retry` and cannot return to the queue. It MUST NOT clear the excerpt of a `pending` or `in-flight` row at any age: that excerpt is context for a dispatch that has not been sent yet, and a retention limit may not silently empty a message the operator has not dispatched. A cleared row keeps **everything else** — id, state, claim and dispatch stamps, repository and issue identity, correlation identifier — so dedupe, history, and correlation are untouched; only the payload text goes, which makes this pass strictly gentler than the dispatched-tail cap (`MAX_DISPATCHED_EVENTS = 500`) that already drops rows wholesale and which this feature does not change. A cleared excerpt MUST be distinguishable from a row that never carried a body (`issueBodyExcerpt: ''` at enqueue) through a machine-readable marker that survives a store round-trip; the mechanism is Phase 4's, the distinction is this requirement's, because a reader must never conclude *this issue had no body*. Each pass that actually clears rows appends one `audit.trimmed` row with `limitReached: 'excerpt-days'` (FR-073); a pass that clears nothing appends nothing. 002's data model places "Trims write an `audit.trimmed` entry first (the trim itself is auditable)" in the same retention line that sets payload excerpts to 30 days, which is why this pass uses the reserved name; **this specification fixes the order** — the row is appended **after** the removal succeeds, because a row describing a removal that did not happen is worse than no row.
- **FR-058**: **`retryMaxAttempts`, `retryBaseMs`, and `retryMaxMs` are consumed by a bounded exponential backoff on the polling/GitHub request path — and by nothing else.** One list request (issues, comments, or pull requests) MAY be attempted up to `retryMaxAttempts` times, **the first attempt included**. The delay before attempt *n* is `min(retryMaxMs, retryBaseMs × 2^(n−2))` multiplied by a jitter factor drawn uniformly from `[0.5, 1.0]`, so every delay lies in `[retryMaxMs / 2, retryMaxMs]` and none ever exceeds the ceiling; the jitter source MUST be injectable so tests are deterministic. When GitHub answers with `retry-after` or rate-limit reset guidance, the delay is **at least** that guidance — the guidance wins even when it exceeds `retryMaxMs`, because waiting longer than the operator's ceiling is what a secondary rate limit punishes — and the wait MUST be logged as a structured line naming its length and its source, with no secret material. **`auth-failed` (401/403) is never retried**: a credential GitHub refuses is a stop condition, not a transient error (002 FR-024; constitution II). When the attempts are exhausted the binding's scan ends with one honest skip reason, the cycle MUST keep walking the remaining bindings, and **the checkpoint is preserved**: the binding's recorded `lastScanAt` MUST NOT advance past data that was not durably represented (002 FR-018, 002 FR-020) and MUST NOT be cleared either — the stamp is **retained**, so the next successful scan re-covers the failed period through `lastScanAt − overlapMs` instead of falling back to a full replay, which is what the shipped skip path does today (`service/poll/loop.ts:418-431`, `lastScanAt: scan.windowFrom` with `windowFrom: null`) and what this requirement changes. **No catch-up burst**: the next cycle is scheduled from the moment the current one *ends*, after any backoff, so a long rate-limit wait delays one cycle and never produces a burst of cycles to make up for it — a property `service/poll/timer.ts` already has, stated here so the retry implementation cannot lose it. **This knob is HTTP-poll retry, not run requeue.** It is bounded per request, inside one scan, and consumed by the service's GitHub list calls; it is **not** 003's automatic requeue budget (003 FR-033 — deferred here as `requeueBudget`, gate answer 4), **not** 003's run attempt counter (003 FR-041), and **not** the operator's own retry of a run (`POST /v1/events/:id/retry`). The panel's copy for these three fields MUST use the poll-retry words (*requests*, *attempts per request*, *poll backoff*) and MUST NOT use *requeue*, *run attempts*, or *retry budget*; a reader must never be able to conflate the two ladders (FR-035).
- **FR-059**: **`overlapMs` and `perPage` are consumed by the scan window and the list request.** **(a) Overlap:** `windowFor` (`service/poll/loop.ts:156`) returns the recorded `lastScanAt` **minus `overlapMs`** as the `since` stamp instead of the bare stamp; a binding with no recorded stamp still replays with no window at all, exactly as today. The widened window re-observes items the previous cycle already saw, and the deterministic event id in `enqueueEvents` (`service/poll/events.ts:347-358`) drops them, so a doubled window cannot produce a second event, a second dispatch, or a second session (002 FR-019's dedupe clause; constitution III). **This closes a conformance gap**: 002 FR-019 has required a configurable 10-minute overlap since 002 v1.1.0, and until this feature **nothing in the service read `overlapMs`** — the default of 600,000 ms is exactly 002's 10 minutes. **(b) Page size:** every list request carries `per_page = perPage`, whose own maximum is 30, so 002 FR-020's ceiling (`per_page` MUST NOT exceed 30) is preserved as the field's bound and configurability lives inside it. `MAX_LIST_PAGES = 2` is **not** changed: one scan still reads two pages, the reachable history is `2 × perPage`, and the row copy must say exactly that rather than implying the page count grew (FR-034). Both consumers read the stored configuration once at the start of the cycle and use those values throughout it, which is what makes both fields `next-cycle`.

#### G. Refusals and failure states

- **FR-060**: **The service is not running.** When the service cannot be reached, the tab MUST keep 005's static content, MUST name the configuration as what could not be read and the service as where it comes from, and MUST read **service not running — settings read-only**. It MUST render **zero input controls and zero save affordances** — the read-only view 005 specified, in the state where a write is genuinely impossible. It MUST NOT present a previously read value as current without marking when it was read (005 FR-019, FR-078).
- **FR-061**: **The store is unavailable.** A `503 storage-unavailable` refusal MUST render with that distinct cause and the setup-prerequisite framing 002 FR-039 defines, MUST be distinguishable from a document the service refused on its merits, and MUST NOT be retried automatically by the panel. The operator's edit MUST NOT be reported as saved, and the panel MUST NOT fall back to an optimistic local value.
- **FR-062**: **The grant is absent.** An unauthorised answer MUST render as *not authorised* and MUST NOT be retried in a loop. Authorization is the host's to grant and the panel's to refuse to work around (constitution II; the panel MUST NOT attempt to obtain configuration authority by another route).
- **FR-063**: **A transport failure is a failure, not a refusal.** An unreachable service, a closed connection, and a body that could not be read MUST render as one distinct cause naming the transport, MUST NOT be reported as *the service refused your values*, and MUST NOT show a value the panel has not read from the service. A panel that conflates "could not ask" with "was told no" teaches the operator to re-edit a document that was fine.
- **FR-064**: **An unexpected failure is visible and identified.** A failure the service did not document MUST render with the envelope's own correlation identifier where one is present, as copyable text, and MUST NOT retry automatically. The panel MUST NOT imply complete traceability it does not have (003 FR-063's rule, applied to this tab).

#### H. Audit

- **FR-070**: **A configuration write is an audited operator action, and it introduces no new audit vocabulary.** The event type is **`config.changed`** — the name `specs/002-agent-event-extension/data-model.md` already reserves for exactly this and which no shipped code has yet written. This feature MUST NOT invent a second name for a configuration change, and MUST NOT reuse a dispatch-lifecycle prefix for it: a `config.` row is a configuration row, distinguishable at a glance from `dispatch.`, `run.`, and `agent.` rows (003 `## Audit Vocabulary`'s prefixing note). The entity is the existing legal kind `service`, identified as the configuration (002's data model reserves `service` for entries referencing no account). Exactly one row is written per accepted write that changed something (FR-048) and exactly one per refused write (FR-072).
- **FR-071**: **Accepted-write row shape.** `eventType: 'config.changed'`; `actorSource: 'operator'` when the write arrived through the panel and `'service'` otherwise; `entity: { kind: 'service', id: <the configuration> }`; `decision: 'applied'`; a secret-free `reason` naming that the configuration was replaced; `details.changes`: one `{ field, from, to }` triple per **changed** field, ordered by field name, restricted to the documented fields; and `details.takesEffect`: the declared take-effect class of each changed field, so a reader knows from the row alone whether the change was live at write time. `from` and `to` are bounded integers or one of the four accepted level names — the configuration document holds no credential-shaped member by construction, and the audit writer's redaction pass runs over the row regardless. Recording both sides is what makes the row explanatory months later; a row saying only *intervalMs changed* cannot answer *from what*.
- **FR-072**: **Refused-write row shape, and the value-free rule.** A refused write MUST append one row: `eventType: 'config.changed'`, the same actor and entity, `decision: 'refused'`, a reason naming that the configuration was refused, and `details` carrying the **count** of issues plus the **documented** field names they named, with any withheld marker preserved as withheld. It MUST carry **no submitted value** — not the offending value, not an accepted value, not a length, not a hash — and MUST carry **no foreign key name**: an unrecognised key appears as a fixed withheld marker, which is strictly narrower than what the refusal body itself carries, and no wider record of operator input belongs in a durable trail. A redaction refusal MUST block the write rather than being logged through (003 FR-061; 002 FR-007).
- **FR-073**: **Trim row shape.** Both trimming passes append `eventType: 'audit.trimmed'` — the name 002's data model already reserves — with `actorSource: 'service'`, the same configuration-or-service entity, `decision: 'trimmed'`, a reason naming which limit was reached, and `details` carrying the entries removed, the oldest and newest sequence numbers removed, the limit that was reached (`day-window`, `entry-cap`, or `excerpt-days`), and the count of minimal references deliberately preserved (FR-053, FR-055 – FR-057; 003 FR-065). The row is appended **after** the removal succeeds and **only when a pass actually removed something**: a pass that removed nothing writes no row, and a row describing a removal that did not happen is worse than no row. A row's `seq` is the next in the trail's own sequence — a trim never renumbers, so gaps in `seq` are the visible signature of one.
- **FR-074**: **Correlation discipline: a configuration write has no run, and does not pretend otherwise.** Per 003 FR-052, a row that is not about a work unit keeps its own generated identifier and MUST NOT be forced onto a run's correlation identifier. A configuration row therefore mints **its own** correlation identifier, records **no** run reference, and MUST NOT adopt, re-derive, or overwrite a run's identifier — the same defect 003 FR-062 corrected for dispatch rows. It is retrievable through the audit read under its own identifier, and a run-filtered view excludes it. An operator asking "which run did this configuration change affect?" is answered **none**, and that is the correct answer: a configuration write precedes every run it might affect.

#### I. Composition with 005, non-negotiables, and verification

- **FR-080**: **005's shell is untouched.** Six tabs, the same order, the same labels, the same mount-once and keep-mounted rule, the same read-state rules, the same teardown completeness. The Settings body gains controls and loses nothing 005 gave it. Every control it adds is disposed with the body, and no timer, subscription, or in-flight write survives teardown (005 FR-013, FR-017; 005 NFR-108).
- **FR-081**: **No second rendering of the same value.** The poll interval appears on Status and on Settings because they own different values (FR-019); it MUST NOT appear on Bindings, Dispatches, Accounts, or About. Neither 005's "one element, one rendering" rule for the starting prompt (005 FR-051) nor its vocabulary rules are disturbed by this feature, and the tab introduces no new user-facing term: the product still says *Bindings* and *Dispatches*, and *Settings* keeps its name.
- **FR-082**: **Token and credential configuration is untouched.** This feature adds no token input, no scope control, no account identifier, and no credential read-back. Accounts owns custody (002 FR-006, 005 FR-060 – FR-069) and nothing migrates here (FR-017).
- **FR-083**: **The automatic requeue budget is not added as a field.** 003 FR-033 states that the number of automatic requeues is bounded and 003's confirmed gate answer describes the value as operator configuration, but no field, bound, default, store location, or consumption site is named anywhere in 003 or in the code. Adding an eleventh field would therefore be **inventing** it, and would hand an operator a dial wired to a lease-expiry sweep that does not exist. It is recorded as a **documented backlog item** with the full reading and the condition for lifting it — see `## Deferred: the automatic requeue budget`.
- **FR-084**: **No setting is invented, and no setting is inert.** The surface is exactly the ten documented fields and nothing else; a knob with no requirement would be pure noise, and a knob with no **consumer** would be the exact defect the gate answer of 2026-09-28 removed from this specification — which is why every field now carries a specified consumer (FR-034 – FR-036, FR-055 – FR-059) and why **adding an eleventh field without one is forbidden by this feature's own lesson**, not merely discouraged. The requeue budget is the one candidate still refused, and `## Deferred` states the condition under which it becomes a field with a consumer of its own. Any future field is a separate feature with its own requirement, its own bounds, its own consumer, and its own take-effect class.
- **FR-085**: **Code quality is the floor, not the aspiration.** Zero suppressions and zero `any` (`AGENTS.md` invariant 7); one validator — the service's; one service-call wrapper set, extended rather than forked (FR-043); one dispatch path (005 FR-088). A panel that grew a second configuration validator would have two sources of truth about the same ten numbers, which is the drift this feature is built to end.
- **FR-086**: **Everything is testable offline.** No test may require a live OpenChamber instance, a real personal access token, or network access (005 FR-086). The panel is tested against the fake host and DOM helpers; the service against a temporary-directory store with a driven clock and a captured log sink; the take-effect classes against observation rather than assertion of a constant; the manifest against the official SDK parser; the bundles against their existing shape and secret assertions. The secret-scan suites gain cases for the new surfaces and **no exemption**.
- **FR-087**: **Release discipline.** Any change under `src/`, `panel/*.ts`, or `service/*.ts` ends with `npm run build` and the rebuilt bundles committed in the same commit (`AGENTS.md` invariant 1). `panel/main.js` remains an IIFE, `service/main.js` remains an ESM module, `SERVICE_VERSION` stays pinned to `package.json` by test (invariant 5), and the project stays **pre-1.0.0** — no requirement here is a reason to bump `version`, and `1.0.0` remains a product-owner decision (invariant 2).
- **FR-088**: **The panel creates nothing.** No project, worktree, session, or agent is created, deleted, or mutated by this feature (002 FR-004, 002 FR-028, 005 FR-089), and any surface that appears to offer such an action MUST instead offer the guidance to perform it in OpenChamber's own surfaces.
- **FR-089**: **The tab is reachable in one click and reads without the service.** Settings is one of the six tabs, is reached in one activation, and renders its static content, its reason, and a retry affordance in every state where the service cannot be read (005 FR-078, FR-060). Nothing about this feature makes the panel depend on the service being up in order to explain itself.

### Key Entities

- **Configuration field**: one of the ten documented settings. Carries its name, kind, unit, bounds or accepted values, documented default, current value, and **take-effect class**. The field is the unit of both the panel's rendering and the service's validation, and it exists in exactly one declaration that both sides read.
- **Take-effect class**: one of `immediate`, `next-cycle`, `restart`, `none` — a **tested claim** about when a saved value changes behaviour, backed by an observed consumer. As of v1.1.0 the ten fields are nine `next-cycle` and one `immediate` (`logLevel`); `restart` and `none` remain in the closed vocabulary but are declared by no field in this feature.
- **Configuration document**: the whole-file `ServiceConfig` — the unit of the write. Either it is accepted whole or nothing is written. There is no partial document, no patch, and no per-field write.
- **Save**: one activation sequence producing exactly one write, or zero. Carries a state — idle, editing, saving, saved, refused, failed — and, when the write changed something, the configuration the service returned.
- **Pending field**: a field whose configured value differs from the effective value the machine is running with, carrying the boundary that governs when they reconcile. Visible on Settings; named on Status as the difference between the two values it owns.
- **Configuration issue**: one service refusal entry — a field name and a remediation, never a value. Additive: a refusal reports every bad field at once. The panel renders these and invents none.
- **Confirmation**: the arm-then-act step required before a write that lowers a retention knob, or that restores defaults. States what will change and, for retention, what will be deleted, when it will be deleted, and what survives it.
- **Audit rows**: `config.changed` (accepted or refused) and `audit.trimmed` (written by either trim pass whenever it removes something — FR-055, FR-057). Both are service-wide rather than run-scoped, both carry their own correlation identifier, and both are credential-free by construction and by the writer's redaction pass.

## Audit Rows

Both rows are specified here; neither name is new, and the trim row is written by **both** passes FR-055 and FR-057 describe, in the one vocabulary 002's data model already reserves for "the trim itself is auditable". `from`/`to` on an accepted write are bounded integers or one of four accepted level names — the configuration document holds no credential-shaped member by construction, and `appendAudit`'s redaction pass runs over every row regardless (003 FR-061; 005 NFR-102).

| `eventType` | Actor | Written when | `entity` | Decision | Required `details` |
| --- | --- | --- | --- | --- | --- |
| `config.changed` | `operator` when the write arrived through the panel, `service` otherwise | A whole-document configuration replacement is accepted **and changed something** (FR-048) | `{ kind: 'service', id: <the configuration> }` | `applied` | `changes`: one `{ field, from, to }` per changed field, ordered by field name, documented fields only. `takesEffect`: the declared take-effect class of each changed field. **No** submitted value from a refusal, and no foreign key name |
| `config.changed` | as above | A replacement is refused by validation | same | `refused` | `issueCount`; `fields`: the **documented** field names the refusal named, with any withheld marker preserved as withheld. **No submitted value of any kind** — not the offending value, not an accepted value, not a length, not a hash — and **no foreign key name**, which is recorded as the withheld marker |
| `audit.trimmed` | `service` | **Either** trimming pass actually removes something — audit entries (FR-055) or stored payload excerpts (FR-057) | `{ kind: 'service', id: <the configuration> }` | `trimmed` | `entriesRemoved`; `oldestSeq` and `newestSeq` removed; `limitReached`: `day-window`, `entry-cap`, or `excerpt-days`; `minimalReferencesPreserved`: the count deliberately kept (FR-056). **Appended only after the removal succeeds, and never when nothing was removed** |

**Correlation.** Each of these rows mints **its own** correlation identifier and records **no run reference** (003 FR-052, FR-074). They are not retrievable under a run's identifier, and no run-filtered view includes them. The identifier is the operator's handle for the row.

## Non-Functional Requirements

- **NFR-101 Rendering safety.** Every string the Settings tab adds renders through the existing non-HTML path (FR-029, 005 FR-080). The sharpest case is the remediation text: it is service-chosen prose about an operator-submitted value, and it is the one string on this tab that is not a fixed label. Verified by a rendering test that supplies remediation text containing markup and secret-shaped content and asserts neither reaches the document as markup and no secret-shaped substring survives.
- **NFR-102 Secret containment.** Zero credential occurrences in any panel state, any `host.storage` value, any rendered surface, any audit row, any log line, or either committed bundle (002 FR-007, 003 NFR-106, 005 NFR-102). Extended with: the refused-write row carries no value of any kind (FR-072), an unknown key name is recorded only as withheld, and the secret-scan suites gain cases for the Settings edit surface rather than being granted an exemption.
- **NFR-103 Durability and preservation.** A refused write leaves the stored configuration byte-identical, because validation runs before any storage access and a whole-document write is all-or-nothing after it (FR-025, FR-040). Verified by a test that captures the stored document before and after every refusal class.
- **NFR-104 Idempotency of read.** Opening Settings, switching away and back, refreshing it, and receiving a read all issue **zero** writes (FR-049). A panel that configures because it was looked at cannot be looked at.
- **NFR-105 Offline determinism.** Everything this feature adds is testable with no live host, no real token, and no network (FR-086). The take-effect classes are testable against a temp-directory store with a driven clock and a captured log sink; the refusals are testable against the real validator; the schema projection is testable by asserting it equals the declaration the validator reads.
- **NFR-106 Compatibility.** Unchanged SDK pin, unchanged engine floor (`>=1.24.0`), no new host capability, API, or permission, no undocumented or private interface (FR-004, 003 NFR-110, 005 NFR-106).
- **NFR-107 Accessibility.** Every field, control, and confirmation step is keyboard-operable with visible focus and no trap; every field's accessible name carries its name, unit, and take-effect boundary; confirmation text is reachable in DOM order and rendered as text; state is conveyed as text and not by colour alone (FR-018, FR-039, 005 FR-083).
- **NFR-108 Teardown completeness.** The Settings body owns no timer and no host subscription that survives teardown, and an in-flight save at teardown is abandoned rather than completed against a disposed runtime (FR-080, 005 FR-017). Verified by the same node/timer/disposer counting test 005 uses.
- **NFR-109 Code quality.** Zero suppressions, zero `any`, one validator, one wrapper set, one dispatch path (FR-085, `AGENTS.md` invariant 7).
- **NFR-110 Release discipline.** Both bundles rebuilt and committed with their sources; `SERVICE_VERSION` pinned to `package.json` by test; the version remains pre-1.0.0 and is not bumped incidentally (FR-087, `AGENTS.md` invariants 1, 2, 5).
- **NFR-111 Observability.** A refused write renders the service's reasons; a failed write renders its cause and, where present, the service's correlation identifier; a saved change states its take-effect boundary; a missing audit row is surfaced rather than swallowed (FR-013, FR-064, FR-070). A panel that cannot account for a change it just made must say so.
- **NFR-112 Honest effect labels.** **No field's rendered affordance, hint, or copy implies an effect that field does not have — and no field in this feature lacks one.** A pending value says which boundary governs it; a retention limit names what it governs and, when it is lowered, what will be deleted, when, and what survives; the poll-retry rows say *poll requests* and never *requeues* (FR-035, FR-052). What is forbidden is the mirror image of the old defect: v1.0.0's hazard was a row claiming an effect it did not have, and the gate revision's hazard would be a row claiming the absence of one — "changes nothing in this build" — about a field this feature has wired. This is the single NFR this feature should be reviewed against, and it is the one 005's NFR-112 established for the whole panel.

- **AC-131**: Given an unauthorised answer, when it renders, then it reads *not authorised* and no retry loop runs.
- **AC-132**: Given a transport failure, when it renders, then it is distinguishable from a value refusal and no unread value is displayed.
- **AC-133**: Given an unexpected failure carrying a correlation identifier, when it renders, then the identifier is copyable and no automatic retry occurs.
- **AC-134**: Given a last read that is stale and a current read that fails, when the operator looks at the tab, then the previous values are visible, marked stale, with the cause named.
- **AC-135**: Given an accepted write changing two fields, when it completes, then exactly one audit row exists with actor `operator`, decision `applied`, and one `field`/`from`/`to` triple per changed field.

- **AC-137**: Given a configuration row and a dispatch-lifecycle row, when both are read, then each carries its own correlation identifier and a run-filtered read excludes the configuration row.
- **AC-138**: Given a trim pass that removes entries, when it completes, then exactly one `audit.trimmed` row — appended after the removal — records what was removed, which limit was reached, and that minimal run references were preserved; and given a pass that removes nothing, no such row exists.

- **AC-140**: Given the Settings tab, when it is rendered with the service unreachable, then its static content and the reason are present and no number is shown that did not come from a read.
- **AC-141**: Given all six tabs, when they render, then the configuration is editable in exactly one of them and the poll interval appears only on Status and Settings, each owning the value it owns.
- **AC-142**: Given the Bindings, Dispatches, Accounts, and About tabs, when they render, then none shows a configuration control, a token input, or a credential.

- **AC-144**: Given the full suite, when it runs, then no test requires a live host, a real token, or network, and `npm run verify` was green before the commit.

## Deferred: the automatic requeue budget

**This section is a decision record, not an omission — and the product owner confirmed it at the gate on 2026-09-28 (answer 4): `requeueBudget` is not added, 003's v1.3.0 record amendment stands, and nothing below changes.** 003's FR-033 states that "**the number of automatic requeues for one run MUST be bounded**" and requires that exhaustion park the run in a dead-lettered state. 003's `## Assumptions` records "**Maximum automatic requeues**: 3 … **Confirmed by the product owner 2026-09-28**". 003's `## Resolved Gate Questions` entry 3 confirms that value and adds one sentence about what it is:

> "No alternative was recorded at the gate; **the value is operator configuration, so it remains adjustable without a behavioural change.**"

**006's reading, stated in full so it can be checked or overturned.** That sentence asserts the value *is* configuration. It does not give it a home. FR-033 is written entirely in terms of behaviour — bounded, park, exclude, resolve — and names no field, no bound, no default, no store location, and no consumer. The `3` exists only as a confirmed assumption. There is no storage story: nothing in 003's `## Audit Vocabulary`, `## Dispatch State Model`, `## Correlation Model`, or `## Out of Scope` names a configuration field, and nothing in `service/` reads a requeue bound, because the lease-expiry sweep that would consume one (003 FR-030 – FR-032) is not implemented.

**006 therefore does not add the field.** Two reasons, both load-bearing:

1. Adding an eleventh field would **invent** it. The product owner chose full CRUD over the **service's settings**; a knob that no requirement defines and no code reads is not one of them, and FR-084 holds this feature to the ten that exist.
2. Even if the field were added, it would be **inert in exactly the way this specification spends its hardest words preventing**. Its consumer is 003's unimplemented lease-expiry sweep. An operator handed a dead-letter-budget dial before the sweep exists would set it, see nothing happen, and reasonably conclude the panel had lied — which is NFR-112's exact failure, and the reason the gate revision wired the fields that *do* have consumers rather than labelling them inert. The correct time to add it is when the sweep lands, at which point the field gets the same whole-file treatment, the same bounds, the same additive refusal, and its own take-effect class.

**When this changes.** The moment 003's lease-expiry sweep is implemented, the budget becomes an eleventh field on `ServiceConfig` with bounds chosen against the sweep's own semantics, a documented default of 3 matching 003's confirmed value, the same whole-file validation treatment, and a declared take-effect class. That is a change to 003's implementation, not to 003's requirements — FR-033 already says *bounded*, and 003's `## Audit Vocabulary` already names `run.dead-lettered` with "attempts consumed" as its detail. Nothing in 003 needs rewriting to accommodate it.

**What is not deferred.** 003 FR-032, FR-033, and FR-036 stand verbatim, and this specification changes none of them (FR-001, FR-083). The dispatch state model, the dead-letter semantics, and the operator's *Return to waiting* affordance are untouched by anything here.

## Out of Scope

The following are explicitly **not** part of this feature:

- **003's run-attempt, lease, and requeue machinery.** The retry fields are HTTP-poll retry (FR-058) and consume none of it: 003's attempt counter, its lease-expiry sweep, and its automatic requeue budget remain 003's, `requeueBudget` stays deferred (confirmed at the gate, answer 4; `## Deferred` above), and the panel MUST NOT label the poll-retry knobs with run-model vocabulary (FR-035, FR-058).
- **The correlation-indexed read API** — the other half of the T-027 deferral `service/audit.ts:13` records. Trimming is specified here (FR-055, FR-057); reading the trail by correlation id is not.
- **Changing the page cap or the dispatched-tail cap.** `MAX_LIST_PAGES` stays 2 and `MAX_DISPATCHED_EVENTS` stays 500; `perPage` sizes a page and the excerpt trim removes text rather than rows (FR-057, FR-059).
- **Auditing re-observed duplicates as `poll.duplicate`.** Overlap widens the window and the deterministic event id suppresses the replay; whether a duplicate observation leaves its own row is 002 FR-023's clause and is unchanged by this feature.
- **Restoring trimmed data.** Trimming is destructive and irreversible; export/restore remains out of scope (002 FR-034), which is exactly why the confirmation must say what will be deleted before it is (FR-052).
- **The automatic requeue budget as a configuration field.** Deferred with the full reading and the condition for lifting it, in `## Deferred` above.
- **Any new setting or knob.** The surface is exactly the ten documented fields (FR-084).
- **Any change to the trigger set or the dispatch mechanism.** This feature adds configuration readers on the cycle boundary — the window, the page size, the retry ladder, both trim passes — and changes no trigger detector, no relay loop, no `host.startSession()` framing, and no dispatch path (FR-032, FR-047, FR-055 – FR-059).
- **Any change to the status projection.** 006 populates only the Settings half of 005 FR-039's configured/effective pair; 005 FR-031 – FR-034 own the projection.
- **Any new tab, sub-tab, drawer, or settings surface.** The edit surface lands inside 005's tab (FR-010).
- **A redesign of the Settings tab's information architecture.** 005 owns the tab's composition; 006 adds controls to its rows and a save bar beneath them.
- **Token, credential, or scope configuration.** Accounts owns custody (002 FR-006, FR-082).
- **Bindings, accounts, or dispatch surfaces.** Unchanged (FR-019, FR-047).
- **Any GitHub write**, in any role (002 FR-031, 003 FR-002, FR-002).
- **Export or restore of configuration.** 002 FR-034 and 005 `## Out of Scope` place it in backlog; this feature neither adds nor removes it.
- **Per-field or optimistic-concurrency writes.** A revision precondition on `PUT /v1/config` is not added (FR-045; confirmed at the gate — `## Resolved Gate Questions` entry 2).
- **Configuration-driven policy profiles, approval gates, or per-action autonomy toggles.** 002 FR-027's gates remain documentation-only; `service/routes/status.ts`'s `pausedReason` vocabulary is 005's.
- **Multi-instance or cross-machine behaviour, multi-tenancy.** The documented deployment is one operator, one panel, one service instance.
- **A mobile or narrow-native settings layout.** The panel remains an extension rail and stays usable at the narrowest width the host allows; ten fields with two extra sentences each is a layout constraint Phase 4 sizes.
- **Phase 4 plan, research, data model, contracts, and the Phase 5 task breakdown, and Phase 6 implementation.** Those are the architect's phases.

## Assumptions

Each assumption below is a documented default chosen where the requirement text and the predecessors' text were silent. Each is reversible without a redesign, and each was a candidate for the gate; the gate was held on **2026-09-28**, and its four answers are recorded in `## Resolved Gate Questions` and `## Clarifications` rows 15–18. Where an answer overturned a default (entry 1), the bullet below states both what v1.0.0 encoded and what the gate accepted.

- **The take-effect classes in `## Per-Field Contract` are read from the shipped code and from this feature's own requirements, not inferred from a field's name.** At v1.0.0 this gave `none` to every field the shipped build did not read; **the gate overturned that** (answer 1: *"Also wire all fields (~3× size)"*), so each of those fields now has a specified consumer — two trim passes, a poll backoff, the scan window, and the page size (FR-055 – FR-059) — and each class names the boundary that consumer actually delivers. Where the shipped code alone was the evidence (`intervalMs` = `next-cycle`, `logLevel` needing a service change for `immediate`), that evidence is unchanged. SC-106 plus SC-107 are the tests that hold it.
- **`logLevel` is made `immediate` rather than `restart`.** Chosen because it is the cheapest field to make genuinely live, because the change is to stop treating a constant as a constant, and because two live fields made the contract demonstrable rather than theoretical at v1.0.0 — a claim that became *every* field at v1.1.0. The cost is a real service-side change and a stricter rule: it may not be downgraded to `restart` without returning to the product owner (FR-037). **Confirmed at the gate as encoded (`## Resolved Gate Questions` entry 3, gate answer 3).**
- **Last-writer-wins, no revision precondition.** Chosen for consistency with `PUT /v1/bindings`, which 005 FR-058 already accepts on the same basis, and with the documented one-operator, one-panel, one-service deployment. The cost is retained and visible: a second panel's save is silently lost, so the panel states that a save replaces the whole configuration and names the fields it is about to change (FR-045). **Confirmed at the gate as encoded (`## Resolved Gate Questions` entry 2, gate answer 2).**
- **Trimming runs at the cycle boundary, not on the write.** Chosen so a configuration write keeps FR-047's promise — it touches `config.json` and the audit trail and nothing else — so the retention knobs' class stays `next-cycle` rather than `immediate`, and so a trim serializes with the poll loop's own chain instead of running inside a route handler. The cost is visible and stated in the copy: a lowered limit takes effect at the next cycle boundary, up to one cycle late, and the confirmation says when (FR-052, FR-055).
- **A no-op write is not a change.** Chosen because a trail that records every double-click as a configuration change stops being evidence, and because the panel already has a distinct and honest word for it: *already saved* (FR-048).
- **A refused write leaves one row; a no-op leaves none.** Chosen together because "a refusal is a change" would be false and "a no-op is a change" would be noise. A refusal row records the fields refused and never a value, which is strictly narrower than the refusal body the operator already saw (FR-072).
- **The save bar sits beneath the ten rows rather than in a header or a per-row control.** Chosen because the write is whole-document, so a control that appeared next to any single field would misrepresent the mechanism (FR-012).
- **Restore defaults is offered.** Chosen because the product owner chose **full CRUD**, and on a whole-document resource whose fields are all required, the only meaningful form of "delete" is returning the field to its documented default. It is non-primary, names every field it changes, and uses the same two-step confirm (FR-016).
- **The schema projection rides on `GET /v1/config` rather than a new route.** Chosen because the projection and the effective document must be consistent with each other, and two reads could disagree; one read cannot. It is the only change to a read this feature makes.
- **Panel-side validation is absent by design.** Chosen deliberately against the usual instinct for a form. A client-side range check is a second copy of the service's bounds, and 002 FR-024 plus 005 FR-052 make the service the single authority; a panel that pre-empts a refusal is a panel that will eventually disagree with the service about what is acceptable. Declared bounds shape the control and the hint and gate nothing (FR-023).
- **Scale**: fewer than ten bound repositories, a handful of accounts, one local OpenChamber installation, one logical service instance, one operator machine — 005's assumptions, unchanged. Concurrency correctness is required across panels, not across service instances.
- **Provider**: GitHub.com REST API; unchanged and still requires later review.
- **The service is expected to be running for any write.** The panel does not attempt to obtain configuration authority by another route, and a write is never attempted against a service it could not reach (FR-060 – FR-062).
